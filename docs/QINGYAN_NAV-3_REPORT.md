## 1. 用户现在会怎么看到

- **今日询盘「待审批回复」**：点「查看草稿」展开后，草稿下面多了一行「想改一改再发？去询盘收件箱改这份草稿（发出后这份草稿自动作废）」。不展开时看不到这行。原来卡片底部那行「不想用这份？去询盘收件箱自己写」没有了。
- **商机详情的待批草稿**：同一行链接，位置不变（那里的草稿本来就是展开的）。
- **点进去**：到询盘收件箱，回复窗口标题是「改草稿再发 · 〈公司〉」，主题和正文已经是这份草稿的原文，上面照常是买家最后一封来信。窗口里写着：「这是等审批的那份 AI 草稿，改好后点「发送邮件」。发出后那份草稿自动作废，不用再去批准；从这里发出的是普通文本邮件。」
- **改完点「发送邮件」**（或在别处发完点「已在别处发送，标记」）：和平时在收件箱回复一样。今日询盘里那张待批卡随之消失，不用再去批。
- **草稿原定的收件邮箱和这位买家在收件箱里的邮箱不一样时**：窗口里有一行黄色提示，写明原本发给谁、从这里发会发给谁。
- **草稿已经处理过或过期时**：页面提示「这份待批草稿已经处理过或已失效，可以直接在下面写回复」，窗口照常打开，正文是空的。
- **想完全自己写**：点进去把预填的文字删掉即可。
- 从客户时间线点「回复」、收件箱卡片上的按钮、「批准发送」「拒绝」，都没有变化。

## 2. 草稿原文从哪来、什么时候给

待批草稿的载荷里有主题和纯文本正文，直接取用（任务书的前置条件「核对草稿载荷里是否存有可直接复用的原文」：有）。审批卡上显示的「预览」不能用——它在原文前面拼了风险提示、后面拼了中文对照。

单会话接口带着草稿 id 请求时，七个条件全满足才返回原文：

| # | 条件 |
|---|---|
| 1 | 这条审批记录属于本企业 |
| 2 | 类型是询盘回复 |
| 3 | 状态为待批 |
| 4 | 未过期 |
| 5 | 它关联的商机就是这位买家的商机 |
| 6 | 买家不是入驻测试询盘的测试买家 |
| 7 | 主题与正文都非空 |

任一条不满足一律为空，不区分原因。返回的只有四个字段：草稿 id、主题、正文、原定收件邮箱；不带 HTML 版、预览与内部元数据。

## 4. 这条路与「批准发送」的差别

改后发出走的是既有的「成员本人在询盘收件箱点发送」，不是审批执行。待批草稿没有被批准，也没有被执行；发出后由既有规则作废，并按既有规则记一条「人工已回复」的改稿反馈（对比的是草稿与实际发出的文字）。

| 审批执行时的检查 | 走收件箱这条路时 |
|---|---|
| 入驻测试询盘一律不发 | 这类草稿不提供原文（上表第 6 条） |
| 收件人取草稿里的邮箱，且须与客户档案一致 | 发给线索的邮箱；与草稿里的不同时窗口里写明 |
| 起草之后已有外发就拒绝 | 这种草稿此时已被既有规则作废，取不到原文 |
| 买家在起草之后又来了新信就拒绝 | 没有照搬成拒绝；窗口上方显示买家最新一封来信，由人判断 |
| 发出的邮件带起草时渲染的 HTML 排版 | 发出的是普通文本邮件，窗口里写明 |
| 发件身份是组织发件身份（没有配置时退回审批人邮箱） | 发件身份是外贸发件身份 |

**关于「出站先审批」**：持 `trade.manage` 的成员可以不经草稿指定的审批人点「批准」，把这份 AI 草稿改完自己发出去。这在以前也做得到（看着审批卡抄过去，或用收件箱自己的 AI 分析草稿），这次省掉了抄的一步；审核时 Q1 定为接受，并把今日询盘上的入口改为先展开草稿才出现。以后如果要收紧（例如只有审批人本人能带走草稿），需要另立 change。

## 5. 与四件套不一致、或实施中才发现的

1. **入驻测试询盘这一条是起草四件套时才加的**（Q6）。任务书没有提。核对审批执行的代码时发现它承诺「入驻测试询盘不会发送给买家」，而收件箱这条路没有同样的检查，所以让这类草稿带不进编辑框。注意：收件箱的回复接口本身仍然没有这道检查——对测试买家手写一封并发送，以前就做得到，这次没有改。
2. **`reply-clarity.test.ts` 没有需要调整的断言**（tasks 2.1 预计要改）：深链分支的形状没有变，只是在里面多带了草稿。`reply-entry.test.ts` 改了三条（旧链接文字换成新的）。
3. **实施中我自己出过一次错**：做反向验证时，两个被备份的文件都叫 `page.tsx`，备份互相覆盖，恢复时把今日询盘页的内容写进了收件箱页。当时收件箱页的改动还没提交。处理：从 git 还原该文件，按原脚本重做一遍修改，重跑全部相关测试后才提交。提交里的内容是重做后的版本。
4. 使用说明「我想做什么」第 3 行仍写「不想用就去询盘收件箱自己写」。它没有引用这行链接的原文，意思也还成立，按 design 没有动。

## 8. 上线注意

- 合并即生效，没有开关，没有数据迁移；回滚 = revert。
- **没有在真实发信环境里验过。** 与 NAV-1c 相同：本机没有配置发信，测试走的是「已在别处发送，标记」那条分支（同一个接口、同一套留底与外发同步）。建议并进 NAV-1c 那一遍 staging 验收里一起走：
  1. 用梦馨「老板 + 外贸业务员」的测试账号，从官网表单提交一条测试询盘（收件邮箱填内部邮箱），等 AI 草稿出现在今日询盘。
  2. 点「查看草稿」→「想改一改再发？…」，确认到了收件箱、窗口里是这份草稿。
  3. 改一句，点「发送邮件」。确认内部邮箱收到的是改后的文字，是普通文本邮件。
  4. 回到今日询盘：这张待批卡应当消失。
- 通知梦馨时可以加一句：AI 写好的回复如果只想改一两句，展开草稿后点下面那行，改完直接发，不用再批。
- 后续候选（都不在本 change）：让收件箱发出的邮件带审批发送的排版；收件箱回复接口对入驻测试买家的检查（§5 第 1 条）；只有审批人本人能带走草稿（§4）。
