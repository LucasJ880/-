## 1. 做了什么

**现状**：发询价一轮只批一次，但催单与缺字段追问是每家供应商每次一张卡，48 小时不批就过期。一轮 8 家最多 24 张。

**现在**（开关打开、网页发起、发起人勾选时）：

1. 发询价的审批卡多带一份**跟进授权**：催单最多 2 次、间隔天数、回复截止、允许一次缺字段追问、模板指纹。卡上显示这份授权和三段模板预览。批准这张卡 = 批准首封 + 授权范围内的后续邮件。
2. 之后每 10 分钟一次的既有扫描判定「该催了」时，逐封做**覆盖判定**（20 个条件）。覆盖得住：照旧为这封邮件建审批记录，然后以批准该轮的人的身份经既有审批入口执行，不等人点。覆盖不住：照旧建待批卡等人批，并记下原因。
3. 每封自动执行的邮件另写一条审计，指向发询价的那张卡，注明这是「随轮次授权」而不是那个人当时的一次点击。
4. 轮次里显示自动跟进的状态（生效中 / 已停止 / 未生效：原因）和已自动发出的封数；有项目写权限的人可以**停止**，停止不可恢复、留审计。

**没有变的**：没有任何邮件能在人批准之前发出；带授权的卡只能在网页上、看得到授权范围的地方批（Muse 里不能批）；没有「白名单免批」；催单与追问的模板文字、节奏（3 天、最多 2 次）、回信解析、比价都没动；经 Muse 发起的轮次不带授权，照旧逐张批。

## 3. 覆盖判定的 20 个条件

任何一条不满足都退回逐张人工批。按检查顺序：

| 原因码 | 含义 |
|---|---|
| `FLAG_OFF` | 开关关闭（包括批准之后才关掉） |
| `NO_ROUND_CARD` | 找不到这一轮的发询价卡 |
| `NO_POLICY` | 卡上没有授权（Muse 发起的、没勾选的），或授权内容不合规 |
| `ROUND_CARD_NOT_EXECUTED` | 发询价卡还没批准并发出 |
| `NOT_HUMAN_APPROVED` | 卡上没有批准人 |
| `APPROVER_INACTIVE` | 批准人已不是本组织在职成员 |
| `ROUND_NOT_IN_PROGRESS` | 轮次已取消或已完成 |
| `STOPPED` | 已停止自动跟进 |
| `PRIOR_ATTEMPT` | 这封邮件此前起草过（过期没人批，或自动执行时发送失败） |
| `KIND_NOT_ALLOWED` | 授权不包含这种邮件 |
| `OVER_LIMIT` | 超过授权的次数 |
| `DEADLINE_PASSED` | 回复截止已过（只限催单） |
| `TEMPLATE_CHANGED` | 模板在批准之后改过 |
| `RECIPIENT_CHANGED` | 收件人与原询价邮件不一致 |
| `THREAD_MISSING` | 原邮件线程缺失 |
| `SUPPLIER_RENAMED` | 供应商名称在批准之后改过 |
| `SENDER_CHANGED` | 发件抬头或回信邮箱在批准之后改过 |
| `SUBJECT_CHANGED` | 原询价邮件的主题对不上 |
| `DEADLINE_CHANGED` | 回复截止在批准之后改过 |
| `SENSITIVE_TEXT` | 正文命中对外敏感词 |

后四条（改名、发件人、主题、截止）是独立审查后补的，见 §5a。`PRIOR_ATTEMPT` 是实施中补的：否则邮箱授权失效时，每 10 分钟的扫描会不停重试并留下一串失败记录。规格与 design 已同步。

## 4. 顺带修的两个现存漏洞

这两处对**人工批准的卡同样生效**，不受开关控制：

1. **轮次取消或完成后仍能催**：以前扫描与执行器都不看轮次状态。现在扫描只看进行中的轮次；执行器发之前再查一次，已取消 / 已完成就不发并说明原因。
2. **过了回复截止仍能发催单**：以前只有扫描在起草时看截止，执行器不看（卡在截止前建好、截止后才批就会发出）。现在执行器也查。追问不受截止限制。

## 5a. 独立审查发现并已修复的问题

实施完成后、开 PR 之前，请了一个不带结论的独立审查，专找「授权范围之外能自动发出邮件」的路径。它确认了下面几处，都已修复并补了测试：

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 自动发出的正文没有和批准的那张卡绑定：供应商名称、发件抬头、回复截止在批准之后别人能改 | 任何成员把供应商改名成一句话，这句话就会出现在以批准人身份自动发出的邮件开头 | 覆盖判定加四条：供应商名称、发件人、原邮件主题、回复截止必须与批准的卡一致，否则退回人工批 |
| 2 | 带授权的卡能在 Muse 里只看标题就批 | 批准人没看到授权范围，每家供应商最多 3 封后续邮件就被授权了 | 带授权的卡在 Muse 里不能批（提示去网页）；标题标明「含自动跟进授权」 |
| 3 | 扫描过滤写成「必须是进行中」 | 草稿状态的轮次（经旧入口逐家标记发出的）不再被催，也不再自动标记「无回应」——开关关闭时也受影响 | 改为只排除已取消与已完成 |
| 4 | 覆盖判定看的是这次起草的内容，不是库里那张卡 | 同一幂等键下若先有一张内容不同的卡，会被代为批准 | 代为执行前按组织与类型读出库里的卡，逐字段核对一致才执行 |
| 5 | 审计在发送之后写，且执行途中抛错会跳过；并发时可能写两条 | 「已自动发出 N 封」可能多计或漏记 | 抛错时按库里的实际状态核对后照样留审计；封数按催单卡去重 |
| 6 | 抽屉里写「过了回复截止后不再发」 | 与实际不符：缺字段追问不受截止限制 | 文字改正 |

审查确认没有问题的部分：发询价卡的查找与组织隔离、收件人始终是批准时的收件人、授权无法在批准后被伪造或放宽、次数上限与并发、失败后不自动重试、停止接口的权限与隔离、测试钩子在生产环境无效。

审查提到但没有改的：`loadRfqMail`（读原询价邮件主题）的查询没有带组织条件——这是本变更之前就有的写法，轮次号来自已按组织过滤的询价项，审查没有找到可利用的路径；留给后续。

## 6. 需要 Owner 明确确认的一处：硬纪律第 2 条的补充文字

`openspec/config.yaml` 硬纪律第 2 条末尾加了一句：

> 一张已批准的审批卡可以一并授权它正文里逐项写明的后续固定模板邮件（目前仅限招投标询价轮次的催单与缺字段追问：次数、间隔、截止、模板指纹都写在卡的载荷里并受哈希保护）；这些后续邮件仍须逐封建 PendingAction 并经执行器发出，由系统以该卡批准人的身份执行并另写审计；任一授权条件不满足即退回逐封人工批准。

「批准前零出站」没有放宽。这句话只说明「批准」可以一次覆盖一组事先写明的邮件，且范围写死为询价轮次的催单与追问。**不同意这句话的话，本 PR 不应合并。**

## 7. 设计取舍

| 决定 | 理由 |
|---|---|
| 授权放在发询价卡的载荷里 | 授权必须和「人看到并批准的那张卡」是同一个东西；载荷哈希天然覆盖它 |
| 每封跟进仍建自己的审批记录，再以批准人身份执行 | 执行器、去重、审计、界面都以单条记录为单位；不发明「一张卡执行多次」，那会绕开「终态不可重放」的保护 |
| 执行走既有的审批入口 | 权限、组织、状态原子切换、载荷哈希、执行器里的全部复核照常生效；批准人失去审批权时执行不了，卡留给别人批 |
| 间隔与截止在批准时定格 | 之后有人改设置，不影响已批准的这一轮 |
| 模板指纹 | 人批准的是当时看到的那版文字；模板改了，已批准的轮次自动退回人工 |
| 停止 = 一条审计记录，不可恢复 | 零 schema；恢复等于重新授权，那应当由人重新逐张批 |
| 只有网页发起且勾选才带授权 | Muse 上看不到卡上的授权说明 |

## 8. 已知限制

1. **以批准人的身份执行**：催单的审批记录上显示他是决定人，但他没有逐封点击。用单独的审计（`source: round_preapproval`）与轮次页的「已自动发出 N 封」说明。
2. **自动发出的跟进不单独通知**，在轮次里与审计里查。试用后再看要不要加。
3. **在审批中心、驾驶舱批准这张卡**只能看到标题里的「含自动跟进授权」与摘要里的一行范围说明，看不到模板预览。模板预览只在项目页的原地审批处有。Muse 里不能批这类卡。
3a. **勾选框默认勾选**（design D7）。规格写的是「明确勾选」；如果你认为默认应当不勾，改一行即可，请在 PR 里说。
4. **批准人离职后授权失效**，不转给别人——该轮退回逐张批。
5. **「要求确认后自动选供应商、自动起草一轮」没做**，是下一个 change（RFQ-AUTO-2）。现在仍需人打开「问供应商要价」、选供应商、点生成，然后批一次。
6. 界面没有组件级自动化测试（仓库没有这类设施），靠真实应用截图与服务层测试。
7. 测试用的钩子 `__setChaseExecuteIoForTest` 只在 `NODE_ENV=test` 生效，生产环境调用无效果。
