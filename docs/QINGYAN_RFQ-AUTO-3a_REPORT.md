## 1. 问题

个人开关「自动起草的轮次带跟进授权」的状态是本人最近一条开关记录。「最近」按记录时间排，而记录时间由写入那台服务器自己的时钟给出，不是数据库的时间。

于是：写「开启」的那台服务器时钟快一点，紧接着另一台处理「关闭」，「关闭」那条的时间反而更早——排序之后最近一条仍是「开启」。界面显示关了，实际还开着，之后自动起草的卡仍带跟进授权。时钟被往回拨也一样。另外，设置时「先读、再判断、再写」之间没有互斥。

**在修复前的代码上复现了**：把「开启」记录的时间拨后 30 秒，调关闭接口——返回成功，状态仍是「开」；随后批准招标分析，自动起草的卡带着跟进授权。

实际触发的概率很低：人的两次操作通常隔着几秒，服务器之间的时钟差通常是毫秒级。但这是表示同意的开关，撤回必须可靠，而且这个问题发生时没有任何提示。

## 2. 修法

`setAutoDraftFollowUpOptIn` 改为一个短事务：

1. 取本人的事务级锁（按组织 + 用户）。
2. 读最近一条记录。
3. 状态已经是想要的 → 不写。
4. 否则写一条，**时间明确给出：至少比上一条晚 1 毫秒**。

持有锁时上一条不会再变，所以新写的一条一定排在最后——不论各台服务器的时钟谁快谁慢。同一个人同时到达的两次设置依次执行。事务里只有这几条语句，不包任何别的调用。

没有变的：默认关；只能本人在网页上设置；开启要求两个功能开关都打开；关闭任何时候都可以；开启时绑定模板指纹；状态变了才追加记录；读取函数、接口、界面。

## 5. 独立审查

请了一个不带结论的独立审查。**它没有找到开关逻辑上的缺陷**：构造不出、也跑不出「后点的关闭没有成为读到的状态」的情形。它实际跑过的：

- 上一条记录拨后 1 小时再关闭 → 关；之后的记录每条比上一条晚 1 毫秒。
- 四个进程、时钟分别快 8 秒 / 准 / 慢 8 秒 / 慢 90 秒，对同一个人共 200 次设置 → 144 条记录，严格递增、严格交替；最后由慢 90 秒的那个进程关闭 → 关。
- 锁确实取到了（数据库里看得到），范围是组织 + 用户；同一个人在另一个组织、同组织另一个人互不影响。
- 新旧两种写法写出的记录，除记录号与时间外每一列都相同；没有别的地方读这些记录。
- 这一列在库里是毫秒精度，晚 1 毫秒一定排在后面。

它指出、已处理的：

1. **「同时到达的一开一关」那条测试测不到锁。** 原来的写法在没有互斥的旧代码上也能过（开着的时候再开一次本来就不写）。已换成「同时到达四次开启与四次关闭」：要求记录严格开关交替、时间严格递增。同一份测试拿到 `main` 的旧实现上跑，这一条写出的是「开关关关关」，失败。
2. **四件套漏了项目规定的固定内容**：design 里没有「与八条硬纪律的关系」「验证方式」两节，tasks 的每一条没有自带 verify。已补。（RFQ-AUTO-5 的四件套有同样的遗漏，在 #431 里补。）

它指出、判断为可以接受而没有改的，都写进了 design 的风险一节与下面的已知限制：极端并发下的排队失败、读开关与建卡之间的短空档（既有行为）、滚动发布期间新旧版本并存、依赖数据库默认的隔离级别。

## 6. 已知限制

- **修复之前已经排错的记录不回头改。** 如果某人现在的状态因为旧的时钟差而与他的最后一次操作不符，他在界面上看到的就是那个状态，点一次即可纠正——修复之后的写入一定排在最后。
- **上一条记录的时间如果被拨得很靠后**，之后几条记录的时间会跟着靠后，直到真实时间追上。先后是对的，只是时间戳不是真实的操作时间。
- **其它「最近一条记录即状态」的地方**：RFQ-AUTO-5 的供应商分组用同样的办法修了（在 #431 里）。RFQ-AUTO-1 的「停止自动跟进」看的是「有没有停止记录」，不看先后，没有这个问题。
- **极端并发下会失败而不是排乱**：同一个人的设置现在排队执行。审查实测同一进程内同时 400 次全部成功；1500 次时约一半因为等不到数据库连接而返回错误（什么都不写，界面提示「没有设置成功，请重试」）。旧实现这时全部返回成功，但记录的先后是乱的。
- **读开关与建卡之间有一个很短的空档**（既有行为，没有动）：恰好在这中间关闭的话，这一张卡仍带授权——它仍要人批准才生效。
- **滚动发布的几分钟里**新旧版本并存，旧版本的实例仍按自己的时钟写、不加锁。
- 隔离库测试在 CI 里是跳过的（CI 没有隔离库），只在本地跑。
