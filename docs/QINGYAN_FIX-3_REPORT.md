## 1. 问题

组织设置是一个组织一份、很多功能共用的一块配置：收信游标、Muse 的个人偏好与账号绑定、询价的发件设置、投标资料、日历监听、门店折扣、开户向导……它们的写法都一样——读出整块、改自己那一项、把整块写回——而且大多不加锁。

两处写入只要交错几毫秒，后写的就会用它读到的旧内容把先写的冲掉，没有任何报错。

**这不是理论上的问题。** 把七种真实的写入同时发起（回写收信游标、学习常用供应商、绑定 Muse 账号、保存询价设置、保存投标资料、切换运营手册执行模式、保存日历监听设置），在改动之前的代码上：

- 第一轮七项里就丢了四到五项；
- 同一个人同时选定 4 家供应商的报价，常用供应商里只留下 1 家；
- 同一个人同时设置贸易条款、设置催单天数、学习一家供应商，贸易条款丢了。

线上「同时」的机会比测试里少得多（多数写入是读完立刻写，窗口是毫秒级），但两个定时任务（收信、日历）让「有人在写」成了常态，而丢了的东西不会有任何提示。

## 2. 修法

新增一个写入入口 `src/lib/organizations/settings-write.ts`：在一个短事务里**锁住这个组织的行 → 读最新的设置 → 只改自己那一块 → 写回**。锁里只做「读一行、算、写一行」，不做别的查询。

锁只让「写同一个组织设置」的操作互相等待，不影响往这个组织新增任何别的数据（见 §6 第 1 条——第一版在这里错了，是独立审查抓出来的）。

然后把所有写入方都接上去：

| 写入方 | 改法 |
|---|---|
| 收信游标（定时任务） | 经入口 |
| Muse 个人偏好：保存、学习供应商、学习贸易条款 | 经入口；修改函数拿到的是锁里读到的最新偏好 |
| Muse `set_preference` | 校验留在锁外；保存时在锁里对最新的偏好再应用这一项修改 |
| Muse 账号绑定 | 成员校验留在锁外；写入经入口 |
| 询价设置接口 | 在锁里对最新的设置应用修改；不合规照旧 400、不写 |
| 投标资料 | 经入口 |
| 运营手册执行模式 | 经入口 |
| 日历监听：设置、游标（定时任务） | 经入口（原来的「写回前重读一次」变成真正的原子操作） |
| 门店折扣设置 | 在既有的事务里，读之前先锁行 |
| 开户向导：新建 / 接管 | 在既有的事务里，读之前先锁行 |
| 开户向导：更新设置 | 设置的合并从事务外挪到事务里，先锁行再读；审计的「之前」取锁里读到的 |
| 三个运维脚本：命令行绑定 Muse 账号、梦馨企业种子、发信说明设置 | 经入口 / 事务里先锁行 |

已经自己锁行的三处（斑马帘比例、质保设置、能力配额策略）没有动；新入口的锁与它们的锁互斥，所以新旧写入方之间也互相等待。

## 3. 范围比计划大，原因在这里

交接文档 §0.5b 的计划写的是「只改询价与 Muse 相关的这几处，销售、安装、开户等别处不动」。读完代码后这个范围不成立：

**只把一部分写入方改成加锁是不够的。** 加锁的写入方只会互相等待；一个不加锁的写入方照样可以先读到旧的整块，等别人提交之后再把旧的整块写回去。留下任何一处，就等于没修好，却让人以为修好了。日历监听的游标也是定时任务在写。

所以这次把 `src/` 下全部 11 处、加上 3 个会在生产上运行的脚本都改了，改动落到了销售（门店折扣）、开户、日历、运营手册这几个本任务之外的模块。每一处都只改「怎么写」：门店折扣只在既有事务里加了一句锁行；开户更新把「读设置」挪进了事务。这些模块既有的真库测试（开户 82 项、日历 80 + 32 + 44 项、价表折扣 54 项）都没改断言，全部通过。

Lucas 2026-11-11 看过这一点后答复：「范围可以，门禁过了就开 PR」。

## 6. 独立审查

请了一个不带结论的独立审查。它核对过、没有问题的：每个修改函数都是同步的、不做任何查询；`set_preference` 在锁里重新应用不会丢掉已通过校验的值；询价设置接口的 404 / 400 / 200 与审计；偏好「没变就不写」；日历游标的跳过条件；新建企业时锁语句匹配不到行是无害的；测试在旧代码上确实失败（它自己跑了三次）；连接池只有 1 个或 3 个连接时新测试也通过。

它找到、已修复的：

1. **锁的强度选错了（中高，最要紧的一条）。** 第一版用的是 `FOR UPDATE`。有 35 张表的外键指向组织；往这些表插入一行时，数据库会对组织行加一把很弱的锁，而 `FOR UPDATE` 与它互斥。三个后果，审查都跑出来了：
   - **新的死锁**：开户更新设置（先锁组织行、后改用户行）与用户切换当前组织（先锁用户行、后做外键检查）同时发生，120 次里 53 次死锁；旧代码 0 次。
   - **写设置被不相干的事务卡住**：别的事务插入了一条本组织的审计还没提交时，写设置要一直等；对方拿着 7 秒，写设置就超时失败。
   - **反过来也卡**：有人拿着设置的锁时，所有往本组织插入记录的操作都要等。

   改成 `FOR NO KEY UPDATE`——它正好是普通的 `UPDATE` 改非主键列本来就会拿的那把锁，与外键检查不冲突，写入方之间照样互斥（包括还在用 `FOR UPDATE` 的三处旧代码）。新增两条测试：有人拿着锁 0.9 秒时，插入一条本组织的审计、把用户的当前组织切过来都在几毫秒内完成，另一处设置写入要等；8 个「先插入、再锁行写设置」的事务同时进行不死锁。把锁换回 `FOR UPDATE` 重跑，这两条立刻失败（等了 910 毫秒；出现死锁）。
2. **三个会在生产上运行的脚本漏改了**：命令行绑定 Muse 账号、梦馨企业种子、发信说明设置。它们不在 `src/` 下，我的清点与守卫都没有扫到。三个都已改，守卫现在也扫 `scripts/`。
3. **三处改动没有测试能发现锁被删掉。** 审查把门店折扣和开户里的锁删掉，两个新测试照样通过。现在：守卫核对这几处「锁在读设置之前」；真库测试加了一段让开户更新设置、门店折扣与另外三种写入同时进行 10 轮。把锁删掉重跑，真库测试第一轮就丢四项，守卫也失败。
4. **守卫有漏网的写法**：按文件判断（文件里别处有一句锁就算过）；带 `//` 的字符串会让后半行被当成注释；不扫 `scripts/`。现在加了一份「直接写这一列的文件」名单，新增的必须先加进名单；注释剥离改了；扫描范围扩到 `scripts/`。仍然认不出的写法（`data` 是变量、经关联的嵌套写入、原生 SQL）仓库里现在没有，写在已知限制里。
5. **开户更新设置的审计**把锁外读到的「之前」和锁内算出的「之后」配在一起，别人在这中间确认的一步会被记成这一次的修改。「之前」改为取锁里读到的。
6. **规格与注释里的不准确**：写的是八种写入方、测的是七种；「第一轮丢五项」实际是四到五项；「组织不存在时处理不变」不够准确（原来报错的仍报错，但错误类型不同）；`set_preference` 的响应现在是写入之后库里的偏好。都已改成与实际一致。

它指出、这次没有动的：

- **已有的三处（斑马帘比例、质保设置、能力配额策略）仍用 `FOR UPDATE`**，它们自己仍会与往本组织插入记录的操作互相阻塞——这是既有行为。其中能力配额策略在持锁期间还会用另一个数据库连接做查询；现在排在这把锁后面的写入方多了，连接池很小时它更容易等不到连接。**建议另开一个小改动把这三处也换成较弱的锁。**
- 在一个已经插入过本组织记录的外层事务里再调用入口会自己卡住自己——这是用 `FOR UPDATE` 时的问题，改锁之后不再成立；现在也没有任何调用方这样用。

## 7. 已知限制

- **写入现在会互相等待。** 每次持锁只有「读一行、算、写一行」，毫秒级。
- **极端并发下写入可能失败并报错**（等不到数据库连接），而不是悄悄丢。收信游标写失败的后果是下一轮多扫一些邮件，既有的去重会挡住重复处理。
- **滚动发布期间**新旧版本并存，旧实例仍是不加锁的整块写回，保护在全部实例换新之后才完整。
- **游标「只进不退」没有做**：两次定时任务同时回写同一个游标时仍是后写的生效，与现在相同。
- **守卫测试认的是写法**：有人用原生 SQL 直接改这一列能绕过去（仓库里现在没有这样的写法）。
- **开户向导的新建 / 接管、日历监听的游标回写、Muse `set_preference` 的整条路径**没有直接的并发用例：前者搭起来要整套开户数据，后两者是内部函数。靠守卫测试核对它们的写法（锁在读之前、在锁里对最新内容修改），靠各自既有的真库测试确认行为没变。开户更新设置与门店折扣有并发用例。
- **已有的三处旧写入方仍用较强的锁**，见 §6 末尾。
- **隔离库测试在 CI 里是跳过的**（CI 没有隔离库），并发的证据只在本地跑得出来。
