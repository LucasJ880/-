# RFQ-AUTO-2 报告：招标分析批准后自动起草第 1 轮询价——系统备好卡，人只批一次

| 项 | 值 |
|---|---|
| change | `rfq-round-auto-draft` |
| TASKFLOW | RFQ-AUTO-2（Phase F 续，接 RFQ-AUTO-1） |
| 来源 | Lucas 2026-11-11：「帮我们发邮件给供应商询价……也要做出自动流，不用我们一个一个点」；四件套回传后答复「可以开始实施了」；实施中就「批准时还有没确认的要求要不要照样起草」选了「照样起草」 |
| 分支 | `claude/rfq-round-auto-draft`（从 main 开，直接指向 main，不叠层） |
| 性质 | 开关 `TENDER_RFQ_AUTO_DRAFT_ENABLED` 默认关；关闭时行为不变（除一处既有缺口的修补，见 §4）。零 schema、零模型调用、不新增定时任务。只起草待批卡，不批准、不发信 |

## 1. 做了什么

**现状**：招标分析批准之后，发第 1 轮询价要人打开「问供应商要价」、看一眼预选的常用供应商、点生成，再批准。前几步每个项目都一样。

**现在**（开关打开时）：人点「批准分析」的那一下，系统接着做完前几步——用这个人自己保存的常用供应商、默认贸易条款，经同一个建轮次函数起草第 1 轮，产出一张待批的发询价审批卡。面板上出现一行结果和「去批准」的链接。人要做的只剩：看卡、批准或驳回。

- **只起草**：卡是待批状态，没有任何邮件发出；首封仍由人批。
- **供应商只取操作者自己的常用供应商**，按他保存的顺序，在用且有邮箱的，最多 8 家。不按品类、标签、评分推荐。
- **只起草第 1 轮，且只起草一次**：项目里已经有轮次（包括已取消的）就不再起草。人驳回了这张卡，之后不会再冒出来。
- **批准分析即视为审核完成**：询价单只带已确认的要求，没确认的不带；结果、卡的摘要、项目页的审批处都写明「带了几条、另有几条没带上」。
- **不起草时说明原因并给出去处**（8 种原因，见 §3）。
- **自动起草的卡只能在网页上批**，不能在 Muse 里批；不带 RFQ-AUTO-1 的跟进授权。
- 每次自动起草留一条审计。

## 3. 判定：8 个原因

任何一条不满足都不起草。按检查顺序：

| 原因码 | 含义 | 面板是否提示 |
|---|---|---|
| `FLAG_OFF` | 开关关闭（响应里根本没有 `rfqAutoDraft`） | — |
| `RUN_NOT_APPROVED` | 这份分析还没批准，或已有更新的一份 | 不提示（批准之前逐条确认时的常态） |
| `ROUND_EXISTS` | 项目已有询价轮次 | 不提示 |
| `NO_CONFIRMED_REQUIREMENTS` | 没有已确认的要求 | 提示，去「需求」 |
| `SENSITIVE_LEAK` | 询价单含不能发给供应商的内容 | 提示，去「需求」 |
| `SENDER_NOT_READY` | 授权邮箱未连接或缺发信权限 | 提示，去连接邮箱 |
| `NO_DEFAULT_SUPPLIERS` | 操作者没有就绪的常用供应商 | 提示，去询价入口 |
| `DRAFT_FAILED` | 建轮次时出错 | 提示，去询价入口 |

中间三条直接取既有询价入口的结论，没有重写判断。

## 4. 实施中改定的三件事

### 4.1 起草条件（Lucas 2026-11-11 定）

四件套原稿要求「每一条要求都确认或驳回」才起草。实施时核对界面发现：要求只能在「批准分析」之前逐条确认或驳回，批准之后界面不再给按钮，也没有批量确认，「批准分析」不会顺手确认剩下的。所以批准时几乎总有没点的要求，按原稿自动起草基本不会触发。

把这个事实和三个选项交给 Lucas，他选了「照样起草」：批准分析即视为审核完成，用已确认的要求起草，没确认的不带，并写明有几条没带上。这与人今天打开抽屉点「生成」得到的询价单相同。规格、design、proposal 已同步。

### 4.2 并发保护换了做法

第一版用事务级咨询锁。独立审查用两个连接的连接池跑出了问题：持锁的事务占着一个连接，建轮次又要用别的连接，池小的时候起草会自己等到超时。改为给建轮次加一个条件「只在恰好是第 1 轮时才建」：轮次号对不上就不建；并发时靠 `(projectId, roundNumber)` 唯一约束让其中一个失败。不持有任何长事务。用两个连接的连接池重跑真库测试：38 项全过。

### 4.3 顺带修的一个既有缺口

建轮次时，原来只有「审批卡没建成」这一种失败会把刚建的轮次标为已取消；轮次建好之后抛错（例如加询价项时数据库超时）会留下一轮没有审批卡的草稿。现在统一处理：出错就把这一轮标为已取消再抛出。**对网页与 Muse 两个既有入口同样生效，不受开关控制。**

## 5. 独立审查发现并已修复的问题

按 RFQ-AUTO-1 留下的教训，开 PR 前请了一个不带结论的独立审查。它确认了下面几处，都已修复并补了测试：

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 自动起草的卡能在 Muse 里只看标题就批 | 没有人看过收件人与正文，回一句「批准」邮件就发出去了 | 这类卡在 Muse 里不能批，提示去网页（与 RFQ-AUTO-1 对带授权的卡的处理一致） |
| 2 | 并发保护的事务占住数据库连接 | 连接池小的时候起草自己超时，审核动作多等 10 秒并得到「没有成功」 | 见 §4.2 |
| 3 | 建轮次途中出错留下没有审批卡的草稿轮次 | 之后自动起草永远不再触发，抽屉里建出来的是「第 2 轮」 | 见 §4.3 |
| 4 | 面板上的提示会过期 | 旧的一行留着，说着已经不成立的话 | 每次带回结果都刷新：要提示的显示，不必提示的清掉 |
| 5 | 开关关闭时询价入口的响应多了一个空字段 | 与「关闭时零变化」不符 | 关闭时没有这个字段 |
| 6 | 测试的几处不足 | 「跨组织」用例其实是同组织；驳回与批量确认两个接口没有真的调用 | 补了「组织对不上」「不是本组织成员的人调接口」「驳回与批量确认接口」的用例 |

审查确认没有问题的部分：操作者身份只来自登录会话、每个查询都按组织与项目限定、不会批准或发送、带不上跟进授权、收件人只来自操作者的常用供应商、任何异常都不影响审核动作、开关关闭时四个审核接口与两个既有入口的行为不变、响应与审计里没有邮箱与价格。

审查提到但没有改的：

- 自动起草与人工起草并发时仍可能各建一轮（自动的那次会被「只能是第 1 轮」拦住；人工的那次不带这个条件）。人工对人工的同类竞争在本变更之前就存在，不在本次范围。
- 一份排队中 / 运行中 / 失败的新分析不算「取代」已批准的那份（与询价单取要求的规则一致）。
- 重复确认已确认的要求、空的批量确认也会触发一次判定（结果是「已有轮次」或「分析未批准」，不提示）。

## 7. 设计取舍

| 决定 | 理由 |
|---|---|
| 在人的审核动作里同步判定，不用定时任务 | 操作者身份明确（卡记在他名下、用他的常用供应商）；不需要任何调度；卡不会在没人做任何动作时冒出来 |
| 供应商只用操作者的常用供应商 | 这正是抽屉今天预选的那几家，等于替人点了「生成」。供应商的品类、标签字段有一部分是模型写的，让它们决定邮件发给谁不合适 |
| 只起草第 1 轮、只起草一次 | 轮次本身就是「起草过」的记录；人驳回即表态，之后由人自己发 |
| 调既有的建轮次函数 | 有效期、幂等键、载荷、轮次锁、待批提醒全部沿用，不出现第二套建轮次逻辑 |
| 自动起草的卡只能在网页批 | 起草时没有人看过收件人与正文，Muse 里只有标题 |
| 不带跟进授权 | RFQ-AUTO-1 的规格写明授权只在「网页发起且明确勾选」时写入；两者怎么接另提 |

## 8. 已知限制

1. **常用供应商未必适合当前项目**（例如常做窗帘的厂被拿去问清洁用品）。系统不判断适不适合，靠人在批准时看收件人。批错的代价是多发了一封询价。这是本方案最主要的取舍。
2. **操作者没存过常用供应商就永远不起草**，只给出去处。首次使用需要人先走一遍抽屉并选定过报价。
3. **批准时没点完的要求不进询价单**。三处都写明了有几条没带上，由批准人判断。
4. **自动起草的轮次，催单与追问仍要逐封批**（不带跟进授权）。
5. **起草同步发生在审核请求里**，批准分析的响应会多出建轮次的时间（本地约 0.2 秒）。
6. 界面没有组件级自动化测试（仓库没有这类设施），靠真实应用截图、源码断言与服务层测试。
