| 项 | 值 |
|---|---|
| change | `requirement-review-batch-confirm` |
| TASKFLOW | RFQ-AUTO-4（Phase F 续，接 RFQ-AUTO-2） |
| 来源 | Lucas 2026-11-11：「其他按照你推荐的做」；四件套回传后答复「可以，开始实施吧」 |
| 分支 | `claude/requirement-batch-confirm`（从 main 开，直接指向 main，不叠层） |

## 1. 做了什么

**现状**：招标要求只能一条一条点「确认」；询价单只带已确认的要求；批准分析之后界面不再允许确认。一个标几十条要求就要点几十次，没点完就批准的那些会被落在询价单外面。批量确认的接口早就有，界面没有用上。

**现在**：

- 要求列表上，每条待确认的要求前面有一个勾选框；列表上方有「全选待确认的」「取消全选」「确认选中的 N 条」。只在分析等待审核时出现，默认一条都不选。
- 列表上方显示计数：已确认 / 待确认 / 已驳回各几条。
- 「批准分析」按钮旁，还有待确认的要求时显示：「还有 N 条要求没有确认：批准后不能再确认，没确认的不会进询价单。」不拦批准、不多一次点击。
- 确认之后显示接口返回的实际确认数；少于选中数时如实说明。
- 批量确认每次成功留一条审计。
- **分析已不是等待审核时不能批量确认**：面板开着的时候别人把分析批准了，这边再点确认会被接口拒绝（一条都不确认），并看到原因。

**没有的**：没有「一键全部确认」（必须先勾选），没有批量驳回，没有功能开关。逐条的「确认」「驳回」照常可用。

## 3. 为什么要在前端分批

批量确认接口一次最多处理 200 条，多出的部分被**静默丢弃**（不报错）。如果界面一次把 450 条发过去，接口返回「确认了 200 条」，界面却以为 450 条都确认了。所以面板按 200 条一批依次提交，把每批返回的实际确认数加起来显示；某一批失败就停，说明此前已经确认了几条。

真库测试专门验证了这一点：一次提交 205 条，接口只确认前 200 条、剩 5 条仍待确认；再提交剩下的一批才全部确认。

## 5. 独立审查

实施完成后请了一个不带结论的独立审查。它确认了下面几处，都已修复并补了测试：

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 面板开着时别人（或另一个标签页）批准了分析，这边仍能批量确认成功。接口本来就不看分析的状态，唯一的防线是面板手里那份可能过时的状态 | 与界面上「批准后不能再确认」的说法矛盾；如果批准时已经自动起草了询价，后确认的要求不会进那张卡，用户却不知情 | 批量确认多一个可选参数「只在等待审核时确认」，条件写进同一条更新语句（没有「先查后改」的间隙）；面板每一批都带上；分析已不是等待审核时 409、一条都不确认、不留审计。不带参数的调用保持原样 |
| 2 | 分批提交时「自动起草」的提示会被后面的批次冲掉 | 起草了一张卡，用户看不到提示 | 保留需要提示的那一个 |
| 3 | 结果消息不会消失 | 重新分析之后，新分析旁边还挂着上一份的「已确认 3 条」 | 消息记着它属于哪份分析，只在那份分析仍在审核时显示 |
| 4 | 成功的状态码但响应看不懂时被当成「确认了 0 条」，文案还把原因归给「别人处理了」 | 误导 | 按失败处理；「少于选中数」的文案不再断定原因 |
| 5 | 审计里的要求号没有长度上限 | 有写权限的人可以往审计里塞很长的字符串 | 只记合规长度的 |
| 6 | 分批函数允许传入超过 200 的批大小（没有调用方这么用） | 潜在的静默丢弃 | 封顶为接口上限 |

为了让第 2、4 条能被真正测到，把「分批提交、累加、失败即停」从面板里抽成了一个纯函数，用假的接口做行为测试——审查指出原来面板的断言全是对源码文本的匹配，测不出这些问题。

审查确认没有问题的部分：新增的状态都在提前返回之前声明，列表为空或不在审核时渲染安全；选中的要求号在使用时会按当前列表再筛一遍；重复提交被挡住；「全选待确认的」选的就是屏幕上渲染出来的那些（列表没有筛选和分页）；批准按钮的行为与可用条件没有变；接口先鉴权再读请求体，组织、项目、分析三层限定都对；失败路径不写审计；响应结构没有变。

审查提到但没有改的：

- **真库测试在 CI 里是跳过的**（CI 没有隔离库），只在本地跑。这是仓库里所有隔离库测试的现状。
- **面板本身没有行为测试**（仓库没有组件测试的设施）；能抽出来的逻辑已经抽成纯函数测了，剩下的靠真实应用截图。
- **单条确认与驳回同样不看分析的状态，也没有审计**——既有行为，本次没有动。

## 6. 设计取舍

| 决定 | 理由 |
|---|---|
| 勾选式，不做「一键全部确认」 | 确认决定了什么会发给供应商。一个按钮就把模型抽出来的全部要求变成「人确认过」，等于取消了审核。全选之后人仍能取消个别几条 |
| 用既有接口，前端分批 | 不改接口的上限与语义；接口对多出的部分是静默丢弃，必须由调用方分批（见 §3） |
| 批准前的提示不拦批准 | 有些要求本来就不打算发给供应商，不确认也不驳回是正常的 |
| 审计写在路由里，用吞错的写法 | 路由才知道操作者是谁；确认已经完成，审计失败不该让请求报错 |
| 「只在等待审核时确认」做成可选参数，写进更新语句的条件 | 不改变其它调用方的行为；写在同一条语句里才没有间隙 |
| 提交逻辑抽成纯函数 | 面板没有组件测试的设施；抽出来才能用假的接口做行为测试 |
| 不加功能开关 | 既有接口上的界面操作，不对外发送；回退方式是不点它 |

## 7. 已知限制

1. **更容易不看就确认**。全选加确认只要两次点击。要求的原文与译文就在勾选框旁边；发出去之前还有询价审批卡，卡上是完整的邮件正文。这是本方案最主要的取舍。
2. **分批提交中途失败不回滚**：前面几批已经确认。界面如实说明已确认几条，刷新后列表反映真实状态。
3. **审计记的是「请求确认的要求」与「实际确认的条数」**，不是逐条的实际结果（接口的更新不返回具体改了哪几条）。两者不一致时（有的已被别人处理），从审计里看不出是哪几条没被确认。
4. **单条确认与驳回仍然没有审计，也不看分析的状态**——既有行为，本次没有动。
4a. **「只在等待审核时确认」只保护面板发起的批量确认**。直接调接口而不带这个字段的调用方，仍然可以在批准之后确认（RFQ-AUTO-2 的设计保留了这条路）。
5. 界面没有组件级自动化测试（仓库没有这类设施），靠真实应用截图、源码断言与纯函数测试。
