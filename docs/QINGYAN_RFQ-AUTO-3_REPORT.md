# RFQ-AUTO-3 报告：自动起草的轮次也能带跟进授权——由本人事先在网页上明确开启

| 项 | 值 |
|---|---|
| change | `rfq-auto-draft-followup-optin` |
| TASKFLOW | RFQ-AUTO-3（Phase F 续，接 RFQ-AUTO-1、RFQ-AUTO-2） |
| 来源 | Lucas 2026-11-11：「开始 RFQ-AUTO-3，其他按照你推荐的做」；四件套回传后答复「可以，开始实施」 |
| 分支 | `claude/rfq-auto-draft-followup`（从 main 开，直接指向 main，不叠层） |
| 性质 | 没有新的功能开关：RFQ-AUTO-1 与 RFQ-AUTO-2 两个开关都打开时才可见，个人开关默认关。零 schema、零模型调用、不新增定时任务。不改覆盖判定、执行方式、停止方式，不改硬纪律文字 |

## 1. 做了什么

**现状**：RFQ-AUTO-2 自动起草的轮次不带 RFQ-AUTO-1 的跟进授权，所以这些轮次的催单与追问仍是每家每次一张卡。两步自动流中间断了一截。

**现在**：加一个个人开关「自动起草的轮次带跟进授权」，默认关。开启之后，你批准招标分析时系统起草的第 1 轮询价会带上催单和追问的授权。一个标从批准分析到供应商回完价，人只点两次：批准分析、批准发询价的那张卡。

- **按人、按组织**：自动起草时只看触发起草的那个人自己的开关，不用同组织别人的。
- **只能本人在网页上开**：接口的请求体里没有用户号，只能改登录的这个人自己的；不能在 Muse 里设。开启处展示授权范围与三段邮件模板，开启前二次确认（确认期间范围收不起来）。
- **随时能关**，包括功能开关关闭期间。开启要求两个功能开关都打开。
- **开启时绑定当时的邮件模板**：模板之后改了，开关自动失效，看过新模板后重新开启。
- **开关的状态不放在组织设置里**，是本人最近一条开关记录（只追加）——不会被别处对组织设置的写入悄悄改掉。
- **开关在项目页「标书与报价」询价区块的顶部**，不在抽屉里——开了自动起草之后第 1 轮不经过抽屉，而且卡一起草入口就被锁住。
- **授权仍然要人批才生效**：卡的标题同时标明「自动起草」与「含自动跟进授权」，只能在网页批；原地审批处同时显示自动起草的说明、授权范围与三段模板。批准之后的行为与 RFQ-AUTO-1 完全相同。
- **关闭只影响之后起草的轮次**；已批准的轮次要停用，用轮次上的「停止自动跟进」。
- 每次开或关留一条记录；自动起草的审计里记下这张卡带不带授权。
- **带授权的待批卡，批准处一定显示授权**：不论跟进授权的功能开关此刻是否打开（关闭时加一句说明）。这一条顺带补上了 RFQ-AUTO-1 留下的一个缺口。

## 3. 三个开关的组合

| 跟进授权（RFQ-AUTO-1） | 自动起草（RFQ-AUTO-2） | 个人开关 | 结果 |
|---|---|---|---|
| 关 | 关 | 任意 | 没有任何授权，没有自动起草；个人开关不显示；开启 404，关闭照样可以 |
| 关 | 开 | 任意 | 自动起草的卡不带授权；个人开关只对开着的人显示（标明现在不生效，可关闭）；开启 404 |
| 开 | 关 | 任意 | 没有自动起草；个人开关同上；网页抽屉里的勾选照常 |
| 开 | 开 | 关（默认） | 自动起草的卡不带授权（与 RFQ-AUTO-2 上线时相同） |
| 开 | 开 | 开 | 自动起草的卡带授权；人批准这张卡后，催单与追问按授权自动发 |

这些组合都有真库测试。个人开关开着、之后功能开关被关掉的情形：开关不生效，但本人仍看得到、关得掉；如果他没关，功能开关重新打开后恢复生效；他关了就不会自己恢复。另外，开启之后邮件模板改过的话，开关是「已失效」，等同于关。

## 5. 独立审查

实施完成后请了一个不带结论的独立审查，专找「超出人知情同意范围的授权或发送」与隔离、权限上的漏洞。它确认了下面几处，都已修复并补了测试：

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 开关存在组织设置的大 JSON 里，而那一块被好几处「整块读、整块写」且不加锁（收信定时任务、Muse 的偏好与绑定、管理员改设置等） | 用户刚关掉，别处把旧数据写回，开关悄悄变回开；接口已告诉他关了、记录也是关，下一次自动起草却又带上授权 | 不放进那块 JSON：状态 = 本人最近一条开关记录，只追加（与「停止自动跟进」同一做法） |
| 2 | 功能开关关闭时，设置接口连「关闭」也返回 404，界面也不显示 | 一个开着的同意在功能关闭期间撤不回，功能一打开又自己生效 | 关闭任何时候都可以；功能关闭期间对开着的人仍显示（注明不生效） |
| 3 | 带授权的卡起草之后，跟进授权的功能开关被关掉，批准处就不显示授权范围 | 批准人看不到范围就能批；授权还在卡里，功能再打开就恢复生效。这是 RFQ-AUTO-1 留下的缺口，自动起草让它更要紧（没有人在这张卡上看过范围） | 待批卡只要载荷里有授权，批准处就显示范围与模板；功能关闭时加一句说明 |
| 4 | 开关只存「开 / 关」，不绑定开启时看到的内容 | 开启时看的是那一版模板，以后模板改了，授权跟着新模板走 | 开启时记下模板指纹；指纹变了开关失效，看过新模板后重新开启 |
| 5 | 界面写「仍然要你批准」；二次确认期间范围说明可以收起 | 批准人常常是另一个有审批权的人；确认的那句「上面这份授权」可能指向一段看不见的内容 | 文字改为「有审批权的人」并写明催单以批准人身份发出；确认期间范围收不起来 |
| 6 | 几处代码注释仍写着「自动起草不带授权」 | 误导后来的人 | 已改 |

审查确认没有问题的部分：谁能设置（组织设置接口的校验是严格的，注入不了；Muse 的 `set_preference` 只碰自己的四个字段；没有通用的设置接口）；读的是触发动作的登录用户自己的开关；所有批准入口对这类卡都只能去网页；授权内容与网页勾选时是同一个构造函数、同一套入参；`prepareRfqRound` 的三个调用方里 Muse 不传 `autoFollowUp`；设置接口先鉴权再读请求体。

审查提到但没有改的：

- 测试里「人批准并发出」是直接改库模拟的，没有走真实的批准与发送路径（发询价的执行器没有可注入的假发送器）。批准路径本身由 RFQ-AUTO-1 的测试覆盖，但「自动起草 + 带授权」的卡没有单独走过一遍真实批准。
- 一部分接线断言是对源码文本的匹配，不随运行行为变化；它们防的是「有人改掉这一行」，不能代替真库测试。

## 6. 设计取舍

| 决定 | 理由 |
|---|---|
| 按人，不按组织 | 自动起草的卡记在操作者名下、用他的常用供应商；带不带授权由同一个人决定。管理员替所有人开的话，操作者没选过，卡上却带着授权 |
| 状态 = 本人最近一条开关记录，不放进组织设置，也不放进 Muse 的个人偏好 | 组织设置那一块会被别处整块回写（见 §5 第 1 条）；Muse 的偏好只认四个字段，而且能在 Muse 里改 |
| 开启时绑定模板指纹 | 与 RFQ-AUTO-1 用模板指纹保护已批准的轮次是同一个原则：人同意的是他看到的那一版 |
| 关闭不受功能开关限制 | 同意必须随时撤得回 |
| 开关放在询价区块顶部 | 自动起草的路径上看不到抽屉；这个位置不受入口锁影响，而且范围与模板就在开关旁边 |
| 建轮次函数的条件多认一个来源，不在自动起草的服务里自己拼授权 | 写授权的地方仍然只有一处 |
| 结果与审计里「带不带授权」以卡上实际写了什么为准 | 开关开着但功能开关关了的时候，卡上并没有授权，不能照着开关的值说 |
| 关闭不回头改已起草或已批准的卡 | 载荷受哈希保护；已批准的轮次有专门的「停止自动跟进」 |

## 7. 已知限制

1. **开一次管以后所有项目**，人可能忘了自己开过。每张卡的标题、摘要、原地审批处都写明带授权；询价区块顶部一直显示当前状态；随时能关。
2. **操作者与批准人不是同一个人时**：操作者的开关让卡带上授权，批准人承担后果。批准人在网页上看得到完整范围与模板才能批，可以驳回。
3. **不给已经起草好的卡补授权**。想带授权，驳回后在「问供应商要价」里勾选重发。
4. **开关处展示的范围以当前项目为例**（间隔与回复截止每个项目不同），界面上写明了这一点；实际值以每张卡上列出的为准。
5. **状态靠最近一条记录**：同一毫秒内的两条记录按记录号排先后；审计表如果被清理，开关会回到默认的关（偏安全的方向）。
5a. **组织设置「整块读、整块写」的既有写法没有改**。本次绕开了它（开关不放在里面），但常用供应商、默认贸易条款、发件设置之间仍可能互相覆盖——这是本变更之前就有的问题，建议另开一个 change 处理。
6. 界面没有组件级自动化测试（仓库没有这类设施），靠真实应用截图、源码断言与服务层测试。

## 8. 没做的

- 没有合并、没有部署、没有改生产开关。
- 没有向任何真实地址发过邮件：测试里的催单全部进内存里的假发送器；截图没有批准过任何卡。
- 没有 schema 变更、没有新增模型调用、没有新增定时任务，没有改 `openspec/config.yaml`。
