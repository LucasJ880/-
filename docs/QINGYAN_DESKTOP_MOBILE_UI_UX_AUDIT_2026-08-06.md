# 青砚桌面端 UI/UX 与移动端适配审计

**日期：** 2026-08-06  
**性质：** 只读审计与实施方案；本次没有改动业务代码、数据库、权限、API 或 AI 审批机制。  
**审计基线：** 当前工作树 `qingyan-digital-employee-phase4`；生产已登录管理员环境的桌面实测（1280px），加上仓库内 Chromium 移动基线（320–768px）和当前响应式源码复核。

## 1. 结论摘要

青砚已经具备一个可用的统一外壳：Next.js App Router 下的 `AppShell`、左侧权限过滤导航、顶部搜索/通知/用户入口、移动底栏和分级导航抽屉都已存在。它不需要推倒重来。

真正的问题是功能增长后，**导航层级、实体上下文和页面组成规则还没有完全收敛**：同一项工作常在项目卡片、项目详情、AI 工作台、能力中台、通知和独立管理页之间切换；很多页面绕开了基础 UI 组件直接手写按钮、状态、弹层和标题区。项目详情尤其把“决策、执行、协作、成员管理、系统配置”铺在一个长页面中，首屏无法稳定回答“现在什么阶段、有什么风险、下一步做什么”。

建议按题述 Phase 0–5 渐进更新。优先用项目详情作为样板页，但**先完成 Phase 1 的设计系统收敛，不先重写全站壳**。现有路由、权限、审批和接口均可保留。

## 2. 当前技术与布局基础

| 项目 | 当前事实 | 审计判断 |
|---|---|---|
| 前端 | Next.js 16.2.0、React 19.2、TypeScript | 适合渐进式 App Router 改造，无需换框架。 |
| CSS / 组件 | Tailwind CSS 4、CVA、Radix Dialog/Select/Tabs、Lucide；有自建 `components/ui` | 已接近轻量设计系统，不能再引入重量级 UI 框架。 |
| 全局壳 | `src/app/(main)/layout.tsx` → `AppShell` | 桌面侧栏、Header、主滚动区、移动底栏均在同一位置，具备改造成统一 Shell 的基础。 |
| 桌面导航 | `Sidebar` + `lib/navigation/registry.ts`，按角色、组织、模块和工作区过滤 | 导航来源已统一；问题是管理员可见层级过多、分组过碎。 |
| 顶部导航 | `Header`：全局搜索、通知、语言、企业/用户入口 | 基础足够；尚非“当前实体上下文栏”，没有展示正在处理的项目/客户/报价。 |
| 右侧面板 | 有局部 Drawer、项目快览抽屉、项目内 AI 聊天；没有全局可插槽的 Context Panel | 应建立可按实体页开启、可收起的右侧面板，不应全局强占宽度。 |
| 响应式 | Tailwind 默认 `md=768px`；`useIsMobile` 也以 768 为断点 | 断点统一，但 768–1024 的平板密度和右栏降级策略尚未定义。 |
| 移动导航 | `MobileTabBar` + `MobileNavDrawer`，销售角色另有快捷创建底板 | 已有正确骨架；移动页内容并非均已具备对应信息架构。 |
| 移动专用能力 | 报价单安全区底栏、客户卡片化、视觉器支持相机 `capture="environment"`、AI 助手语音输入 | 可作为 MVP 基础；项目现场拍照/语音记录尚未成为统一工作流。 |

### 断点实测与证据边界

- 本次在生产登录态实测了 1280px 桌面：左侧完整导航、顶部全局入口和主区均可用，但管理员导航约 40 个入口，销售分析与项目详情都呈现明显纵向信息堆叠。
- 仓库已有 2026-07-23 Chromium 基线，覆盖 320/360/375/390/430/768px、14 条代表路由、84 页次；移动二期还记录了弹层、底栏与 Safari 风险。它不是本次 2026-08-06 的全量重新截图，应在 Phase 0 重新跑为当前基线。
- 当前内置浏览器测试环境固定为 1280px，不能在本次只读会话中改变 viewport。因此 1440/1024/768/390 的“当前版本”结论采用源码与既有自动化证据；精确视觉回归将列入 Phase 0 必做项，而不是伪称已重新实测。

## 3. 页面、导航与上下文归属

| 领域 | 当前入口 / 用途 | 顶层保留建议 | 目标上下文与移动分类 |
|---|---|---|---|
| 首页 / 我的工作 | `/`、`/tasks`、`/notifications`、`/service-inbox` | 保留为“工作台”，不要与经营数据混在一起 | A：响应式；手机做“今日”。 |
| 项目列表 | `/projects` | 保留顶层 | A：列表卡片化；按项目进入详情。 |
| 项目详情 | `/projects/[id]` | 保留实体页，不另建重复工作台 | B：独立移动布局，桌面作为样板页。 |
| 招投标与项目智能 | `/bids`、`/projects/intelligence/*` | 招投标入口保留；情报成为项目的上下文能力，列表/监控保留独立入口 | C：手机查看、提醒、审批；深度情报编辑不进 V1。 |
| 销售 / 客户 / 商机 | `/sales`、`/sales/customers/[id]` | `客户与商机` 已共用工作区，应继续合并而非新增两个一级入口 | B：客户详情单独移动布局；列表/快捷联系优先。 |
| 报价 | `/sales/quote-sheet`、`/sales/quotes`、项目内报价 | 报价记录保留；报价单是客户/商机和项目的关联操作 | C/D：手机查看、发送前确认可做；复杂创建编辑首版不提供。 |
| 供应商 / 询价 | `/suppliers`、项目内 `ProjectInquirySection` | 供应商库保留顶层；询价放项目上下文，不另设多个入口 | C：查看、联系、审批；复杂询价编辑后置。 |
| 技术标、文件、讨论 | 项目内文件管理、AI 投标包、讨论；另有开发管理子路由 | 面向业务用户应收敛到项目标签；开发工具仍保留管理员页 | B：文件/讨论可用；技术标编辑后置。 |
| 数字员工 | `/assistant` 与项目内 `ProjectAiChat` | 保留独立全屏“跨工作总览”，同时在实体页作为上下文面板 | B：AI 全屏页。 |
| Pending Action | `/capabilities/approvals`，以及 AI 内联确认 | 审批中心保留；业务页须出现与当前实体相关的待确认项 | C：展示、确认/拒绝、结果回执。 |
| 设置 / 企业管理 | `/settings/*`、`/organizations`、`/knowledge` | 保留低频顶层，放入侧栏底部“管理” | D：首版手机不提供完整管理。 |
| 管理员 / 诊断 | `/capabilities/runs`、`/agent-trace`、`/admin/*`、项目 Prompt/Agent/Tools 页面 | 独立管理员/开发调试区，不能混入普通业务任务 | D：不进入手机业务版。 |

### 重复与认知冲突

1. 侧栏已经有“数字员工”和“AI 工作中心”两类入口；前者是业务助手，后者包含审批与运行诊断。名称和目标用户须分层，否则普通用户无法判断去哪处理待确认动作。
2. 项目工作在 `/projects`、`/bids`、项目详情、项目智能和“调查室”之间切换。应把“项目实体页”作为主容器，独立页面只承担跨项目列表、监控和管理员维护。
3. 销售的客户与商机已经合并在 `/sales`，这是正确方向；报价、邮箱绑定、个人业绩和销售分析仍把同一销售循环拆成太多平级项。
4. 当前管理员侧栏可见项目开发者工具、能力目录和运行诊断，符合管理员需要；但能力中台的“Agent / Skill / Tool / Workspace”等术语仍可能出现在一般企业成员可见的概览中，需按角色改成业务语言或仅给管理员。

## 4. 设计系统审计

### 已有可复用基础

- `Button`（CVA 变体/尺寸）、`StatusBadge`、`Badge`、`Input`、`Select`、`Dialog`、`Drawer`、`EmptyState`、`PageHeader`。
- 全局 Token 在 `src/app/globals.css`：色彩、圆角、阴影、层级与安全区已经集中。
- 统一导航注册表、移动滚动锁、统一 z-index token 已存在，说明系统可通过收敛而非重造解决问题。

### 主要不一致

| 类别 | 发现 | 应对原则 |
|---|---|---|
| 页面标题 | `PageHeader` 已广泛使用，但项目详情、运营/增长和许多业务页仍手写 `h1 + actions` | 所有标准页迁 `PageHeader`；全屏聊天、打印/展示可例外。 |
| 按钮 | 基础 `Button` 规定 32/36/40px，但业务页大量直接写 `rounded-lg px-* py-*` | 禁止新页面继续手写主/次/危险按钮；仅将高频页分批迁移。 |
| 状态 | 通用 `StatusBadge` 与页面内自定义绿色/橙色/红色标签并存 | 定义业务状态词典与 6 个 AI 可见状态；色彩只表达语义，不表达页面来源。 |
| 卡片 / 看板 / 表格 | 同一实体在卡片、信息块、无横滚表格中不同呈现；部分宽表有安全横滚，项目成员等仍无包装 | 明确“实体列表卡片 / 数据表 / 指标卡”三种规则，移动按类型决定卡片或横滚。 |
| 抽屉 / 弹窗 | Radix Dialog、UI Drawer 与多处手写 `fixed inset-0` 并存 | 新功能只能用统一 Dialog/Drawer；旧实现不在本轮删除，后续逐簇替换。 |
| 页面状态 | `EmptyState` 存在，加载多以局部 spinner 实现，错误状态格式不统一 | 建立 `PageState`（loading / empty / error / retry）组合规范。 |
| 间距与文本 | Token 完整，实际存在 `text-[10px]`、自由圆角和卡片 padding 变体 | 正文最低 12px；标签可 10–11px；页面/卡片间距按 token。 |
| 操作入口 | 项目页同时出现标签、卡片按钮、底部成员管理、生成菜单、开发链接 | 每页只保留一个主行动、最多两个次行动；其他进入溢出菜单或上下文面板。 |

## 5. 项目详情页重点审计

### 当前表现

当前 `/projects/[id]` 有四个标签：**概览、文件、报价、工作台**。实际“概览”内又顺序堆叠引导、AI 摘要、历史经验、规则、投标调查、供应商、进度、讨论、活动、成员、加入简报和通知规则；生产实测中，项目头还出现管理员专属 Prompt、会话、Agent、工具和质量链接。

这使页面具备能力，但无法稳定回答下列五个问题：

| 用户问题 | 当前情况 | 样板页目标 |
|---|---|---|
| 目前处于什么阶段？ | 头部状态、投标调查和进度卡分散 | 顶部固定阶段条 + 当前阶段结论。 |
| 哪些事项尚未完成？ | 任务数、引导、检查清单和 Pending Action 分散 | “待处理”清单按截止/责任人/阻塞排序。 |
| 最近发生什么？ | 讨论与活动分别在长页靠后 | 概览只放最近 5 条，完整活动独立标签。 |
| 下一步该做什么？ | AI 建议、入门引导、生成菜单并列 | 唯一“推荐下一步”卡，说明原因和影响。 |
| 有哪些风险、哪些需要确认？ | 风险卡/调查/审批散落 | 顶部风险摘要 + 右栏待确认，不将 AI 建议当最终决定。 |

### 推荐的项目实体结构

```text
项目头：名称 · 当前阶段 · 截标/关键日期 · 负责人 · 健康度
  └─ 主行动：推进当前阶段 / 处理待确认

标签：概览 | 要求 | 文件 | 询价 | 报价 | 技术标 | 讨论 | 活动记录

概览首屏：阶段与健康度 | 待处理事项 | 风险 | 最近变化 | 推荐下一步
右侧（桌面 >=1280）：青砚上下文面板 / 当前实体待确认动作
```

“成员、通知规则、项目加入简报、Prompt/Agent/Tool”等应分别进入“更多/管理”或管理员开发页；路由可以原样保留，只需调整默认露出位置。项目详情是最适合先落地右侧面板的页面：现有 `ProjectAiChat` 已传递 `projectId`，后端也会构建项目上下文，因此不需要改 AI Scope 或数据模型。

## 6. AI 与 Pending Action 审计

### 当前安全与上下文

- 项目内聊天会以 `projectId` 过滤/创建线程；消息路由会构建项目上下文块，当前实体绑定已经存在。
- 独立助手的线程可以绑定项目，但客户和报价在统一助手中的显式一等上下文并未形成同样清晰的 UI 契约；销售上下文目前是 best-effort。建议后续仅增加前端 `entityContext` 展示和路由参数映射，不改工具 Scope。
- Pending Action 有 `pending / approved / executed / rejected / failed / expired` 的持久状态、审批中心、内联确认和运行回填；审计中**没有发现**应当修改或绕过人工审批的理由。
- 生产实测的数字员工页面已以业务语言展示“待我确认”和“关键动作保持人工确认”，没有直接暴露 Runtime/Executor/Scope 等运行时字段；能力中台和项目开发者链接应继续只在管理员/开发调试层展示。

### 建议的用户可见状态映射

| 统一用户文案 | 现有实现可映射状态 | UI 规则 |
|---|---|---|
| AI 建议 | 无副作用的建议/风险/下一步 | 可采纳、可忽略；不等同审批。 |
| 等待确认 | `pending`、`awaiting_approval` | 显示影响对象、摘要、确认/拒绝。 |
| 正在执行 | `approved`、`executing` | 显示进度，禁止重复触发。 |
| 执行成功 | `executed`、完成 run | 显示回执及“查看变更”。 |
| 执行失败 | `failed`、`expired` | 显示可理解原因与重试/转人工入口。 |
| 需要补充信息 | 前置资料/字段不足 | 直接定位缺失字段或上传入口。 |

状态统一只改变展示层和入口位置；执行器、权限校验、审批前置和邮件发送机制都不改变。

## 7. 移动端审计与定位

### 当前判断

| 宽度 | 当前判断 | 主要风险 |
|---|---|---|
| 1440px | 左栏 + 内容区空间充足；右栏可常驻但应可折叠 | 不是布局空间问题，而是导航和长页信息密度。 |
| 1024px | 可保留桌面左栏；右栏必须降为按需抽屉 | 三栏并置会挤压表格/报价单。 |
| 768px | 当前以 `md` 切换到移动壳 | 这正是桌面→平板的硬切换点，需 Phase 0 重新回归。 |
| 390px | 底栏、导航抽屉、报价安全区已有基础；历史 Chromium 基线可用 | 宽表、复杂表单、手写弹层和软键盘仍是高风险；Safari/iPhone 真机未完成验证。 |

### 页面的 V1 手机分类

| 页面 / 场景 | 分类 | 第一版处理 |
|---|---|---|
| 今日、任务、通知、收件箱 | A | 响应式单栏；强调待办和确认。 |
| 项目列表 | B | 项目卡片、阶段/风险/截止日、筛选底板。 |
| 项目详情 | B | 独立单栏摘要；标签改为分段导航或二级页。 |
| 客户与商机 | B | 客户卡、联系、导航、跟进、快速新建记录。 |
| 日程 | B | 日/周议程优先，不复制桌面日历网格。 |
| 讨论、文件上传、拍照 | B | 相机/相册入口、上传队列、消息/讨论。 |
| 青砚 AI | B | 全屏对话 + 当前项目/客户上下文胶囊；现有语音输入可复用。 |
| Pending Action | C | 专注展示、确认/拒绝、结果回执，不做运行诊断。 |
| 报价、询价、供应商 | C | 查询、联系、发送前确认；复杂价格/明细编辑不进首版。 |
| 技术标深度编辑、项目智能研究 | C | 只读摘要、风险、附件、待确认。 |
| 电子报价单新建/复杂编辑 | D | 首版不提供；避免把高金额多行表单硬缩至手机。 |
| 企业设置、权限、能力中台、管理员运行诊断 | D | 不进入首版业务移动端。 |

### 移动目标架构

```text
底部导航：今日 | 项目 | 客户 | 日程 | 青砚 AI
全局角标：待确认数量（通知中心和 AI 内同步）

项目详情：摘要 → 待办/风险 → 文件/拍照 → 讨论 → AI → 待确认
客户详情：联系 → 商机/报价摘要 → 跟进记录 → AI
```

相机能力已有 Visualizer 的 `capture="environment"` 示例，语音输入已有 `useVoiceInput`/转写接口；Phase 5 应把它们抽成项目现场记录组件，并明确离线/失败上传回执。不能假设所有普通文件选择器都会在手机上自然变成良好的现场拍照流程。

## 8. 推荐桌面目标 Layout

```text
┌────────────业务导航────────────┬────────────顶部上下文栏──────────────────────────┐
│ 工作台                         │ 面包屑 / 当前项目、客户或报价 / 搜索 / 通知 / 用户 │
│ 业务（销售、项目、供应商）     ├──────────────────主要业务工作区───────────────────┤
│ 增长                           │ 页面标题 + 单一主行动                             │
│ 企业管理                       │ 内容：列表、详情、表单或看板                       │
│ ───── 管理员工具（按角色） ─── │                                                     │
└───────────────────────────────┴───────────────────────────────┬───────────────┤
                                                                  │ 青砚上下文面板 │
                                                                  │ 摘要/风险/下一步│
                                                                  │ 待确认/最近变化 │
                                                                  └───────────────┘
```

- 右栏只在有实体上下文的桌面页启用，默认 320–360px，可关闭；1024px 以下改成右抽屉，手机改全屏 AI。
- 左栏保留现有权限过滤，但将日常可见一级组收敛为：**工作台、业务、项目、增长、管理**；能力运行/审计进入管理员工具或个人菜单，不与日常业务并列。
- 顶栏新增的是“可读的实体上下文”，不是改变路由：例如“客户 A · 报价 Q-102 · 草稿 · 有 2 项待确认”。

## 11. 风险与兼容性

1. **不能一次性改全站 Layout。** 当前主滚动、移动底栏、聊天全屏和多角色导航均在 `AppShell` 内；Shell 必须先做插槽兼容层。
2. **不能把 AI 建议变成业务真相。** 阶段、报价、客户状态仍由现有业务数据和审批流决定。
3. **不能把管理员诊断简单隐藏后删除。** Runtime、Tool、Prompt、Agent 等信息需要继续保留在管理员/开发调试入口，业务端只改变呈现和入口。
4. **移动端不是缩放桌面。** 报价、复杂询价、宽表和技术标编辑应分级供给，尤其避免移动端误提交高金额内容。
5. **现有手写弹层有一致性与 Safari 风险。** 二期已有记录：少量多层 Overlay、z-index、键盘和滚动锁需继续回归；不构成先做 Phase 1 的阻塞。
6. **现有移动自动化不是最新视觉验收。** 必须在 Phase 0 重新跑 1440/1024/768/390，至少补一次 iPhone Safari 真机 smoke。

## 12. 阻塞项与开工建议

没有发现数据库、权限、AI Scope、Pending Action 或 API 兼容性层面的阻塞项。唯一需要补齐的是 **当前版本的精确多视口视觉基线和 iPhone Safari 验收**；它是 Phase 0 的质量门，而不是阻止 Phase 1 组件收敛的业务阻塞。

**建议进入编码阶段，但先执行 Phase 0 + Phase 1。** 不建议直接开始全站 Shell 重构，也不建议先动销售报价单。第一个业务样板页应是 **项目详情页**，在 Phase 1 稳定后进入 Phase 3。
