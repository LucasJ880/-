## 1. 问题

斑马帘比例、质保设置、能力配额策略三处保存时用 `FOR UPDATE` 锁住组织那一行。别的表插入一行、外键指向这个组织时（写审计、建项目、加成员、把用户的当前组织切过来……），数据库会对组织行加一把很弱的锁；`FOR UPDATE` 与它互斥。后果是：保存会被任何一个还没提交的「往本组织插入一条记录」卡住，反过来也卡住它们。实测：有人插入一条审计后 0.9 秒不提交，这三处的保存都要等满 0.9 秒。

FIX-3（#436）已经把其余写入方换成了不互斥的 `FOR NO KEY UPDATE`，这三处是当时留下的，锁的写法也因此散在四个地方。

## 2. 做了什么

1. 三个文件、四条语句改为调用 FIX-3 已有的 `lockOrganizationRow`（`FOR NO KEY UPDATE`）：
   - `src/app/api/sunny-process/zebra-ratios/route.ts`
   - `src/app/api/install/warranty-settings/route.ts`
   - `src/lib/capabilities/governance/policy.ts`（新建、修改各一条）
2. 守卫测试加几条：`src/`、`scripts/`、`prisma/`、`deploy/` 下不得再出现对组织行取 `FOR UPDATE` 的语句；入口那条锁行语句原样在；这三处都在读之前锁行、写回的内容取自锁里读到的那一份。
3. 新增一份隔离库测试，直接调两个接口和配额策略的两个函数，用「有人拿着锁不放 0.9 秒」量等待时间。

`FOR NO KEY UPDATE` 就是普通的 UPDATE 改非主键列本来会拿的那把锁：与外键检查不冲突，与自己、与 `FOR UPDATE` 互斥。所以写入方之间照样一个一个来。

## 3. 需要你知道的

### 3.1 交接文档里说的「会引出死锁」，对这三处并不成立

交接文档 §0.5c 写的理由是「`FOR UPDATE` 会与外键检查互斥、引出死锁」，我的四件套初稿也照这个写了。独立审查在旧代码上把我那个「并发不死锁」的场景跑了 7 次都通过，又定向试了 98 轮，没有造出死锁。原因：FIX-3 当时测到的死锁，是因为开户的事务锁住组织行之后还要去更新用户那一行，两边拿锁的顺序是颠倒的；这三处锁行之后只再插入审计或写策略行，没有那种颠倒。

所以这次改动**实际解决的是互相卡住**（有实测数字），不是死锁。提案、设计、规格、测试里的说法都已改成这样；那个并发场景保留为回归检查，并注明它在改动前后都通过。

### 3.2 没有开关，合并即生效

改动只是把锁换成更弱的一种，写入方之间照样互斥。滚动发布时新旧代码并存也没问题：两种锁彼此互斥（独立审查用 psql 逐项核过），与删除组织、改组织唯一键的操作也仍然互斥。

### 3.3 守卫拦不住变量拼出来的 SQL

守卫按源码文字找「带引号的组织表名 … `FOR UPDATE`」。带 schema、JOIN 进来、`FOR UPDATE OF`、写在普通字符串里的都能拦下；表名或锁子句由变量拼出来的拦不住。CI 没有数据库，那种情形只能靠本地的隔离库测试发现。规格里照实写了这一条。

守卫宁可多拦：一条语句里读了组织表、锁的是别的表，也会被拦下，需要把读组织表拆成另一条语句。目前代码里没有这种写法。

### 3.4 Sunny 工艺单的隔离库测试在 main 上本来就失败

`src/lib/sunny-process/__tests__/autogen-db.isolated.test.ts` 里有斑马帘比例接口的用例，本想拿来做回归。它在 main 上第一步就失败（`mark-signed` 返回「无权操作此报价单」`NO_BINDING`），之后因取不到工艺单而中断，跑不到斑马帘比例那一段。#440 合并之前的提交上也是一样，与这次改动无关。CI 不跑这份测试（没有数据库），所以一直没人看到。我没有动它；斑马帘比例接口由这次新增的隔离库测试覆盖。**这件事需要另外有人看一下**：是鉴权改动之后测试数据没跟上，还是接口行为变了。

审查确认没有问题的：没有任何代码依赖原来那把更强的锁；组织不存在时三处的行为与原来相同；测试的时间阈值在加压下也稳（不该等的 22–136 毫秒，该等的 909–942 毫秒，界线 500 毫秒）；测试跑完不留数据。
