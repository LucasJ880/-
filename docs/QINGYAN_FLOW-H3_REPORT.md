## 1. 为什么改写了 H3

方案原写：「接受补遗变更后，受影响的要求回到待确认；已发询价若引用了被改的要求，在该轮上标出」。动手前的只读调查（交接文档「H3 调查要点」）发现前提不成立：

- 生产上没有增量分析。补遗来了 = 一份新的完整分析，要求全部重新抽取、都是待确认——「回到待确认」已经发生，而且是全部。
- 要求跨分析没有稳定的标识（V2 的编号是去重之后按位置编的 `R-001…`）。
- 询价轮次不记它用了哪些要求，只存了渲染好的邮件正文。

所以做不到「标出引用了被改的要求的那一轮」。能确定的是：**这一轮的正文定下之后，询价单取要求用的那一份分析变了**。

## 2. 做了什么

- 询价入口接口（`GET /api/projects/{id}/tender-rfq/entry`）在开关开启时多返回 `analysisUpdateNotes`：询价引擎发出的每一轮，如果询价单取要求用的那一份分析（最新创建的等待审核或已批准的分析，与 `loadRfqRequirementInputs` 同一份）在这一轮的发送卡创建（正文定下）之后才完成、或才批准，就给这一轮一句提示。
- 提示写：「这一轮是 X 起草的；之后招标分析在 Y 有了更新（新的一份完成或批准），这一轮引用的要求可能已经变了，请对照最新的要求核对，需要时另发一轮」（日期按组织时区）。
- 更新之后已经又起草过一轮的，之前的轮次不再提示。
- 询价区在那一轮的状态行下显示（收起的轮次也看得到）。

## 5. 独立审查

开 PR 前请了一个不带结论的独立审查（只给分支与四件套，它在自己的工作区里跑测试与 18 处变异）。没有高等级问题。处理：

| 编号 | 发现 | 处理 |
|---|---|---|
| M-1 | 同一份分析在起草之后被批准（带「全部确认」），询价单少了一批要求，却没有提示 | 修。更新时刻 = 完成与批准里较晚的那个（D1）。单条确认、驳回仍不算，写进 spec 与 Risks |
| M-2 | 两条主要的时间规则没有能失败的测试：「按完成时间、不按创建时间」「按起草时间、不按发出时间」两处变异都存活 | 修。隔离库测试加「起草时还在进行、之后才完成」「起草很久之后才发出」 |
| L-1 | 「最新的分析」与询价单取要求时的取法不同：一份更早创建、失败后重试、最近才完成的分析会误报 | 修。改用询价单同一份（最新创建的可用分析）；测试覆盖这个情形 |
| L-2 | design 与代码注释说有一条路径写等待审核而不写完成时间——不对 | 改正说法；回退到创建时间只作防御 |
| L-3 | 起草时读要求与建发送卡之间的极短窗口 | 写进 Risks |
| L-4 | 已经另发了一轮，旧的轮次还一直挂着「需要时另发一轮」 | 修。更新之后又起草过一轮就不再提示 |
| L-5 | 状态行的呈现没有测试（藏起来、只在等待时显示两处变异存活）；没有截图与报告 | 修。加呈现测试；真实浏览器截图；本报告 |

## 7. 已知限制

- **会多提示**：分析更新了，这一轮引用的要求其实没变，也会提示。措辞写「可能」。
- **会少提示**：单条要求的确认、驳回不算更新；起草时读要求与建发送卡之间的极短窗口。
- **另发的一轮不一定覆盖之前那一轮的供应商**：只要更新之后起草过任何一轮，之前的就不再提示。
- **只管询价引擎发出的轮次**；人工标记已发送的轮次没有提示。
- **入口接口多一次查询**（开关开着、项目有引擎发出的轮次时）。

## 8. 没做的

- 说出具体哪条要求变了；自动起草、重发、通知供应商。
- 补遗变更候选（V2 在完整分析里写的）的显示与「接受」按钮——单独定（交接文档「H3 调查要点」第 3 条）。
