## 3. 现状（产品侧读代码核对过）

青砚有四种发给供应商的文件，五条生成路径：

| 文件 | 入口 | 内容取自 | 问题 |
|---|---|---|---|
| 国内供应商询价（没有分析综合时） | 「一键生成文档」菜单，docType `supplier_rfq` | 无项目内容，固定 7 行英文 | 工厂拿到无法报价 |
| 国内供应商询价（有分析综合时） | 同上 | AI 分析综合的技术要求与商务交付条目（标题与说明） | 说明是站在我方角度写的；只查招标身份，**不查敏感词**；内容不是人工逐条确认的；没有数量、贸易条款、截止日期、抬头 |
| 供应商技术确认表 | 菜单，docType `tech_confirm` | 无项目内容 | 英文占位模板，竖线字符画的假表格 |
| 国内供应商简报 | 菜单与简报面板，docType `china_supplier_brief` | 情报室事实 | 英文与内部标签为主，多处 `[PENDING]`；**面板默认备注（一句内部提醒）会印进正文** |
| 询价单（邮件附件） | 发询价审批卡 | 人工确认的供应商侧要求 + 关键事实 + 发起人填写项 | 最好的一份。开关默认关，未对 Sunny 打开 |

邮件附件询价单本身的问题（RFQ-PDF-2 要解决的）：

1. 问了单价、起订量、交期、有效期，但没有地方填。
2. 请工厂「打印本表填写后拍照或扫描」发回，而回信解析不读图片，扫描件读不出文字（`inbound-parse.ts` 的 `extractAttachmentTexts`）。
3. 「序号」与「要求编号」两套编号并存。回信解析只拿到强制要求的编号（`mandatoryCodes`），工厂按序号回答时对不上。
4. 数量、贸易条款、交付要求排在最后一页；数量写成「1240（请分档报价）」，没有单位。
5. 规格栏只占表宽约 37%，两栏空白占约 38%；14 条要求排 4 页。
6. 「强制 / 评分」「招标文件 p.14」对工厂没有意义。
7. 中文化失败的要求整行只有英文，没有提示（`requirement-translate.ts` 失败时按设计保留英文）。
8. 要求编号超过约 7 个字符会压到「类型」列上（编号列定宽且不换行）。
9. 询价方只有公司名，没有联系人。

## 5. 任务

### T1 · RFQ-PDF-1 `supplier-docs-converge`

**Why**：菜单「国内供应商询价 PDF」走的是内容最少的路径，其中一条把 AI 写给我方的说明印给工厂且不查敏感词；简报会把一句内部提醒印进正文。

**What**（每条一个可验证的改动）：

1. 改 `supplier_rfq` 的生成：用发询价时同一个询价单生成器排出内容（已确认的供应商侧要求、关键事实、组织询价设置里的发件抬头与回复截止提前量），用询价单附件的同一个模板渲染。菜单生成没有发起人填写项：数量阶梯、目的地、范围说明、附加问题都为空，贸易条款为空。
2. 不再读 AI 分析综合来生成任何供应商侧文件；`supplier_rfq` 不再有「有分析 / 无分析」两条路径。
3. 没有可收入的要求时不生成：接口返回 422 与既有说明「没有已确认且属于供应商侧的要求，先在青砚「招标要求」里逐条确认后再生成询价。」，不写文件、不建记录。敏感词与招标身份命中沿用询价单生成器的既有结果，同样 422、不写文件。菜单把说明原样显示出来。
4. 生成的 PDF 过附件同一套检查（是 PDF、内嵌 Noto Sans SC、不超过 5 MB）。任何一项不过：不写文件、不建记录、返回中文说明。`supplier_rfq` 不再回落成 HTML 文件。内部文件（备忘录、RFI、任务单、投标起草）的 HTML 回落保持不变。
5. 下线 `tech_confirm` 与 `china_supplier_brief` 的生成：去掉两个菜单项和简报面板；接口对这两个 docType 按无效类型拒绝；已生成的旧文件与记录保留，照常能在列表里打开和下载。
6. 菜单项改名为「供应商询价单 PDF」；生成记录的标题为「询价单-{询价编号} vN」，下载下来的文件名含询价编号。
7. 清理不再被调用的代码与测试（有分析时的供应商询价表模板、简报正文拼装），保留仍在用的敏感词判断函数（`build.ts` 等在引用）。`start-intelligence.ts` 清单里的「国内供应商中文 PDF」一项，核实它指哪种文件后改成指向询价单或删去，在 design 里写明。
8. 写 `docs/QINGYAN_RFQ-PDF-1_REPORT.md`，更新 TASKFLOW 状态列。

**受影响的 Muse 意图**：无。本 change 不触碰 muse-bridge，也不改询价起草、审批、执行。

**受影响的主规格**：`tender/supplier-identity-guard` 的「供应商侧生成文件」「供应商侧文件命中时不生成」两条要改。specs 增量要覆盖：菜单生成的询价单内容从哪来；与邮件附件是同一份模板；没有要求、命中敏感词或身份、PDF 检查不过时接口各返回什么；两种文件下线后接口返回什么；旧文件保留。

**Out of scope**：询价单模板的文字与版式（RFQ-PDF-2）；邮件正文；审批卡、执行器、附件开关；内部文件；回信解析；任何 schema 改动。

**验收**（每条对应一个测试或命令）：

- 同一个项目、同一起草日期、没有发起人填写项、贸易条款为空时，菜单生成的询价单 HTML 与起草询价时附件的 HTML 逐字节相同（内容指纹相同）。
- 项目没有已确认的供应商侧要求：`POST /api/projects/{id}/generate-pdf`（`supplier_rfq`）返回 422 与上面那句说明，生成记录数不变。
- 分析综合里写着「毛利」「预算」的项目：生成成功且文件里没有这些词（因为不再读分析综合）。
- 注入一个返回「没有内嵌中文字体的 PDF」的生成函数：返回错误说明，不建记录，没有 HTML 文件落库。
- `tech_confirm`、`china_supplier_brief` 的 POST 被拒；GET 列表仍含之前生成的这两类旧记录。
- 源码断言：`generate-docs.ts` 不再引用分析综合的供应商询价表模板与简报正文拼装。
- 门禁：`npm test`（失败项与开工前基线逐项对照）、`npm run typecheck`、`npm run lint:baseline`、`bash scripts/check-test-registry.sh`、`openspec validate supplier-docs-converge --strict`、`git diff origin/main -- prisma/ vercel.json` 为空。

**design 里要回答的**：起草日期用哪个时区（附件用的是组织时区）；`supplier_rfq` 继续沿用生成记录的版本号与过期标记；已下线类型的响应码与说明文字；PDF 生成失败的说明文字。

### T2 · RFQ-PDF-2 `rfq-sheet-template-v2`

依赖 T1 合并（或基于 T1 的分支开工）。T1 之后菜单与邮件附件共用模板，本 change 只动模板与询价单生成器。

**Why**：现有询价单问了价格却没有填写处，让工厂用系统读不了的方式回复，两套编号与回信解析对不上；同样的内容排得比需要的长一倍。

**What**：

1. **首屏。** 抬头印公司名、联系人、邮箱；右侧编号区印询价编号、询价日期、回复截止，回复截止加粗。其下「一、询价内容」印范围说明（有时）、数量、贸易条款与目的地、交付要求（有时）。
   - 联系人取组织投标档案报价抬头里的默认经办人，为空就不印这一项。邮箱取询价设置里的展示发件人，不取授权邮箱。
   - 数量：发起人填了数量阶梯就印阶梯；没填而有已确认的数量事实时，印这条事实的中文原文（带单位）；都没有时沿用现有那句话。数量事实原文是招标文本，要进招标身份检查与内部字段检查，命中即整份失败。
2. **报价表。**「二、报价」：每个数量档一行，列为数量、单价（含包装）、币种、贸易条款、备注；另有一行「其他数量档」；下面一行三格：最小起订量、生产交期（天）、报价有效期至。这六项与 `INBOUND_MISSING_FIELDS` 一一对应。
3. **规格确认表。** 列为编号、要求、类型、是否满足、差异说明。
   - 只留要求编号一列，去掉序号列。
   - 要求一格：中文在上，英文对照小字在下；中文与英文相同时只印一遍。去掉「招标文件 p.N」。
   - 类型：「必须」「加分」，替换「强制」「评分」。
   - 是否满足：三个勾选框「□ 满足 □ 部分满足 □ 不满足」。
   - 按类别分四组，组内按要求编号升序，组标题带条数：产品与规格（产品、技术、性能）；安全与认证（安全）；样品与图纸（样品、图纸）；交付、质保与服务（交付、质保、安装、培训）。没有条目的组不印。
   - 长编号在自己的格子里换行，不压到别的列。规格栏不少于表宽的 45%。表头每页重复，行不跨页。
4. **没有中文译文的要求。** 按既有的语言判断（`needsChineseTranslation`）判为非中文的，中文位置印「（暂无中文译文，以原文为准）」，下面照印英文。询价入口状态与菜单生成结果提示「有 N 条要求还没有中文译文」，并指向既有的补翻入口（合规矩阵卡上的翻译按钮）。只提示，不阻止生成与送审。
5. **固定文字。**
   - 规格表上方：`以下是最终客户的要求。原文里的 bidder / vendor / supplier 指我方，贵司只需确认产品与资料能否满足。`
   - 回复方式：`请把回复发给发来本询价单的联系人：按编号逐条写明，或把填好的表以 Excel / 可复制文字的 PDF 发回，请不要只发照片或扫描件。做不到的请直接写明，我们更看重准确。`
   - 不再印固定的 Q1 到 Q5（规格表的勾选栏与报价表已经承接）；发起人填写的附加问题仍然印，标题「请另外回答」，没有就不印这一节。
6. **请随报价提供。** 改成勾选清单。既有派生项之后固定追加一组，组名「首次合作或尚未提供过的，请一并提供」：营业执照复印件；工厂照片（车间与生产现场）；劳工与安全生产制度说明；原材料来源（公司与国别）；材质证书；BSCI / SMETA / SA8000 审核报告（如有，非强制）。
7. **邮件正文同步。** 规格行按同一分组顺序；每行以要求编号开头，不再有序号；【强制】【评分】改【必须】【加分】；去掉「（招标文件 p.N）」；材料清单与附件同序同条数；结尾措辞统一为按编号回复。固定问题 Q1 到 Q5 在正文里保留（正文没有表格可填）。
8. **收尾。** 签章栏做成带边框的一块，不与上一行拆页；页脚、内容安全策略、同输入同输出、PDF 检查都保持不变。版式版本从 1 升到 2。写 `docs/QINGYAN_RFQ-PDF-2_REPORT.md`，更新 TASKFLOW。

这 8 组如果在 tasks 里装不下 8 条，就拆成两个 change，但两个 change 合起来只升一次版式版本，并在同一个 PR 周期内相继合并；怎么拆在 proposal 里写明。

## 6. 与八条硬纪律

| 纪律 | 关系 |
|---|---|
| 1 零 schema | 不加表和字段。联系人读组织投标档案里已有的报价抬头 |
| 2 出站先审批 | 不新增发送路径。菜单文件仍是下载；邮件附件仍走审批卡与内容指纹 |
| 3 禁止第三套队列 | 不涉及 |
| 4 脱敏 | 改善：AI 分析文字不再进入供应商文件；新增的数量事实原文要过内部字段检查 |
| 5 不爬登录页 | 不涉及 |
| 6 邮箱分离 | 抬头只印展示发件人，不碰授权邮箱 |
| 7 确定性优先 | 不新增 AI 调用。分组、类型用词、译文判断、合规清单都是查表或规则 |
| 8 测试注册 | 新增或改名的测试在同一个 task 里注册进 `scripts/test-all.sh` |
