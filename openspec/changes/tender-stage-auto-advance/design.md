# Design：阶段记录跟着事实自动前进（FLOW-H1c）

## Context

- 阶段记录 = 项目上的几个时间（`interpretedAt`、`supplierInquiredAt`、`supplierQuotedAt`、`submittedAt` 等），`recordedStageOf`（`src/lib/tender/stage.ts`）取最靠后的那个。项目列表、Muse 的 `status`、主动提醒、放弃项目的接口都读它。
- 正式推进走 `advanceProjectStage`（`src/lib/tender/stage-transition.ts`）：要人确认；同时改招投标状态、写讨论区消息与审计、通知成员、有来源系统时触发 BidToGo 状态回调、建阶段任务。
- 已有两处绕过它、只写时间：
  - 分析收尾（`src/lib/tender-auto-analysis/worker.ts`）：`interpretedAt` 为空时写入；
  - 询价发出（`src/lib/tender-rfq/execute.ts`，审批通过后执行，Muse 或网页审批都走它）：每发出一轮都覆盖 `supplierInquiredAt`。
  两处都不改招投标状态、不发回调、不建不关任务。
- 人工把询价项标记为已发送（电话、微信询价，`…/items/{itemId}/mark-sent`）不写任何阶段时间。
- 「供应商报价」没有任何自动写入。录入报价有两条路：人工录入接口（`/api/projects/{id}/inquiries/{inquiryId}/items/{itemId}/record-quote`）与回信自动解析（`src/lib/tender-rfq/inbound-sync.ts`），都调 `recordQuote`（`src/lib/inquiry/service.ts`）。
- FLOW-H1b 让项目页按事实显示阶段，并写明「阶段记录没有自动推进」；是否让记录本身前进留给了 Lucas，他定为要。
- FIX-5（#447，待合并）修好了阶段任务：进入新阶段时关掉之前各阶段还没完成的自动任务、为新阶段建任务、同一项目加锁查重、已放弃不建。**本 change 调它的入口 `onStageAdvancedTasks`，建任务那部分要 #447 合并之后才真的生效**（main 上建任务仍会因 `sortOrder` 失败，错误被吞掉）。

## Goals / Non-Goals

**Goals**

- 第一家报价录入后，阶段记录到达「供应商报价」。
- 三处自动写入在真的推动阶段时，与人推进时一样收、建阶段任务。
- 不新增任何对外动作。

**Non-Goals（具体到文件）**

- 不改 `src/lib/tender/stage-transition.ts`（推进规则、人确认、回调、通知）。
- 不改 `src/lib/tender/stage-tasks.ts`（任务模板与收建规则，FIX-5 的范围）。
- 不改 `src/lib/project-intake/service.ts`（分发写的时间）。
- 不改 `src/lib/muse-bridge/`、`src/lib/proactive/`、项目页组件（`src/components/tender/project-progress-section.tsx` 那行「阶段记录没有自动推进」的说明不改，见 Risks）。
- 改动的既有文件只有：`src/lib/inquiry/service.ts`（`recordQuote`、`markItemSent`）、录入报价与标记已发送两个接口、`src/lib/tender-rfq/execute.ts`、`src/lib/tender-auto-analysis/worker.ts`、审计的两张标签表（`src/lib/cockpit/audit-labels.ts`、`src/lib/activity/formatter.ts`）。
- 不改两处已有写入原来写不写、写什么：分析收尾仍是「为空时写」，询价发出仍是「每轮覆盖」。

## Decisions

### D1 只写时间，不改招投标状态，不走 `advanceProjectStage`

自动前进只做条件写入（该段时间为空时写），加上任务与审计。

- 否决：调用 `advanceProjectStage`（带 `humanConfirmed`）。它会改招投标状态，并在项目有来源系统时向 BidToGo 发状态回调——那是对外发送，原来要人确认后才发；自动触发违反「出站先审批」。它还会给全体成员发「项目已推进」的通知，录一家报价就通知一次太吵。
- 否决：同时改招投标状态但不发回调。招投标状态与回调是一对（回调就是告诉来源系统状态变了），只改一边会让两边对不上。
- 代价：招投标状态会落后于阶段记录（例如阶段是「供应商报价」，状态还是「供应商询价」）。这与已有两处自动写入一样。

### D2 一个共用的「到达某阶段」函数，三处都调

新文件 `src/lib/tender/stage-auto.ts` 的 `recordStageReached`：看总开关 → 读项目 → 看组织的开关、判断能不能前进 → 条件写时间 → 收建任务 → 写审计。调用方在加载这个模块之前先看总开关，关闭时不加载、不查库。

- 已有两处：在原来的写入**之前**调它；原来的写入原样保留。开关关闭时与原来完全相同；打开时函数先写了，原来的写入要么什么也不改（分析收尾：已不为空），要么照旧覆盖成这一轮的时间（询价发出）。
- 否决：把两处原来的写入替换掉。会改变它们在开关关闭时的行为，或者让「每轮覆盖」变成「只写第一次」，影响时间轴。
- 否决：每处各写一份判断。三份规则会走样。

### D3 只对进行中、还没有结果的招投标项目生效

不是招投标项目、已放弃 / 已归档、招投标状态已是结果或已记了授标日期的，不写不建不关。已取消的询价轮次里录入报价不算。

- 否决：照写时间、只是不建任务。已放弃的项目录一家报价就把阶段记录往前推，项目列表与复盘会显示一个放弃之后才到的阶段。
- 这对已有两处意味着：开关打开时，它们对这类项目只做原来那一次写入，不另外做什么。

### D4 只前进一次；只在会变靠后时写

写之前先算：把这一段的时间写上之后，阶段记录会不会比现在靠后。不会就不写。用条件更新写（这一段为空、仍是进行中、招投标状态没变、没有授标日期、更靠后的各段仍为空），并发时只有一个写成功，读之后状态变了也不写。

- 否决：为空就写，只是阶段没变时不动任务（初稿的做法）。独立审查指出两个问题：阶段只由招投标状态得出的项目（例如状态是已提交、没有任何阶段时间），写上「供应商报价」的时间反而把阶段记录往回拉；已提交的项目补上报价时间，时间轴上「供应商报价」会排在「项目提交」之后。
- 否决：每次录入报价都去收建任务。第二家报价会重复。
- 分析收尾、询价发出原有的「为空就写 / 每轮覆盖」不受这条影响，照旧。

### D7 人工标记已发送也算「供应商询价」

电话、微信询价没有经过执行器，人会在青砚里把询价项标记为已发送。它和执行器发出是同一个事实。执行器内部也调用标记已发送，但不在那里触发（执行器按这一次真的发出了几家自己触发，记的是批准执行的人）。

- 否决：只认执行器发出的。电话询价的项目阶段记录会从「项目解读」直接跳到「供应商报价」，中间那段的任务永远不建。

### D5 负责人：触发的那个人，不知道是谁时是项目负责人

人工录入 → 登录用户；询价发出 → 批准执行的人；分析收尾 → 发起分析的人；回信自动解析 → 项目负责人。

- 否决：一律给项目负责人。人工录入时录的人更清楚下一步。
- 否决：不知道是谁就不建任务。回信自动解析是常见路径，这样会让那条路上永远没有任务。

### D6 审计用独立的动作名

动作名 `tender.stage.auto_advance`，不用通用的「状态变更」：通用的会被活动流与通知按「状态变更」解读。审计里不放报价金额。

- 否决：不写审计。自动改了别人看得见的阶段，要能查到是什么触发的。

## 与八条硬纪律的关系

1. **零 schema**：遵守。写既有的时间字段与审计表。
2. **出站先审批**：遵守。不调 `advanceProjectStage`，不触发 BidToGo 回调，不发邮件。询价发出本身仍在 Muse 审批之后。
3. **禁止第三套队列**：遵守。在录入报价、询价发出、分析收尾的原有流程里同步执行，没有新的后台机制。
4. **脱敏**：遵守。审计只有阶段、触发与人，不含金额。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。回信自动解析读的仍是原来的授权邮箱。
7. **确定性优先**：遵守。条件判断，不调模型。
8. **测试注册**：新测试注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## Risks / Trade-offs

- **招投标状态落后于阶段记录，而且「供应商报价」这个状态以后就到不了了**（D1）。阶段推进在目标阶段已到时什么也不做（返回「无需重复推进」），所以自动写了时间之后，人在对话里推进到「供应商报价」不会再改招投标状态、也不会给 BidToGo 发这一次回调；招投标状态会从「供应商询价」直接跳到推进到「项目提交」时的「已提交」。已有两处自动写入对「项目解读」「供应商询价」两个状态本来就是这样。要不要让人确认的推进在阶段已到、状态落后时仍补状态与回调，要改 `stage-transition.ts`（#446 也在改它），不在这次做，留给 Lucas 定。
- **那行「阶段记录没有自动推进」的说明**（FLOW-H1b）：开关打开后，它只在三种情形下出现——只有投标报价单、项目级报价单、开关没覆盖的组织——这些情形里阶段记录确实没有自动推进，所以照旧准确；措辞写在 #445 归档的规格里，这次不改。
- **审计挂在人名下**：回信自动解析等不知道是谁的情形，审计记在项目负责人名下（另有「是否知道是谁」一项）；驾驶舱把这条审计标为系统动作，活动流写「（系统）自动推进了阶段记录」。
- **依赖 #447**：#447 没合并时，开关打开也只会写时间、关上一阶段的任务，建不出新任务。合并顺序：#447 在前。
- **成员会看到更多任务提醒**：自动前进也会建任务，FIX-5 报告 §3.1 说的到期提醒同样适用。
- **回信自动解析可能解析错**：把一封不是报价的回信当成报价，会让阶段记录提前到「供应商报价」。这是解析本身的问题，人可以在询价里改回；阶段记录不会退回（阶段不允许回退，既有规则）。
- **开关打开后的头几天**：已经落后的老项目不补写，要等它们下一次有报价录入。

## Migration Plan

无数据迁移。开关默认关。回滚 = 关开关；已经写入的时间与任务留着。
