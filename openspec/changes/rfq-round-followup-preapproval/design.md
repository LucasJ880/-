# Design

## Context

现状（均已对照代码核实，`文件:行` 见 `docs/QINGYAN_RFQ-AUTO-1_REPORT.md` 的底稿部分，实施时补）：

- 发询价：一轮一张卡 `tender.send_rfq`，有效 72 小时，载荷含每家供应商的收件人、主题、正文；整份载荷有哈希，批准时校验。
- 催单 / 追问：每个询价项每个槽位一张卡 `tender.send_chase`，槽位是「第 1 次催单 / 第 2 次催单 / 缺字段追问」，有效 48 小时。扫描每 10 分钟跑一次（挂在既有的回信同步之后），由 `decideChases` 决定该起草什么。
- 执行只能经 `executePendingAction(审批记录 id)`：一条记录执行一次，执行后不可重放；审计、去重、界面列表、通知全部以单条审批记录为单位。
- 催单扫描与执行器都不看轮次状态，也不看回复截止（扫描在起草时看截止，执行器不看）。

## Goals / Non-Goals

**Goals:**

- 一轮询价，人只批一次；之后的固定模板邮件按卡上写明的范围自动发。
- 每封对外邮件仍有自己的审批记录、正文哈希与审计，可逐封追溯到是谁批的哪张卡。
- 任何一条条件不满足就退回今天的逐张人工批，不存在「批不了也发不了」的中间状态。

**Non-Goals:**

- 免批发送、白名单、按供应商信任度放行。
- 改模板、改节奏、自动起草轮次（RFQ-AUTO-2）。

## Decisions

### D1 授权放在发询价卡的载荷里

`TenderSendRfqPayload` 加可选字段 `followUpPolicy`：`{ version: 1, maxReminders: 0|1|2, chaseAfterDays, replyBy, allowMissingFieldQuestion, templateHash }`。载荷哈希天然覆盖它，批准时既有的防篡改检查不用改。间隔天数与回复截止在批准时定格——之后有人改组织设置，不影响已批准的这一轮。

备选：把授权存到组织设置或另建记录。没选：授权必须和「人看到并批准的那张卡」是同一个东西，分开存就可能出现卡上写的和实际执行的不一致。

### D2 每封跟进仍建自己的审批记录，再以批准人的身份执行

执行器、去重、审计、界面都以单条审批记录为单位（现状）。所以不发明「一张卡执行多次」：扫描照旧为这封邮件建 `tender.send_chase` 记录，然后立刻调用既有的 `executePendingAction`，执行上下文里的用户是**批准该轮的那个人**（发询价卡上的决定人），并带上来源标记「随轮次授权」。

- 好处：正文哈希、状态原子切换、有效期、线程与供应商状态的复核全部照常生效；并发两次扫描只会有一条记录建成（幂等键唯一），只会执行一次（`pending → approved` 是原子的）。
- 执行器会重新检查这个人现在是否仍有审批权；没有了（离职、降权）就执行不了，记录留在待批，等别人处理。这正是想要的行为。
- 审批记录上的决定人如实是那个人；另写一条审计说明这是「随轮次授权自动执行」，指向发询价卡，免得日后看记录以为他当时点了 16 次。

备选：让发询价卡保持「已批准」状态反复执行。没选：会绕开执行器「终态不可重放」的保护，那条保护正是为了防止崩溃后重复对外。

### D3 覆盖判定是一个纯函数

`decideFollowUpCoverage(input)` 返回「覆盖」或「不覆盖 + 原因码」。十二个条件见规格。输入全部由调用方查好传入，函数本身不查库、不调模型，可以离线逐条测。原因码写进审计与轮次页（「未自动发出：模板已变更」）。

判定做两次：建记录前一次，执行前一次（两者之间可能有人取消了轮次或点了停止）。

实施中补的一条：同一封邮件（同一家、同一序号）此前起草过——过期没人批、或自动执行时发送失败——之后重起草的不再自动发，原因码「此前起草过」。否则邮箱授权失效时，每 10 分钟一次的扫描会不停重试并留下一串失败记录。

### D4 模板指纹

催单与追问的正文由 `renderChaseEmail` 生成。新增常量 `CHASE_TEMPLATE_VERSION`，指纹 = 版本号 + 三段模板用固定样例渲染后的哈希。以后谁改了模板文字，指纹就变，已批准的轮次自动退回人工批——人批准的是当时看到的那版文字，不是之后的。

### D5 停止

停止 = 一条审计记录（动作 `tender.rfq_followup.stop`，对象是这一轮）。覆盖判定时查这一轮有没有这条记录。不可恢复：要恢复就得有人重新看一遍授权内容，那等于重新批，不如让他逐张批。

选审计记录而不是新字段：零 schema；「停止」本身就是一个需要留痕的动作，记录即状态。取消轮次也会停止（见 D6）。

### D6 取消 / 完成的轮次与回复截止

- 扫描：查询条件加上轮次状态必须是进行中。
- 执行器：发之前查轮次状态；催单再查回复截止。不满足就不发，返回成功但说明原因（与今天「供应商已回复就不发」的处理方式一致），不算失败。
- 这两条对人工批准的卡同样生效——是修现存缺口，不只是为自动流加的。

### D7 只有网页发起且勾选才带授权

建轮次的请求体加可选布尔 `autoFollowUp`；网页入口在开关打开时默认勾选，并在勾选框下列出范围。Muse 的 `rfq` 意图不传，载荷里就没有授权。

卡片摘要（所有界面共用的那行文字）加一句「含自动跟进：催单最多 N 次、缺字段追问 1 次」，这样在审批中心、驾驶舱看到这张卡的人也知道批的是什么。但模板预览只在网页原地审批处有——所以经 Muse 发起的不带授权。经网页发起、却在别的界面批准的情况：摘要那行字保证批准人知道范围。

### D8 硬纪律第 2 条的补充文字

现文：「出站动作一律先审批：任何对外发送……必须先建 PendingAction，批准后由执行器发出；批准前零出站。……」

拟在其后加一句：

> 一张已批准的审批卡可以一并授权它正文里逐项写明的后续固定模板邮件（目前仅限招投标询价轮次的催单与缺字段追问：次数、间隔、截止、模板指纹都写在卡的载荷里并受哈希保护）；这些后续邮件仍须逐封建 PendingAction 并经执行器发出，由系统以该卡批准人的身份执行并另写审计；任一授权条件不满足即退回逐封人工批准。

这句话不放宽「批准前零出站」，只说明「批准」可以是一次性覆盖一组事先写明的邮件。**需要 Owner 在 PR 里明确确认这段文字**；不同意的话，本 change 的其余部分不应合并。

### D9 界面

- 建轮次：勾选框「这一轮的催单和追问自动发（批准这张卡即一并批准）」+ 范围说明。
- 待批卡：授权范围一行 + 三段模板预览（可折叠）+ 「可随时停止」。
- 轮次状态：自动跟进「生效中 / 已停止 / 未生效：原因」+ 已自动发出 N 封 + 「停止自动跟进」按钮（二次确认）。
- 既有的待批催单卡列表不变——覆盖不住的照旧出现在那里。

## Risks / Trade-offs

- **批准一次，之后发错没人拦**：正文是固定模板、收件人锁定为原询价的收件人、次数有硬上限、任何条件变化即退回人工；最坏情况是给一家已经口头回复的供应商多发一封催单——与今天有人不看内容直接点批准的结果相同。停止按钮与开关是两层紧急制动。
- **以批准人的身份执行**：审批记录上显示他是决定人，但他没有逐封点击。用单独的审计与来源标记说明；轮次页也写明「自动发出」。
- **批准人离职**：执行器复核审批权时失败，该轮退回人工。不迁移授权给别人。
- **硬纪律文字被改动**：范围写死为「询价轮次的催单与追问」，不是一般性放开；其它出站动作仍然逐张批。

## Migration Plan

无数据迁移。开关默认关；打开后只对新建且勾选的轮次生效，已在进行中的轮次不受影响。回滚：关开关即回到逐张批；已建未执行的记录按待批处理。

## Open Questions

- 自动发出的跟进要不要给项目负责人一条站内通知（现在的设计是不通知，轮次页可查）。先不加，试用后看是否需要。
