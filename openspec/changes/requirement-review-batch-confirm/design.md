# Design

## Context

现状（main，`a17f4f7f`），动手前核对过界面：

- 招标分析面板的「要求」页签逐条列出要求；每条待确认的要求下面有「确认」「驳回」两个文字按钮，只在分析还没批准时出现。没有勾选、没有批量操作、没有计数。
- 「批准分析」是一次点击，不会顺手确认剩下的要求；批准之后界面不再给确认按钮。
- 询价单只带已确认的要求。RFQ-AUTO-2 之后，批准分析的那一下还会自动起草第 1 轮询价，卡上写明「另有 N 条没有确认的没带上」——那时已经来不及确认了。
- 批量确认的接口 `POST …/requirements/batch-confirm` 已经存在：请求体 `{ requirementIds }`，只把仍是待确认的那些改为已确认，返回 `confirmedCount`；一次最多处理 200 条，多出的被静默丢弃；不写审计。界面没有任何地方调用它。RFQ-AUTO-2 已经在这个接口成功后接了自动起草的判定。

约束：八条硬纪律；确认哪些要求必须是人的明确选择（它决定什么会发给供应商）。

## Goals / Non-Goals

**Goals:**

- 把「点几十次」降到「勾选 + 点一次」。
- 人在批准分析之前就知道还剩几条没确认、后果是什么。
- 批量确认留下「谁确认了哪些」的记录。

**Non-Goals:**

- 不改 `src/lib/tender-auto-analysis/review.ts`（确认、驳回、批准的行为）。
- 不改单条确认 / 驳回路由与批准路由。
- 不改 `src/lib/tender-rfq/**`（询价单取要求的规则、自动起草）。
- 不做批量驳回、一键全确认、筛选分组、批准后再确认。

## Decisions

### D1 勾选式，不做「一键全部确认」

每条待确认的要求一个勾选框；「全选待确认的」把当前列表里待确认的全部勾上；然后「确认选中的 N 条」。最快的路径是两次点击。

- 确认决定了什么会发给供应商。勾选让「选了哪些」可见、可改；全选之后人仍能取消个别几条。
- 默认不选任何一条：不替人做选择。

否决的备选：

- **一个「全部确认」按钮**：一次点击就把模型抽出来的全部要求变成「人确认过」，等于取消了审核。批准接口本来就有 `confirmAllRequirements` 参数，界面一直没用它，是同一个考虑。
- **批准分析时弹窗问「要不要顺便确认剩下的」**：把两个决定绑在一起，容易顺手点过去。

### D2 用既有接口，超过 200 条在前端分批

前端把选中的要求按 200 条一批依次提交，累加每批返回的 `confirmedCount`。某一批失败就停，告诉人已经确认了几条。

- 不改接口：它的上限与语义别处可能依赖。
- 接口对多出的部分是静默丢弃——所以必须由调用方分批，否则界面会显示「选了 450 条」而实际只确认了 200 条。

否决的备选：**把接口上限提高**——改的是既有行为，而且单次更新太多行没有必要。

### D3 计数与批准前的提示

要求列表上方一行：「已确认 X 条 · 待确认 Y 条 · 已驳回 Z 条」。Y > 0 且分析等待审核时，「批准分析」按钮旁一句：「还有 Y 条要求没有确认：批准后不能再确认，没确认的不会进询价单。」

- 这句话放在人做决定的那个按钮旁边，不拦、不多一次点击。
- 文案与计数由纯函数给出，可以离线测。

否决的备选：**Y > 0 时禁用「批准分析」**——有些要求本来就不打算发给供应商，不确认也不驳回是正常的。

### D4 审计写在路由里

批量确认成功后在路由里写一条审计（动作 `tender_analysis_requirements_batch_confirm`，对象是这份分析；内容：请求的要求号、实际确认的条数）。用吞错的写法：确认已经完成，审计失败不应让请求报错。

- 写在路由而不是 `review.ts`：路由才知道操作者是谁（服务函数今天不接收操作者），而且不改服务函数的签名。
- 单条确认与驳回今天也没有审计，这是既有缺口，本次不补（写进报告）。

否决的备选：**给服务函数加操作者参数并在里面写审计**——要改三个函数的签名与全部调用方，超出本次范围。

### D5 不加功能开关

这是既有接口上的界面操作，不对外发送、不改数据结构。出问题的回退方式是不点它（逐条确认照常可用）。

否决的备选：**加一个默认关的开关**——每多一个开关就多一种要测的组合；这里没有需要灰度的风险。Owner 如果要开关，加一个环境变量判断即可。

### D6 与自动起草的关系

批量确认接口成功后已经会做自动起草的判定（RFQ-AUTO-2）。分析还没批准时结果是「不必提示」，面板不显示任何东西；本次不改这段逻辑。实际效果是：人先批量确认，再批准分析，自动起草出来的询价单就带上了全部确认过的要求。

## 与八条硬纪律的关系

1. **零 schema**：遵守。审计写 `AuditLog`。
2. **出站先审批**：不涉及（不发送任何东西；确认要求只影响之后询价单的内容，询价仍要人批）。
3. **禁止第三套队列**：不涉及。
4. **脱敏**：不涉及（不触碰 Muse 通道；审计里只有要求号与条数）。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。计数、全选、分批都是纯函数；不新增模型调用；选择由人做。
8. **测试注册**：两个新测试注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## 验证方式

- `npx tsx src/lib/tender-auto-analysis/__tests__/requirement-batch-confirm.test.ts`（新）：计数、全选只选待确认的、分批（0 / 1 / 200 / 201 / 450 条）、结果文案（全部确认 / 少于选中 / 中途失败）、批准前提示的出现与消失；面板源码断言（只调用批量确认这一个新接口、控件只在等待审核时渲染、没有全部确认与批量驳回、默认不选）。
- `npx tsx src/lib/tender-auto-analysis/__tests__/requirement-batch-confirm-db.isolated.test.ts`（新，本地隔离库，没有库时自跳过）：经真实路由处理函数——确认成功与审计内容、实际确认数少于请求数、没有写权限被拒且不留审计、响应结构不变、别的项目的要求号不被确认。
- 既有测试全量：`npm run test:ci`、`npm run typecheck`、`npm run lint:baseline`、`scripts/check-test-registry.sh`、`scripts/test-runtime-architecture.sh`。
- 真实应用截图（本地库、演示数据）：勾选若干条与工具条、确认后的计数、批准按钮旁的提示，存 `docs/acceptance/rfq-auto-4/`。
- 开 PR 前请一个不带结论的独立审查。
- `openspec validate requirement-review-batch-confirm --strict`。

## Risks / Trade-offs

- **更容易不看就确认**：全选 + 确认只要两次点击。缓解：要求的原文与译文就在勾选框旁边；发出去之前还有询价审批卡，卡上是完整的邮件正文。这是本方案最主要的取舍。
- **分批提交中途失败**：前面几批已经确认，不回滚。界面如实说明已确认几条，刷新后列表反映真实状态。
- **两个人同时审同一份分析**：接口只改仍是待确认的那些，所以不会把别人驳回的改成确认；界面显示的是实际确认数。

## Migration Plan

无数据迁移，无开关。上线即可用；回退是回滚这次改动（逐条确认不受影响）。

## Open Questions

无阻塞实施的问题。两处取了推荐做法，Owner 可以改：不加功能开关（D5）；不做「一键全部确认」（D1）。
