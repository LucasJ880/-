# Design：邀请码直接绑定企业 + 用户管理按企业隔离（USR-1）

## Decisions

### D1 企业要显式选；公司 logo 跟随企业、不再手选
`Company` 与 `Organization` 是一对多（`Organization.companyId`），一个公司 logo 可能对应多个企业，所以不能从勾选的公司反推企业。反过来可以：logo 由企业决定。左上角品牌区（`CoBrand`）本来就优先取当前企业关联的公司，只有企业没关联公司时才退回账号上的 `companyIdsJson`。
Lucas 2026-11-09 决定把公司 logo 收进后台：邀请码页与用户管理详情都不再提供「公司归属」选择；绑定企业时服务端写 `companyIdsJson = [企业关联的公司]`（没有则空），保证账号级回退值也与企业一致。不绑企业的码仍接受接口旧参数 `companyIds`，接口不破坏；解绑企业不动已有的 logo 字段。
否决：选公司自动推企业（一对多时会进错企业）；继续让人手选 logo（与企业不一致时左上角显示会混乱）。

### D2 绑定企业的码只给销售 / 外贸，与注册校验同一套常量
注册路由对带企业的码已经有二次校验 `checkOrgBoundInvite`（平台角色 `sales` / `trade`，企业内角色 `org_member` / `org_admin`）。邀请码页新增的校验 `validateAdminInviteOrgBinding` 放在同一文件、用同一组常量，保证「能建出来的码一定能注册成功」。老板 / 总经理平台角色历史上带跨企业权限，不能经邀请码直接进外部企业；运营、普通用户本次不放开（见 Out of scope）。
否决：放开全部平台角色（会让 `boss` / `manager` 直接进入任意企业）。

### D3 企业必须存在且启用；个人工作区不出现在下拉里
接口层校验 `Organization.status === "active"`（注册时也会再查一次）。页面下拉排除 `personal-` 开头的个人工作区（每个旧式注册的人都有一个，混在里面容易选错）；接口不按 code 拦，平台管理员确实要绑也可以直接调接口。

### D4 补绑 / 改绑只影响以后的注册
`PATCH` 只改码本身；已经用这个码注册、落进个人工作区的人不会被搬走（搬人要动成员关系与岗位，仍走企业成员页）。

### D5 多次使用的企业码：条件更新按上限占用
原来 `registerIntoOrg` 用 `usedCount = 读到的值` 做 CAS，入驻向导的码都是单次使用所以没问题；平台邀请码常见「不限次数 / 10 次」，两个人同时注册时后到的人会误报「已达使用上限」。改为：有上限 → `usedCount < maxUses`；无上限 → 不加次数条件。单次码（`maxUses = 1`）语义完全相同。

### D6 用户管理的范围在服务端决定
`resolveUserListScope`（纯函数）：`scope=platform` → 全平台；否则 `orgId` 参数 → 该企业；否则当前工作企业（`User.activeOrgId`）；都没有 → 400 `ORG_SCOPE_REQUIRED`。企业范围按 `OrganizationMember.status = active` 过滤（离开企业的人不算员工），每行带该企业内角色。默认不回落到全平台，避免「没选企业就看到所有人」。权限不变：仍只有平台 super_admin 能调。
否决：只在页面上过滤（接口照样返回全平台，范围不由服务端保证）。

## Risks / Trade-offs

- 超级管理员找不在任何企业里的账号（例如旧式注册落进个人工作区的人）需要切到「全平台」——这是显式动作，页面上有按钮。
- 页面默认选中当前企业：如果管理员要建不绑企业的码，需要把「加入企业」改成「不加入企业」。表单上写明了用这个码注册会进哪个企业。

## Migration Plan

无 schema / 数据迁移；纯代码，随部署生效；回滚 = 还原文件。回滚后已绑定企业的码仍按既有注册路径加入企业（注册路由本来就支持）。
