# Design：Alberta 授标的人工录入

## Context

- 授标记录唯一写入口是 `src/lib/tender-intel/awards.ts` 的 `createOrObserveAwardRecord`：按 `(orgId, sourceType, sourceKey)` 幂等；同招标编号 + 同中标方 → 挂源到既有记录（`ATTACHED_EXISTING`）；按编号没找到时，同中标方 + 同授标日期 + 同金额（不看编号、不看采购方）→ 同样挂源；同中标方 + 同采购方但日期 / 金额对不上 → 新记录 `status = NEEDS_REVIEW` + `possibleDuplicateOfId`；`SYSTEM_VERIFIED` 只认带编号的 `CANADABUYS_OPEN_DATA`（服务里强制）。它不写审计。
- 信任级词表：`AI_EXTRACTED | HUMAN_CONFIRMED | SYSTEM_VERIFIED | NEEDS_REVIEW`；来源类型：`CANADABUYS_OPEN_DATA | WEB_SEARCH | PROJECT_RECORD | USER_ENTRY | OTHER_PUBLIC`。
- 授标情报的数字层（`deriveAwardIntelligence`）只算 `ACTIVE` 且 `HUMAN_CONFIRMED / SYSTEM_VERIFIED` 的记录；`NEEDS_REVIEW` 只算线索、不出数字。组织管理员在「历史中标」页确认（→ `HUMAN_CONFIRMED`）或撤回（`tender/award-review`）。
- CHAIN-2 / CHAIN-3 的「本采购方的他人授标」读同一张表，按采购方规整名找；CHAIN-3 的中标者名单只认 `ACTIVE` 且人工确认或权威来源的记录，CHAIN-2 的可比价格只用权威记录——待复核的人工录入要等组织管理员确认后才进入它们。
- CHAIN-1 前置核查：APC 对程序化访问返回 Cloudflare 人机验证，到此为止；交接文档第四十四次更正：现有授标历史面板做不了 Alberta 人工录入。

## Goals / Non-Goals

**Goals**：人在 APC 上看到的 Alberta 授标能如实录进来，来源、链接、信任级一看就知道是人工录入待复核；系统从头到尾不访问 APC。

**Non-Goals**：
- `src/lib/tender-intel/awards.ts` 的写入规则（幂等、去重、信任级白名单）——只改一处：按「中标方 + 授标日期 + 金额」挂到既有时，两边都有编号且不同就不挂（D8，Lucas 2026-11-20 GATE「收紧」）；其余只调用。
- `src/app/api/organizations/[orgId]/tender-awards/[awardId]/review/route.ts`（复核照旧）。
- `src/app/api/projects/[id]/external-intel/award-history/route.ts`（项目里确认 CanadaBuys 检索结果的入口不改）。
- `src/lib/tender-intel/award-intelligence.ts`、`src/lib/tender-intel/sourcing-suggestions.ts`、`src/lib/tender-import-leads/**`。

## Decisions

### D1：落库口径；撤回后可以重录

调用 `createOrObserveAwardRecord`：`actor = { actorType: "user", userId }`；`source.sourceType = "USER_ENTRY"`、`source.sourceUrl = 规整后的 APC 链接`、`source.sourceKey = "manual:apc:" + sha256(规整链接 + "\n" + 中标方规整名)[0:32]`、`source.capturedAt = 现在`、`evidenceSnippet = null`（系统没读过公告，不写任何「原文」）；`verificationStatus = "NEEDS_REVIEW"`、`confidence = "MEDIUM"`；`projectId = null`（组织级录入）。写入服务的幂等不看记录状态：同一来源键命中一条已被撤回的记录时，改用确定性的后继键 `{来源键}:after:{撤回记录 id}` 再写（与项目结果回灌 `own-result-backfill.ts` 的做法相同），撤回的那条保持撤回，重放仍幂等。

- 备选 A：`verificationStatus = "HUMAN_CONFIRMED"`（录入的人就是人）。否决：Lucas 定「信任级为待复核」；确认应由组织管理员在页面上做。
- 备选 B：`sourceType = "OTHER_PUBLIC"`。否决：Lucas 定「来源标成人工录入」。
- 备选 C：来源键 = `manual:{cuid}`（每次新建）。否决：同一条公告的同一个中标方录两次就是两条；用链接 + 中标方做键，重录返回「已经录过」。一条公告有多个中标方时各自一条。
- 备选 D：不处理撤回，撤回的就永远录不进来。否决：`tender/award-review` 写明撤回的记录不参与去重；填错的人撤回后要能更正。

### D2：APC 链接的校验与规整（不访问）

原文先查长度（≤ 2048），再用 `new URL` 解析（只做字符串解析，SHALL NOT 发起请求；只写了 `purchasing.alberta.ca/…` 的先补 `https://`），再判：协议恰为 `https:`、主机名恰为 `purchasing.alberta.ca`、没有端口、没有用户名密码、路径恰为 `/posting/AB-年份-编号`（编号 4–6 位，末尾的 `/` 不算）。路径形状按 Lucas 2026-11-20 给的样例 `https://purchasing.alberta.ca/posting/AB-2026-07664` 定（本次没有打开这个链接，也没有访问 APC）。合格的统一存成 `https://purchasing.alberta.ca/posting/AB-…`（编号大写，`?` 与 `#` 之后都去掉），存、算来源键、显示都用这一种写法——同一条公告只有一个来源键。反斜杠、全角主机名、`:443`、空白都由解析器收敛，`javascript:`、别的主机、`@` 把戏、带端口、末尾带点的主机、别的路径都被拒。源码断言该模块与接口里没有网络调用。

- 备选 A：接受任何链接。否决：Lucas 定「带 APC 公告链接」。
- 备选 B：只校验主机与「不是首页」（开 PR 时的做法）。否决：Lucas 给了样例后可以收紧；收紧后同一条公告只有一种写法，来源键不会因为 query 或大小写分成两个。
- 备选 C：编号只认 5 位（与样例相同）。否决：没有核对 APC 编号会不会变长，留 4–6 位的余量。

### D3：谁能录入

本组织有效成员且组织角色不低于 `org_member`（`org_viewer` 不行），平台超级管理员按既有规则（`requireOrgRole(request, orgId, "org_member")`）；平台超级管理员录入时组织必须存在（不存在 404）。复核仍只限组织管理员。列表接口返回 `canEnterManual`（同一判定），页面据此显示表单。

- 备选 A：只限组织管理员录入。否决：录的人常是做标的人；信任级已是「待复核」，确认仍要管理员。
- 备选 B：任何能看页面的人（含 `org_viewer`）。否决：查看角色不应写数据。

### D4：其它字段的校验

- 采购方、中标方：去空白后非空、≤ 200 字。采购方输入框带候选：调用人按项目可见性（`buildProjectVisibilityWhere`）看得到的本组织**招标**项目（`workDomain = "tender"`）的采购方写法，项目写法在前、最近更新的在前；再加本组织未撤回授标的采购方写法；按 `normalizeBuyerName` 去重、最多 200 个（每个来源最多读 1000 行，不用 Prisma `distinct`——没开 `nativeDistinct` 时它会把全部行读进内存）。照项目里的写法填才能和 CHAIN-2 / CHAIN-3 对上（按规整名完全相等，不做模糊匹配）。
- 招标编号：选填、≤ 100 字。
- 授标日期：选填、`YYYY-MM-DD`，并且往返一致（`2023-02-29` 这种会被 JS 进位的日期拒绝）、不早于 1900-01-01、不晚于今天（UTC 日期 + 1 天容差，与 CHAIN-3 同口径；表单的日期框 `max` 是本地今天）。
- 合同金额：选填、数字、0 ≤ 金额 ≤ 1,000,000,000,000、最多两位小数；先 NFKC（全角数字、全角逗号变半角），去掉开头的 `$`；逗号只认千分位（`1,234,567.89`），`1234,56` 这种把逗号当小数点的拒绝（否则差 100 倍）；`CAD 1,000` 这种带币种字样的拒绝（币种另选）。只填币种不填金额时忽略币种（表单里没填金额时币种不可选）；币种只认 `CAD`、`USD`（不分大小写），缺省 `CAD`。
- 范围摘要：选填、≤ 2000 字；单行输入，候选是本页列表里已有的写法（去重、最多 100 个）。可比价格按规整后的范围（小写、标点变空格、至少 4 个字）分组，同一采购方 × 同一范围 × 同一币种的已确认记录满 3 条才算（`award-intelligence.ts`），所以提示写「一句能反复用的采购内容，不带年份、编号、地点」。
- 链接：只写了 `purchasing.alberta.ca/…`（没带 `https://`）的替人补上再判。
- 字段是数字（接口调用方）时按字符串校验，不静默丢掉（`awardDate: 20261120` → 日期写法不对）。
- 请求体 ≤ 16 KB（先看声明的长度，没声明的边读边数，超了就停）；不是 JSON 当作空表单；校验失败 400 `{ error, code, field }`，返回第一处错误的那句话（顺序：采购方、中标方、链接、编号、日期、金额、币种、摘要），`field` 让表单标出那一格；不写库。

- 备选：币种接受任意三个字母。否决：落地价与可比价格只认 CAD / USD；别的币种录进来也用不上。

### D5：结果、审计、事务、并发

判定顺序：未登录 401 → `requireOrgRole` 403（平台超级管理员 + 组织不存在 404）→ 授标情报开关关 409 `组织授标情报尚未启用`（与既有处理接口同一句）且不访问授标表 → 校验 400。接口在一个事务里：调用写入服务（传事务客户端，撤回时按 D1 换后继键）→ 新建、疑似重复、挂到既有时写审计 `tender.award_manual_entry`（`targetType = "award_record"`、`targetId = 记录 id`；`afterData` 含结果、提交的全部字段（采购方、中标方、编号、日期、金额、币种、摘要、APC 链接）、信任级、挂到既有时那条记录的信任级）。重录（`ALREADY_OBSERVED`）不写审计。两次并发提交撞上来源唯一约束（P2002）时重读一次，按「已经录过」返回。成功 200，返回 `{ outcome, record: { id, verificationStatus, status, buyerName, solicitationNumber, awardDate }, messageZh }`。挂到既有的原因分两种说：招标编号与中标方相同；招标编号没对上（没填、或与既有的不同）但中标方、授标日期、金额都相同（写入服务的两条强匹配路径，前者看编号、后者不看编号也不看采购方）。挂到既有时写入服务只加来源，用户填的金额、日期、范围、采购方都不写进那条记录，所以结果那句要说「那条记录原有的内容和可信度不变」。同一条公告的同一个中标方撤回超过 10 次后再录 → 409 `这条公告的这个中标方撤回过太多次，没有录入；请联系组织管理员。`（不是 500）。

- 备选 A：审计写在事务外。否决：记录写了、审计没写，就查不到是谁录的。
- 备选 B：结果只返回代码、页面自己拼句子。否决：说法要和规格逐字一致，一处定义。

### D6：文字与页面

- 页面叫「历史中标」（导航与页面标题）。表单标题：`录入 Alberta 授标（APC）`（整行可点、带展开图标、`aria-controls`）；收起时：`把在 APC 上看到的中标结果录进来，经人工确认后计入统计。`；展开后的说明：`只录入你在 Alberta Purchasing Connection（APC）上亲眼看到的授标公告。系统只保存这个链接，不会自动访问它；复核的人会点开核对。录入后先列在下表、标为「待人工复核」，不计入金额、周期、可比价格和已确认的竞争对手；经人工确认属实后才计入（一般由组织管理员在下表确认）。`
- 字段分两组，贴近抄公告的顺序：「公告信息」（APC 公告链接 → 采购方 → 招标编号 → 授标日期 → 范围摘要）、「这个中标方」（中标方 → 合同金额 + 币种）。提示放在输入框下（`aria-describedby`，不放进 label）：
  - 采购方：`先从候选里选（本组织招标项目和已有授标里用过的写法）；候选里没有，再照公告上的采购机构原文填。大小写、标点、开头的 The 不影响匹配，其余要和项目里的采购方一字不差，系统才能对上。`
  - 招标编号：`建议填写。同一采购方、同一中标方的不同招标靠编号区分，不填容易被当成疑似重复。`
  - 金额：`一条公告有几个中标方就录几条；金额填这个中标方自己的合同金额。公告只给总额或预估值时留空。`（占位 `例如 1,250,000.00`）
  - 范围摘要：`写一句能反复用的采购内容，不带年份、编号、地点（例如 Snow removal services）。大小写和标点不影响；同一采购方、同一句、同一币种的已确认记录满 3 条，才会算出可比价格。`
- 录入成功：写 `「{中标方}」：{结果那句}`（绿色、`role="status"` 常驻）；保留公告信息，只清空中标方与金额，焦点回到中标方（一条公告的下一个中标方）；重录时不清空。另有 `换一条公告（清空）`。出错：`role="alert"`，标出那一格（`aria-invalid`）并把焦点移过去；403 写 `你在本组织没有录入权限（需要成员及以上角色），请联系组织管理员。`；其余 `没有录入成功，请稍后再试。`，断网 `网络出错，请稍后再试。`。按钮 `录入` / `正在录入…`（提交期间禁用）。表单按组织换（切换组织不带上一组织填的内容）。
- 结果：`已录入，等组织管理员复核。`（新建）／`已录入；和已有的一条记录可能重复，等组织管理员裁决。`（疑似重复）／`已有同一条授标（招标编号与中标方相同），这条公告链接已挂到那条记录上。那条记录原有的内容和可信度不变（你这次填的没有写进去）；有出入请告诉组织管理员。`（按编号挂到既有）／`已有同一条授标（中标方、授标日期、金额都相同），这条公告链接已挂到那条记录上。那条记录原有的内容（含招标编号与采购方）和可信度不变（你这次填的没有写进去）；有出入请告诉组织管理员。`（按日期金额挂到既有）／`这条公告的这个中标方已经录过了（同一公告同一中标方只录一条；中了几个标段的请合成一条，金额合计或留空）。`（重录）
- 校验：`请填写采购方。`、`请填写中标方。`、`请填写 APC 公告链接。`、`APC 公告链接要以 https://purchasing.alberta.ca/ 开头，并指向具体的公告。`、`授标日期要写成 年-月-日，且在 1900 年到今天之间。`、`合同金额只填数字（可以带千分位逗号和 $），不能为负，最多两位小数。`、`币种只能是 CAD 或 USD。`、`{字段}太长了（最多 N 字）。`（链接超长也用这句：`APC 公告链接太长了（最多 2048 字）。`）；请求体太大 `请求太大`；组织不存在 `组织不存在`。
- 列表：人工录入的记录在中标方下面写 `人工录入 · APC 公告 ↗`（原生 `<a>`，新窗口打开，`rel="noopener noreferrer"`，`aria-label="在新窗口打开 APC 公告"`；不用 `next/link`、不预取、不嵌入）；招标编号下面显示范围摘要（一行，悬停看全文）。统计条原来的「AI 待确认 N」改为 `待确认（AI 提取 / 人工录入，不计入统计）N`（这一项本来就把待人工复核的记录算在里面），原来的「待复核（不计入统计）N」（只数疑似重复）改为 `疑似重复待裁决（不计入统计）N`。刚录入的那一行高亮并滚到它；被筛选条件挡住时写 `已录入，但被当前筛选条件挡住了，清空筛选可以看到。`
- 组织管理员提示改为：`你是组织管理员：「AI 提取·待确认」「待人工复核」（含人工录入）和「疑似重复」可以确认或撤回。人工录入的记录，确认前先点「人工录入 · APC 公告」打开原公告核对。填错的撤回后重录：项目结果回项目里重新标记，人工录入在上方表单重新录入。`；空状态对能录入的人多一句：`在 APC 上看到的 Alberta 授标，也可以用上方「录入 Alberta 授标（APC）」直接录入，经人工确认后计入。`

- 备选 A：结果写在列表顶部的通知栏。否决：通知栏离表单远，人看不到自己的录入结果。
- 备选 B：录完一条清空全部字段。否决：一条公告常有几个中标方，范围摘要要逐字相同才算得上可比价格，重打容易写得不一样。
- 备选 C：页面上「买家」统一改成「采购方」。不在本次：「买家」遍布这一页的既有统计与画像（「按买家采购规律」等），只改表单附近会更不一致；另立文案 change。

### D7：列表里只显示人工录入的 APC 链接

列表接口对列出的记录查来源：只取 `sourceType = "USER_ENTRY"` 且 `sourceKey` 以 `manual:apc:` 开头的，返回前按 D2 重新校验一次主机，按来源创建时间取第一条，作为 `manualApcUrl`。别的 USER_ENTRY 来源（项目结果回灌、项目里确认的对手）不显示。

- 备选：显示一条记录的全部来源。否决：本次只为复核人工录入；全部来源的展示是另一件事。

### D8：按「中标方 + 授标日期 + 金额」挂到既有时不跨不同的招标编号（Lucas 2026-11-20 GATE「收紧」）

`awards.ts` 的强匹配第二条路径（按编号没找到时退到中标方 + 授标日期 + 金额）里，候选记录与这一次都有招标编号、且规范化后不同（`isDistinctSolicitation`，与 P2-0c 疑似重复的例外同一个函数）时跳过它。跳过后走既有的疑似重复判断：同采购方同中标方、编号不同 → 按「不同招标编号不判疑似重复」正常新写；编号缺一方或只差写法 → 照旧挂上。主规格 `tender/award-records` 新增一条要求写明这一点。

- 备选 A：不改，规格照实写（开 PR 时的做法）。否决：Lucas 定「收紧」。
- 备选 B：第二条路径也要求采购方相同。否决：采购方写法常不一致（CanadaBuys 与人工录入），加了会让同一条授标挂不上、变成两条；GATE 只要求不跨不同的编号。
- 备选 C：只对人工录入收紧。否决：口径应对所有写入方一致，P2-0c 也是全局的。

## 八条硬纪律

1. 零 schema：遵守（写既有 `AwardRecord` / `AwardRecordSource` / `AuditLog`；不改 `prisma/`）。
2. 出站先审批：不涉及（没有任何出站）。
3. 禁止第三套队列：不涉及。
4. 脱敏：遵守（不收、不存联系方式；审计不记联系方式）。

## Risks / Trade-offs

- 采购方写法与项目里的不一致时，CHAIN-2 / CHAIN-3 对不上这条授标（按规整名找）；表单提示写明，不做模糊匹配（T3 纪律）。
- 待复核的人工录入记录不进统计、可比价格与 CHAIN-3 的中标者名单，要等组织管理员确认；表单说明写明这一点。
- 项目里有人按编号确认了同一条授标（授标历史面板带编号确认、或项目结果回灌），写入服务会把这条人工录入直接提升为人工确认，不经组织管理员（既有规则）；之后 CanadaBuys 观察到同一条时只挂来源、记录不升级。
- 录入的人可能填错：组织管理员复核时可撤回（既有入口，原因必填、留痕）。
- **按日期金额挂到既有**：已按 GATE 收紧（D8），两边编号都有且不同就不挂；编号缺一方时仍按中标方、日期、金额挂上，不看采购方（结果那句写明那条的内容不变）。这一改对所有写入方生效（CanadaBuys 观察、项目结果回灌、授标历史面板的确认）：以前会被挂到一起的两次不同编号的招标，现在各成一条。
- **招标编号区分大小写**（写入服务既有规则）：手打的 `ab-1` 与 CanadaBuys 的 `AB-1` 对不上；采购方写法也不同时会成为一条新记录。表单不替人改大小写（编号的规范写法未核对）；列入已知限制。
- 组织管理员录入后可以自己确认（没有职责分离）：与既有「项目里人工确认」一致，不另加限制。
