# Proposal：交付前检查清单由已确认的要求确定性生成

TASKFLOW：FLOW-H4b（Phase F 续）
来源：交接文档 §0.5c 第 2 项的后半（方案 §7 的 H4，断点 G7）；Lucas 2026-11-12「按照你的推荐开始吧」。前半（记「已提交」并留回执）是 FLOW-H4a（#446）。

## Why

「提交」页签上的「投标准备清单」是模型生成的：提示词只看项目概况、任务、询价、成员与文件名，不看招标要求，每一项的「已完成 / 有风险」也是模型猜的；打开项目页还会自动调一次模型。而招标分析已经把强制的提交类要求逐条抽出来、人也逐条确认过，这份清单却没有用到。

## What Changes

- 新增接口 `GET /api/projects/{id}/submission-checklist`：从当前这份分析里**已确认的、强制的、提交类的要求**逐条生成清单，每条带原文出处；另列还没确认的、当前判为不满足的强制要求（废标风险）、截标与提问截止时间、招标文件里写的提交方式 / 保证金 / 保险。
- 新增接口 `PUT /api/projects/{id}/submission-checklist/items/{key}`：把一条标为「备好了」「不适用」或改回「待办」，存进这条要求已有的交付物行。
- 让「提交」页签在新开关开启时显示这份清单，取代模型生成的那一份。
- 让模型生成清单的接口在新开关开启时不再调用模型（返回「已由确定性清单取代」），打开项目页也不再自动触发它。
- 新增开关 `TENDER_SUBMISSION_CHECKLIST_ENABLED`（可配组织名单），默认关；关闭时页面、接口与现在相同。

## 受影响的 Muse 意图

无。不改 `src/lib/muse-bridge/` 下任何文件。

## Out of scope

- 判断某一条「实际上备好了没有」：不做。系统只列出该备什么、记下人标的状态，不替人下结论。
- 把清单的完成情况变成提交的闸门（没备齐不让记「已提交」）：不做。
- 删除模型生成清单的代码与已存的清单：不做。开关关闭时照旧。
- 对话里的「投标废标风险检查」技能（另一处模型生成的清单）：不动。
- 上传某一条对应的文件、把文件关联到清单项：不做。
- 改分析时生成交付物的逻辑：不做。
- schema 变更、模型调用、定时任务：没有（反而少一次模型调用）。

## Capabilities

### New Capabilities

- `tender/submission-checklist`：交付前检查清单——由什么生成、分哪几组、每条的状态存在哪、谁能改、与模型生成的那份的关系。

### Modified Capabilities

无。
