# Design：修好阶段推进之后的自动任务（FIX-5）

## Context

- `src/lib/tender/stage-tasks.ts` 的 `onStageAdvancedTasks` 做两件事：把上一阶段的自动任务标为完成；按模板为新阶段建任务。唯一的调用方是 `advanceProjectStage`（`src/lib/tender/stage-transition.ts`），调用后不等结果，出错只打一行日志。
- 建任务用 `db.task.createMany`，每条数据带 `sortOrder`。`Task` 表没有这一列（`prisma/schema.prisma`），Prisma 每次都抛「Unknown argument sortOrder」。所以第一件事一直正常，第二件事从来没成功过。没有任何测试覆盖这个文件。
- 模板：项目分发 2 条、项目解读 3 条、供应商询价 2 条、供应商报价 3 条、项目提交 2 条（「准备投标文件」「提交投标」）。
- 进入「项目提交」阶段 = 写入提交时间、招投标状态变成已提交。也就是说模板在标交完之后才建「提交投标」。
- 走阶段推进的入口目前只有项目对话里的「阶段推进建议」卡片；FLOW-H4a（#446，待合并）的「记录提交」也走它，并且指明不建任务。分析完成写「项目解读」、询价发出写「供应商询价」这两处自动写入不经阶段推进，所以不触发任务。

## Goals / Non-Goals

**Goals**

- 阶段推进之后，新阶段的自动任务真的出现。
- 不在标交完之后建「提交投标」。

**Non-Goals（具体到文件）**

- 不改 `src/lib/tender/stage-transition.ts` 的推进规则。
- 不改 `prisma/schema.prisma`（不为排序加列）。
- 不改 `src/lib/tender-auto-analysis/worker.ts`、`src/lib/tender-rfq/execute.ts`（两处自动写入阶段时间的地方）。
- 不给老项目补建任务。

## Decisions

### D1 去掉 `sortOrder`，顺序用创建时间表达

删掉那一列的赋值。为了让同一批任务按模板顺序排，给每条的创建时间依次加 1 毫秒（任务列表按创建时间排）。

- 否决：给任务表加 `sortOrder` 列。零 schema；为了一个排序不值得。
- 否决：不管顺序。同一毫秒建的几条，顺序由数据库决定，每次可能不一样。

### D2 「准备投标文件」「提交投标」挪到供应商报价阶段，项目提交阶段不建任务

- 否决：原样保留。修好之后，每次把项目推进到「项目提交」（这时标已经交了）都会冒出一条三天后到期的「提交投标」。
- 否决：把这两条删掉。它们是交标之前确实要做的事；进入供应商报价阶段时建出来，进入项目提交时随「[供应商报价]」前缀一起被关掉，正好对上。
- 这是对模板的一处调整，写在 PR 最上面；不同意可以改回去，只是会带着上面那个毛病。

### D3 「提交投标」的到期日取截标时间

模板里它原来是「三天后」。挪到供应商报价阶段之后，离截标可能还有几周，也可能只剩一天；到期日写截标时间才有意义。没有截标时间、或已经过了，退回按天数算。

- 否决：一律按天数。任务到期日与真实的截标时间无关，会误导。
- 否决：别的任务也按截标时间倒推。那是在重新设计模板，不在这次范围内。

### D4 去重仍按「新阶段是否已有没完成的自动任务」

不改去重的口径。

- 否决：改用任务表的来源键做唯一约束。更严，但要动既有的唯一键用法（交接任务在用），而阶段推进本身已经不会重复执行。

## 与八条硬纪律的关系

1. **零 schema**：遵守。只是不再写那个不存在的列。
2. **出站先审批**：不涉及。
3. **禁止第三套队列**：遵守。仍在阶段推进之后同步执行，没有新的后台机制。
4. **脱敏**：不涉及。任务标题与说明是固定文字。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。固定模板，不调模型。
8. **测试注册**：新测试注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## 验证方式

- `npx tsx src/lib/tender/__tests__/stage-tasks.test.ts`（新，纯逻辑）：模板的内容与顺序；到期日的三种情形；任务数据里没有任务表不认识的列。
- `npx tsx src/lib/tender/__tests__/stage-tasks-db.isolated.test.ts`（新，隔离库）：逐个阶段真的建出来；关掉上一阶段的；不重复；只关不建；从阶段推进的入口走一遍。同一份测试在改动之前的代码上要失败（建不出来）。
- 变异核对；独立审查。
- 全量：`npm run test:ci`、`npm run typecheck`、`npm run lint:baseline`、`bash scripts/check-test-registry.sh`、`bash scripts/test-runtime-architecture.sh`、`openspec validate stage-tasks-create-fix --strict`。

## Risks / Trade-offs

- **合并之后行为立刻变**（没有开关）：之后每一次阶段推进都会给推进的人建 2–5 条任务。这是这些任务本来的设计，只是以前从没生效过；用的人会突然看到它们。
- **老项目没有**：已经在某个阶段的项目不会补建，要到下一次推进才有。
- **自动写入阶段时间的两处不建任务**：分析完成、询价发出不经阶段推进。所以实际会建任务的只有人在对话里确认推进的时候。等「阶段记录自动前进」那个 change 定。
- **按标题前缀识别自动任务**：人把自动任务改了名，它就不会被自动关掉；人自己建一条以「[阶段名]」开头的任务，会被当成自动任务关掉。既有做法，不改。

## Migration Plan

无数据迁移。回滚 = 回滚代码（回到建不出任务的状态）；已经建出来的任务留着。
