# Design

## Context

- 现有的相邻机制，都不拦投标流程里的任何一步（差距分析 §1.1、§3.2）：
  - Bid-fit 矩阵：人工标注，只是标签。
  - 供应商情报的强制要求闸（`src/lib/supplier-intel/mandatory-gate.ts`）与认证规则（`deterministic-match.ts`）：按「要求 × 候选」判定。认证规则里，范围为「整个供应商」的已核验证书即可通过——对「整机须有加拿大认可的电气认证」这种按型号的要求过宽。
  - 补遗变更候选：「接受」只记意图。
- 证据词表：企业记忆是三根正交的轴（性质、置信度、核验状态，`prisma/schema.prisma` 的 `MemoryClaim`）；Skill 用五值。差距分析 §3.1 定的做法是投影，不压扁存储。
- 已有的确定性「下一步」查表在 `src/lib/muse-bridge/next-step.ts`（10 条规则，只接在冻结的 Muse 通道上）。它回答「这个标现在最该做什么」；本次的阶段策略表回答「这一类事该不该不问就做」，两者不重叠。
- 硬纪律第 2 条（出站先审批）、第 7 条（下一步是查表，不让模型决定）、第 3 条（不新增调度器 / 队列）。架构守卫禁止 `src/lib` 文件基本名含 `plan`、`scheduler`、`engine` 等词。
- 第二轮开源调研（`docs/QINGYAN_TENDER_FLOW_OSS_SURVEY.md` §6.3）：研究代理里「不询问」的通行做法是每个工具一个静态权限加一个关掉澄清提问的开关。

## Goals / Non-Goals

**Goals:**

- 一份能回答「卡在哪」的阻断项清单，覆盖任务书验收项 A7、A21，并把 A16（过期）接进来。
- 一张阶段策略表，使只读阶段永不产生询问，只有对外动作停下。

**Non-Goals:**

- 不动 `src/lib/supplier-intel/**`（不改现有认证规则与强制要求闸）。
- 不动 `src/lib/muse-bridge/next-step.ts`、`src/lib/tender/workbench-state.ts`、`src/lib/bid-workflow/**`。
- 不动 `src/lib/workforce-runtime/**`、`src/lib/tender-workforce/**`、任何 `src/app/api/cron/**`。
- 不动 `prisma/schema.prisma`；不加 `src/app/**` 下任何路由或页面；不加环境变量与开关。

## Decisions

### D1：新建纯函数目录 `src/lib/tender-bid-readiness/`

文件：`evidence-status.ts`、`certification-gate.ts`、`staleness.ts`、`readiness.ts`、`stage-policy.ts`。基本名均不含守卫禁用词（所以叫 stage-policy，不叫 run-plan）。

- 被否决：把阶段策略放进 `workforce-runtime/`。那是运行时；策略表只回答该不该做，不执行，放进去会被当成新调度逻辑，也确实容易长成一个。
- 被否决：把认证闸写进 `supplier-intel/deterministic-match.ts`。那条规则已有测试钉着「供应商范围的证书可通过」的行为，改它是另一个 change 的事；本次另立更严的一条，只用于带认证闸的价格表行。

### D2：证据状态是投影，不是新存储值

投影函数的输入就是现有三轴加时效与「是否被反驳」；输出五值只用于显示与闸门。

- 被否决：给 `MemoryClaim` 加「指示性」「互相矛盾」两个存储值。要动数据库，而且会把正交的三轴压成一轴，丢信息。
- 被否决：把置信度（高 / 中 / 低）也算进投影。Skill 的五值里没有置信度的位置；置信度单独显示。

### D3：认证闸六个条件全是输入，本能力不核验真伪

「已核验」「发证机构在加拿大受认可」「覆盖整机」都是上游人工确认后的输入；缺省值是「未确认」，未确认即不通过。

- 被否决：内置一份受认可发证机构名录。名录会变，且「受认可」取决于具体标准与产品类别，写死在代码里迟早出错。
- 被否决：有证书号就算通过。任务书验收 A7 明确：部件上的 UL、CE、经销商页面、预留的认证费用都不算。

### D4：补遗失效按「行 + 版本」判断

每条结论带 `basedOnAddendum`（0 = 原始文件）与行号；影响该行的最新补遗号大于它即失效。不解析补遗正文。

- 被否决：任何新补遗使全部结论失效。18 行里补遗只动 3 行，全部重做是浪费，也会让人习惯性忽略「待复核」。
- 被否决：从补遗正文自动判断影响哪些行。那是抽取问题，输入由上游（分析结果或人工）给出。

### D5：可投标判定只有两个结果，提示单列

「不可投标」与「可提交 Owner 决定」。阻断项与提示分两张清单：含未核实的关税假设是阻断项（差距分析 §13 已定：未核实参数不得进入可投标判定）；含指示性价格只是提示——用平台标价去投是商业判断，由 Owner 决定。

- 被否决：三档（可投 / 有条件可投 / 不可投）。「有条件」会被当成可投；条件本身就是阻断项，列出来即可。
- 被否决：尺寸无法判断只作提示。供应商情报里「未知永不折算通过」是既定规则，这里保持一致。

### D6：阶段策略是「类别 + 来源状态 + 手头材料 → 决定」的查表

十三个阶段写成常量表。决定的取值是封闭的六个：执行、等材料、未接通、仅人工、停下等批准、已关闭——类型里就没有「询问」。

- 被否决：让模型按情况决定要不要问。这正是现在的问题，也违反硬纪律第 7 条。
- 被否决：做成带依赖关系的有向图并计算执行顺序。那是调度，属于运行时；本次只回答每个阶段该不该做。

### D7：覆盖只能收紧，不能放开要批准的阶段

组织覆盖只接受「关闭某阶段」。把要批准的阶段设为自动会被拒绝。

- 被否决：允许组织自行放开。硬纪律第 2 条没有组织级例外。

## 与八条硬纪律的关系

1. 零 schema：不涉及。不落库；证据状态是投影，不新增存储值。
2. 出站先审批：遵守，并用代码固化——供应商外联、政府资料申请、提交恒为「停下等批准」，覆盖不能放开（D7）。本能力自身没有任何对外动作。
3. 禁止第三套队列：遵守。阶段策略只回答该不该做，不调度、不排队、不运行；有源码断言守住不引用运行时与定时任务。
4. 脱敏：不涉及敏感字段。判定输出的是阻断项的类别与行号，不含金额。
5. 不爬登录页：遵守。取决于来源的阶段沿用 TI-3a 的连接状态，登录门户恒为按纪律禁用 → 阶段决定为已关闭。
6. 邮箱分离：不涉及。
7. 确定性优先：遵守。可投标判定与阶段决定都是查表，零模型调用。
8. 测试注册：新增 4 个测试文件，全部登记进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## Risks / Trade-offs

- [仓库里又多一个「该做什么」的表] 已有项目阶段、投标相位、工作台三步、Muse 的下一步查表 → 本次不新增流程状态（可投标是推导判定），阶段策略也不是进度模型；把它们收成一张 Web 上的指路表是 FLOW 方案 H1 的事，届时本次的阻断项就是那张表的输入。
- [认证闸比供应商情报现有规则严] 同一张供应商范围的证书，在供应商评估里通过、在这里不通过 → 这是有意的：两处回答的问题不同（「这家供应商有没有这类资质」对「这个型号的整机有没有证」）。报告里写明，接界面时两处并排显示时要讲清楚。
- [「受认可」「覆盖整机」靠人工输入] → 缺省即未确认、不通过；界面上要让人看到是谁在什么时候确认的（持久化那个 change）。
- [本次代码线上不可达] → 有意为之，先过 Owner Gate B。
