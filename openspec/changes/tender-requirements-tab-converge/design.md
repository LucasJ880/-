### 2. 73 与 54 为什么不同

- **只能是两次不同的分析，不可能是同一次分析的不同过滤。**
  - 同一次分析里，面板列表列全部要求，矩阵的任何计数都是它的子集：总数 ≤ 300，或者只算强制的。所以同一次分析里列表条数 ≥ 矩阵条数。
  - 54 < 73，因此面板那次与矩阵那次不是同一次。
- **54 条那次更新，且不在「等待审核 / 已批准」里**：如果它在，它就同时是两处的最新一条。
- **它有要求，说明已经过了落库那一步。**
  - 落库在一个事务里一次写完全部要求（`v2-persist-core.ts:130-146`）。
  - 一键分析在落库后还要跑后面几步，之后才终态化（`tender-workforce/tools.ts:1290` 的注释：落库后仍是 AGENT_ANALYZING）。
  - 所以它是「AI 数字员工分析中」（落库后、终态化前），或者「AI 分析未完成」（落库后失败）。
- **为什么两次会并存**：一键分析完成后不会把更早的待审结果标为已被替代。只有旧管线的重新分析会这样做（`enqueue-package.ts:487-500`）。
- 生产上怎么核对：附录 A、B。

### 6. 「未完成」能用什么判定

- 状态值与中文标签（`display-labels.ts:14-25`）：PENDING 等待分析、EXTRACTING 正在提取、ANALYZING 正在分析、REVIEW_REQUIRED 等待审核、APPROVED 已批准、FAILED 分析失败、SUPERSEDED 已由新分析替代、AGENT_ANALYZING AI 数字员工分析中、AGENT_FAILED AI 分析未完成。
- 这些状态都不算「已完成」：
  - FAILED 不一定是终态：旧管线失败时没到 5 次就写下次重试时间，到了才把 `nextAttemptAt` 置空（`worker.ts:44`、`:155-185`），cron 会再认领（`constants.ts:35-40`）。
  - AGENT_FAILED 是一键分析的收尾失败（`analysis-run-service.ts:419-450`）。FIX-20b 合并后它也不一定是终态：「从失败的这一步继续」把同一条记录改回「分析中」（`/home/user/wt/fix20/openspec/changes/tender-job-continue-from-failed/design.md:137`），已完成步骤的产出原样复用；第 9 步有 V2 分析的执行证据时只改状态（`tools.ts:1063-1073` → `analysis-run-service.ts:323-345`），否则走 V1 终态化整块换摘要（`tools.ts:1228`）。
  - AGENT_ANALYZING 在落库后、终态化前已经有要求。
- **一键分析一发起就有新记录**：第 1 步就新建一条「AI 数字员工分析中」（`analysis-run-service.ts:189-205`）；旧管线入队、文件处理完后的自动入队（`enqueue-package.ts:561-656`，开关开时）也一样新建。
- **分析中的那一次写标注不安全**：
  - 旧管线落库（`report.ts:400`、`v2-persist-core.ts:233-240`）与一键分析的 V1 终态化（`tools.ts:1228` → `analysis-run-service.ts:383-396`）都整块写 `summaryJson`；

- 「局限说明」`summaryJson.limitations` 只是给模型的文字，本次不用。

## Decisions

### D1 「本页的这次分析」= 该项目最新创建的一条，不分状态

口径与面板今天一样（`runs/route.ts:27-31`，项目 + 组织，按创建时间倒序取第一条）。

- 「已完成」= `REVIEW_REQUIRED` 或 `APPROVED`。
- 其余七种都是「未完成」，查表判定，不看要求条数、不看摘要字段。

被否决的备选：

- **两处都取「等待审核 / 已批准」里最新的一条**（即矩阵今天的口径）。
  - 面板的进度就看不到正在跑、或刚失败的那一次了，失败原因也没处说。
  - 「以下可能不全」这句话也无从谈起：那一份永远是完成的。
- **混合口径**（最新一条失败了就退回上一份完成的，网页「下一步」对旧管线 FAILED 是这样做的，`tender-next-step/service.ts:97-99`）。
  - 页面上又会出现「进度说的是 B，列表列的是 A」，正是这次要去掉的东西。
  - Evan 要的是口径定死。

### D2 面板一拿到最新一条就交给矩阵；插槽交一个对象

- 面板加一个插槽，位置在进度部分之后、收起的页签之前。
- 面板的 `runs?latest=1` 一返回最新一条，就渲染插槽，交给它一个对象：这次分析的 id、状态与「重新加载」。不等 `runs/[runId]` 详情加载完。
  - 详情加载中或加载失败时，面板照样挂一键分析卡片（FIX-18 的卡片回报照旧）、显示出错提示，矩阵照常显示。
  - 详情加载完后，状态改用详情里的那一个。
- 「招标要求」页签把矩阵放进这个插槽，把对象原样展开成矩阵卡片的属性。以后面板多交的字段（FIX-16 的 `incompleteNotes.matrixLine`，G6）不用改页签文件就能到卡片。
- 矩阵带 `runId` 读接口。面板每次重新加载（卡片完成、增量变更接受 / 忽略、陈述要点确认等），矩阵都拿到新的 id 与状态。
- 矩阵批准成功、收到「已有更新」的 409、或读接口说这一份已不是最新一条时，调用「重新加载」，面板与矩阵一起刷新。

被否决的备选：

- **两处各自按同一口径去取**：两次请求之间要是新建了一条分析（上传后自动入队、别人点了一键分析），页面上又是两次分析。
- **把取数提到页签里，再分给面板与矩阵**：面板的重新加载散在七八个动作里（`analysis-panel.tsx:299-319`、`:346-407`），要全部搬出来，改动大，也会碰到 FIX-18 刚接好的卡片回报。
- **等详情加载完再交给矩阵**：首屏变成「列表 → 详情（全量要求与来源）→ 矩阵」三段串行；详情失败时矩阵整张消失。
- **插槽只交三个固定参数**：FIX-16 要多交一句话时，还得改页签文件（G6 的 B）。

### D3 未完成的分析只读；写入接口用 409 拦；第二句按状态写

- 未完成时卡片不渲染任何写控件。顶部第一句是 Evan 原话「本次分析未完成，以下可能不全」，第二句按状态查表：

| 状态 | 第二句 |
|---|---|
| 等待分析、正在提取、正在分析、AI 数字员工分析中 | 分析完成后才能标注 |
| 分析失败，系统还会自动重试（`nextAttemptAt` 不为空） | 分析完成后才能标注 |
| AI 分析未完成 | 继续或重新分析完成后才能标注 |
| 分析失败，不会再自动重试；已由新分析替代 | 重新分析完成后才能标注 |

- 这次分析还没有要求时，矩阵照样显示（今天整张卡不显示，`bid-fit-matrix-card.tsx:164`），两句之后加「这次分析还没有摘出要求」。
- 矩阵读接口返回「是否还会自动重试」，判定是「状态为分析失败且 `nextAttemptAt` 不为空」。
- 写入接口在事务里锁住这次分析的记录行，重读状态；不是该项目最新一条或未完成时，返回 409，不改任何东西、不写审计：
  - 「这次分析未完成，完成后才能标注」；
  - 「页面上的分析已有更新，已为你重新加载」。卡片收到它就调用 D2 的「重新加载」。
- 「是不是最新一条」在锁里查一次。它与新建分析之间不加锁：锁住之后、提交之前有人新建了分析，这次写入仍落在原来那一份上，结果与「先写、后建」相同。
- 读接口返回这一份已不是最新一条时（面板停着、别人新建了分析），卡片同样调用一次「重新加载」，期间写一句「这次分析已不是最新的一份，正在重新加载」。
- 分析中只读是硬的：那时写进去的标注可能被整块覆盖（Context 6）。
- 终态失败（「AI 分析未完成」、不会再重试的「分析失败」）也只读（G1 已定 A）。

被否决的备选：

- **只在界面上藏，接口不拦**：旧页面、停着的标签页照样能写进去。
- **后三种状态都写「重新分析完成后才能标注」**（原稿）：旧管线还会自动重试的失败、FIX-20b 能继续的「AI 分析未完成」都会叫人白白重新分析一遍。
- **写入时锁项目行来判断最新**：要与发起分析拿同一把锁（`enqueue-package.ts:405-410` 锁 Project 行），每次标注都去挡发起分析；换来的只是上面那个与「先写后建」结果相同的窗口。

### D4 五态推出确认状态：写入时一并改审阅状态，审阅状态仍是询价单唯一的依据

确认状态不另存，就是 `reviewStatus`。矩阵写入时在同一个事务里同时改 `bidFitMatrix` 与 `reviewStatus`，对应关系是一张表（批准后各行按已定的 G12 A 写）：

| 分析状态 | 动作 | 作用于哪些行 | 写入后的五态 | 写入后的审阅状态 |
|---|---|---|---|---|
| 等待审核 | 选五态 X | 这一行，不论原来是待确认、已确认还是已驳回 | X | 已确认 |
| 等待审核 | 「这不是要求」 | 这一行 | 去掉 | 已驳回 |
| 等待审核 | 「未标…设为已有」「本组全部已有」 | 没有五态、也不是已驳回的行，一次最多 300 条 | 已有 | 已确认 |
| 等待审核 | 「采纳全部历史建议」 | 有候选、没有五态、不是已驳回的行 | 候选里的那项，带来源 | 已确认 |
| 等待审核 | 「把这 N 条一并确认」 | 有五态而待确认的行 | 不变 | 已确认 |
| 已批准 | 选五态 X | 已确认或待确认的行 | X | 不变 |
| 已批准 | 「未标…设为已有」「本组全部已有」「采纳全部历史建议」 | 没有五态、也不是已驳回的行 | 已有 / 候选那项 | 不变 |
| 已批准 | 已驳回的行上的任何写入、「这不是要求」、「一并确认」 | — | 拒绝 409 | 不变 |
| 未完成，或不是最新一条 | 任何写入 | — | 拒绝 409 | 不变 |
| 任何 | 请求体缺 `matrixVersion: 2` | — | 拒绝 409（D19） | 不变 |

- 写法：锁住这次分析的记录行 → 重读 `summaryJson` 与状态 → 校验（最新、已完成、行的范围）→ 只改 `bidFitMatrix` 里涉及的键 → 写回 → `updateMany` 改这几条要求的 `reviewStatus` → 提交 → 提交之后写审计（D12）。
  - 批量与采纳的「作用于哪些行」在锁里按重读到的标注与审阅状态重新筛：别人刚标成 No-Go 的行，批量「设为已有」不会盖掉。
  - 批准接口的条件更新也要更新这一行（`review.ts:88-101`），所以两者按实际先后串行。锁到时分析已批准，就按已批准几行处理。
- 合规记忆照旧只记五态（`bid-fit/route.ts:152-169`），事务外、失败不阻塞。「这不是要求」不记。
- 询价单、自动起草、提交清单、网页「下一步」、Muse 的 `rfq` 意图一个字不改，它们读的仍是 `reviewStatus`（Context 4）。
- **后果**：五态是「我方能不能做」，确认是「这是不是一条要求」。按 Evan「任一五态即视为确认」，No-Go、需 RFI、需 Partner、可开发的行都成为已确认；属于供应商侧类别的，按询价单既有口径（`build.ts:219-232`，规格 `rfq-requirement-selection`）都进询价单行项。G10 已定 A：询价单规则不改，No-Go 的行照收。

被否决的备选：

- **让询价单改读五态**：改了询价单取要求的口径（Evan：口径不变），五个读者都要跟着改。
- **读的时候由五态现算确认状态，库里不写**：`reviewStatus` 与页面会对不上，Context 4 表里的读者都看不到矩阵上的确认。

### D5 「这不是要求」= 已驳回 + 去掉五态，不是第六种五态；投标草稿不收已驳回的行

- 写法见 D4。
- 投标草稿取要求时加一个条件「审阅状态不是已驳回」（`tender-bid-draft/gather.ts:89-92`）；起草元信息的要求总数与已标条数也不算已驳回的（`bid-draft/route.ts:38-49`）。
  - 改动前：草稿不看审阅状态，选了「这不是要求」的行因为五态被去掉，在草稿合规表里成了 "To confirm"（`contract.ts:26-38` 的默认分支），与人的意思相反。
  - 也影响上线前在面板上驳回过的行：它们从此不在草稿里。这与供应商搜索、采购视图、报价表预填排除已驳回的做法一致（Context 4）。
- 「这不是要求」不撤回之前标注时写进组织合规记忆的立场：那条立场照旧会作为候选推到别的项目。撤回要改 `tender-compliance-memory/**`，登记为后续任务（tasks 7.1）。

被否决的备选：

- **在 `bidFitMatrix` 里存第六种取值**：
  - 投标草稿会把它当成一条有标注的要求（`gather.ts:113-114`，`contract.ts:38` 落到默认分支）；
  - 「已标几条」会把它算进去（`bid-draft/route.ts:49`）；
  - 合规记忆会把它当立场记下来，再推到别的项目；
  - 矩阵的五态计数、例外区也都要跟着改。
- **草稿照旧，只在 Risks 里写**：本次让「这不是要求」成为页面上唯一的驳回入口，草稿里留着 "To confirm" 的就是本次造成的错。

### D6 批准之后冻结确认状态，五态照常能标（G12 已定 A）

依据有两条：既有提示写明「批准后不能再确认」（`requirement-batch-confirm.ts:87`）；自动起草规定「批准招标分析即视为要求审核完成」（`openspec/specs/tender/rfq-auto-draft/spec.md`「起草条件」）。所以批准后：

- 已确认的行仍可在五态之间改，投标草稿批准后仍要读五态（`gather.ts:80-116`）；
- 待确认的行仍可标五态，审阅状态不变，行上写「批准前没确认，不进询价单」；
- 批量与采纳只填五态，确认框写「批准后的标注不改确认状态，没确认的不会进询价单」；
- 已驳回的行只读；不再提供「这不是要求」与「把这 N 条一并确认」。

为什么待确认的行仍可标五态：今天批准之后照样能给任何行标五态，投标草稿合规表靠它；「批准时还有 N 条没确认」是常态（`approveHintZh` 就是为此写的）。不让标，这些行在草稿里永远是 "To confirm"。批准后单条与批量都不改确认状态，所以不会出现「单条算确认、批量不算」的混淆（D9 否决的那种）。

被否决的备选：

- **批准后矩阵整张只读**：批准后改五态今天是可以的，投标草稿要用，去掉就是回退。
- **批准后待确认的行只读**（原稿的做法，即 G12 B）：对这些行就是上一条的回退。
- **批准后照样能确认**：与上面两条既有规格冲突，自动起草的「有几条没带上」也会对不上。

### D7 矩阵上的标注不触发自动起草的判定

- 矩阵只在分析等待审核时改审阅状态，这时的判定一定是 `RUN_NOT_APPROVED`（`auto-draft-pure.ts`，`quiet: true`），调用只是白跑一次查询。
- 批准后矩阵不再改审阅状态（D6）。
- 所以矩阵写入接口不调用 `maybeAutoDraftRfq` / `maybeAutoSupplierRun`，规格里写明（`rfq-auto-draft` MODIFIED）。

被否决：**照逐条确认接口那样每次都调一遍**。没有任何情形会起草，只多两次查询，也让人误以为标注会触发起草。

### D8 上线前的数据：不迁移，按显示规则对上，再给一个人点的「一并确认」（G11 已定 A）

今天两套状态互不相干，所以库里会有四种组合。每一行按下面的先后显示：

1. 已驳回 →「这不是要求」，不管它标过什么；
2. 有五态 → 该项；仍是待确认的，再加「待确认」（已批准的分析加「批准前没确认，不进询价单」）；
3. 已确认而没有五态（在旧列表上确认过）→「已确认（未标）」；
4. 其余 →「未标」。

- 分析等待审核、看页面的人有写权限、且有第 2 种「待确认」的行时，矩阵顶部写「已标的 N 条还没算确认」，并给「把这 N 条一并确认」。点后弹确认框，确认后只改这 N 条的审阅状态，留审计。
- 生产上有多少这样的行、按来源拆开各多少，看附录 C、F。

被否决的备选（都写进 G11）：

- **一次性脚本把「有五态的待确认」全改成已确认**（G11 C）：
  - 这些标注里有合规记忆打开页面时自动带入的（Context 3），从来不是人对这个项目的确认；
  - 人工标的那些，当时标五态也不等于确认，有的是顺手「全部设为已有」。
  - 批量改成已确认，会直接进询价单，正是 RFQ-AUTO-4 否决「一键全部确认」的理由（D9 的出处）。
- **只把人工标的（没有 `provenance.via = "memory"`）改成已确认**（G11 B）：合规记忆那一半的理由没了，人工那一半的理由还在。
- **不给「一并确认」，让人逐行重选**：下拉框选同一项不触发改动，人得先改成别的再改回来，很别扭。

### D9 批量标注与合规记忆（G2 已定做法 A）

「标注即确认」之后，矩阵上原来只填五态的三个批量按钮会变成「批量确认」。这推翻了 RFQ-AUTO-4 的既有决定，出处四处：

- 归档 design `openspec/changes/archive/2026-11-11-requirement-review-batch-confirm/design.md:31-41`（D1 否决「一个『全部确认』按钮」：「一次点击就把模型抽出来的全部要求变成『人确认过』，等于取消了审核」）；
- 主规格 `openspec/specs/tender/requirement-review-batch-confirm/spec.md`「勾选后批量确认」：「系统 SHALL NOT 提供不经过勾选就确认全部要求的操作，SHALL NOT 提供批量驳回」；
- TASKFLOW `docs/QINGYAN_MUSE_BRIDGE_TASKFLOW.md:258` 的 RFQ-AUTO-4 一行：「没有一键全部确认，没有批量驳回」；
- 拍板人：Lucas 2026-11-11（归档 proposal「其他按照你推荐的做」）。

做法（已定 A）：

- 三个按钮保留，都先弹确认框，写明条数与「这些要求会算作已确认，属于供应商侧的会进询价单」。三个按钮是「未标 N 条全部设为已有」（今天已有确认框，`bid-fit-matrix-card.tsx:349-355`）、「本组全部已有」（今天没有）、「采纳全部历史建议」。逐字一致的合规记忆不再自动带入，与相似的候选一起由人点「采纳全部历史建议（N）」带入。批量「这不是要求」不提供，保留 RFQ-AUTO-4 的「不批量驳回」。
  - 理由：Evan 定的是「标注任一五态即视为确认」，批量标注本来就是人做的标注。
  - 理由：矩阵可用性批次的实测是「条款基本都是普通合规，不需逐条看」（`bid-fit-matrix-card.tsx:5`），批量是这张卡存在的原因。
  - 自动带入是没人操作的写入，标注即确认之后它就成了系统替人确认，必须停。
后果（G2 写全）：

- 矩阵上没有回「待确认」的路。批量误确认只能逐条改成「这不是要求」（意思又变成驳回）或重新分析。
- 「采纳全部历史建议」含相似（fuzzy）候选：凭别的项目里相似条款的立场，一次确认这个项目的若干要求，可直接进询价单。
- 等待审核时确认的行立刻能用于页面上的「问供应商要价」（`web-next-step.ts:216`），不必等批准。
- 主规格那两句 SHALL NOT 随「勾选后批量确认」一起移除；「不提供不经勾选就确认全部」换成「带确认框的批量标注」，「不提供批量驳回」在新能力里重写为「不提供批量『这不是要求』」。

被否决的备选：

- **批量按钮只填五态、不算确认**：等待审核时，同一个五态单条选算确认、批量选不算，人分不清，询价单也说不清为什么少了几条。
- **去掉全局的「未标 N 条全部设为已有」，只留按组的「本组全部已有」与采纳**（G2 的 C）：人至少要按组看一眼，但多点几下；其余后果与 A 相同，换不来更少的误确认。

### D10 「批准分析」移到矩阵顶部

- 位置：矩阵标题行下方、计数行旁边，只在分析等待审核、是最新一条、且 `canManage` 时显示。
- 请求不变：同一个接口、同样的请求体 `{ confirmAllRequirements: false }`。服务端的权限与条件不变（写权限、仅等待审核）。
- 旁边是 `approveHintZh(待确认条数)`；待确认条数按这次分析的全部要求算（D11）。
- 批准响应里的 `rfqAutoDraft` 显示在矩阵顶部，写法与今天面板上的那块相同（`analysis-panel.tsx:620-644` 搬过来）；然后调用 D2 的「重新加载」。
- 唯一可见的变化：没有写权限的人不再看到一个点了会 403 的按钮。

被否决的备选：

- **面板与矩阵两处都放**：两个「批准」入口，Evan 要的是「移到」。
- **照旧对所有人显示**：沿用了一个点了必 403 的按钮，没有好处。

### D11 来源、展开与条数

- 矩阵读接口一并取每条要求的来源记录与这次分析的文件名，序列化沿用 `serializeSourceRef`（`serializers.ts:51-97`）。点「来源」用既有的 `SourceSnippetDialog`，写法与旧列表一致。没有来源记录的写「来源未记录」，不可点。
- 每一行可以展开，展开后显示译文全文与原文。读接口返回两者全文，不再截到 200 字（`bid-fit/route.ts:81`）；行上收起时仍只显示译文前 200 字。
- 去掉读接口的 300 条上限，返回这次分析的全部要求。
  - 改动前：面板列表不限条数（`runs/[runId]/route.ts:46-49`），删掉列表后矩阵是唯一能确认的地方；300 条以后的要求再也确认不了、驳回不了、进不了询价单。

### D14 自动补翻的触发点：矩阵读接口，交给「响应发出后执行」

- 触发点在矩阵读接口 `GET …/bid-fit` 里，按以下顺序：
  1. 算出这次分析的中文化状态（D16）。只有这一份是该项目最新的一条时才可能是「该补」。
  2. 是「该补」时，把一件事交给「响应发出后执行」：开始频控（D15）→ 翻译 → 合并写回（D17）。
  3. 交出去成功，响应里的中文化状态写「自动补翻中」；交出去失败（抛错），按没有补翻处理，什么都没占用。
- 「响应发出后执行」是读接口的一个依赖：生产上是 Next.js 的 `after()`；隔离库测试换成测试自己收集、自己等待的执行（Context 7：`after()` 在请求作用域外会抛错）。
- 开始频控放在交出去的那件事里做，不在响应之前做：两个读请求都会回「自动补翻中」，交出去的两件事里只有一件能开始，另一件什么都不做；交出去失败也不会白占一次次数。
- 补翻调用与手动接口抽成同一个函数（`zh-backfill.ts`），只是被两个入口调用：取目标 → `translateAnalysisZh(…, { timeoutMs })`（预算见 D18）→ 合并写回。
- 路由文件加 `export const maxDuration = 120`，与手动补翻接口相同。
- 「有没有英文」看这次分析的要求译文、事实中文与关键事实文字，判定函数与卡片、翻译服务同一个（`requirement-lang.ts:9`）。

为什么不算新队列、新调度（硬纪律第 3 条）：

- 不建表、不加模型字段，不加 cron 条目，不扫描别的项目或别的分析。
- 只有有人打开**这个项目**的「招标要求」页签时才可能发生，做的事限定在**这一次分析**（该项目最新的一条）。
- 补翻跑在这次请求自己的生命周期里（`after()` 受同一个 `maxDuration` 约束）。
- 没有 worker 名单、没有持有者、没有续期、没有心跳、没有回收器；函数中途被杀，不会有任何东西去接手。下次有人打开页面时按次数（D15）重新判定，次数用完就停。
- 唯一的状态是这次分析摘要 JSON 里的「最近一次开始补翻的时间」与次数。手动补翻接口今天就把频控戳 `bidFitTranslateAt` 写在同一处，性质相同。G9 已定 A：它不算第 3 条禁止的租约。

被否决的备选：

- **挂进既有的 `/api/cron/tender-auto-analysis`，每个 tick 找还有英文的分析补翻**：
  - 那是一个「找活干」的扫描，就是第 3 条禁止的东西换了个名字；
  - 「CJK 占比 < 15%」写不成 SQL，每个 tick 要把很多分析的全文读出来算；
  - 旧管线 cron 还受它自己的开关约束。
- **加进一键分析的计划（第 9 步之后加一步）或终态化**：
  - 改了 Job 计划与运行时面（runtime-architecture 基线）；
  - 只覆盖一键分析，旧管线还要另挂；
  - 落库前那一次就是在这条链上被截止时间挤掉的。
- **卡片打开时自动调用手动补翻接口**：
  - 只有有写权限的人能触发，只读成员会一直看到英文；
  - 要求标签页开着 100 秒，两个标签页要靠客户端自己防重。

### D15 防重与次数：开始时间与次数写在这次分析的摘要里，锁行判定

`summaryJson.zhBackfill = { startedAt, startedKind, autoAttempts, autoLastTranslated, last: { at, kind, translated, failed } }`。`startedKind` 与 `last.kind` 取 `auto` / `manual`。不记是谁、不记哪个进程。

- **开始**（自动与手动共用）：在事务里锁住这次分析的记录行，重读摘要，然后判定：
  - 「有补翻在进行」=`startedAt` 不早于 150 秒前，且 `last` 为空或 `last.at` 早于 `startedAt` → 不开始（自动：这次不补；手动：409「正在自动翻译，请稍候」）；
  - 自动开始时，还要满足「还有次数」：`autoAttempts = 0`，或 `autoAttempts = 1` 且 `autoLastTranslated ≥ 1`；
  - 否则写 `startedAt = now`、`startedKind`；自动的 `autoAttempts + 1`，`autoLastTranslated` 置空；提交。
- **结束**：在写回那个事务里写 `last = { at: now, kind, translated, failed }`；自动的写 `autoLastTranslated = translated`；手动的照旧写 `bidFitTranslateAt`。
- **中断**：`startedAt` 早于 150 秒前、而 `last.at` 早于它（或 `last` 为空）的，是中断的那一次。它已计入次数，`autoLastTranslated` 为空，按「没有进展」算：中断的第 1 次之后不发第 2 次，直接到兜底按钮。
- **150 秒**：大于 `maxDuration` 120 秒。
- **上限 2 次的理由**：每次最多 400 条、预算不超过 100 秒。实测每批 50 条 15–25 秒（`requirement-translate.ts:34-38`），100 秒约译 200–300 条，2 次覆盖 400 条。第 1 次一条也没译成，多半是模型或账户的问题，再试也一样，所以不发第 2 次。G4 已定 A：2 次。

被否决的备选：

- **翻译期间一直持有 PostgreSQL 锁**：把一个连接占 100 秒、跨模型调用，FIX-18 D4 也否决了长时间持锁的做法（`trigger-service.ts:229` 那 20 秒的启动事务都不让锁 Project 行）。
- **只用既有的 60 秒频控戳**：戳是翻完才写的（Context 7），挡不住翻译期间的第二次；它也没有次数。
- **记下持有者（`runningBy`）**（原稿）：判定用不到它；有了持有者、到期回收，就是 FIX-18 D4 否决的那种（「新建锁表或租约。违反硬纪律 1、3。」）。
- **中断按「有进展」算、再给一次**：中断多半是平台把函数停了（部署、超时），再来一次多半一样；兜底按钮还在。

### D16 中文化状态与兜底按钮

矩阵读接口返回 `zh: { state, englishCount, attempt }`，`state` 由纯函数查表：

| 条件 | `state` | 卡片 |
|---|---|---|
| 分析未完成，或不是最新一条，或没有英文 | `none` | 什么都不显示 |
| 有英文，补翻正在进行，或这次刚交出去 | `auto` | 自动的写「正在自动翻译成中文…」，手动的写「正在翻译成中文…」；每 15 秒重读 |
| 要求译文里有英文、没有在进行、自动次数用完 | `fallback` | 有写权限：「翻译成中文」按钮；没有：「有 N 条要求还是英文，自动翻译没有译完，请项目负责人点「翻译成中文」」 |
| 只有事实或关键事实还是英文、自动次数用完 | `none` | 什么都不显示（矩阵不显示事实；手动接口仍可调用） |

- `englishCount` 是要求译文里还是英文的条数，由服务端对这次分析的全部要求算，不再只算卡片当前可见的行（今天是 `bid-fit-matrix-card.tsx:120-123`）。触发自动补翻看要求、事实、关键事实三样。
- `attempt` 是这次补翻是第几次自动补翻（手动时为 0）。卡片按它计重读次数：同一个 `attempt` 最多重读 12 次（3 分钟）；`attempt` 变了重新计；12 次用完停下，写「自动翻译还没完成，稍后刷新页面查看」。
- 手动按钮的接口、60 秒频控、返回字段都不变。
- 已知限制：只有编号、标准号的要求（Context 7）永远判为英文，补完两次后兜底按钮会一直在，点了也译不成。报告里列出附录 D 查到的条数。

被否决的备选：

- **一直显示按钮**：Evan 要的是兜底。
- **重读次数一次计满 12 次、不分第几次**（原稿）：第 1 次约 100 秒后再自动发第 2 次，两次合计可超过 3 分钟，卡片会停在「正在自动翻译成中文…」不再刷新。

### D18 时间预算从请求开始算

- 补翻预算 = min(100 秒, 请求开始时刻 + 105 秒 − 现在)。「请求开始时刻」在项目级守卫检查通过之后紧接着记下（守卫必须是第一步，D21），交给补翻；手动接口同样。守卫本身的几十毫秒落在 15 秒余量里。
- 留出的 15 秒给写回：最多 400 条要求、400 条事实的按行条件更新，加一次摘要写回，一个事务。
- 剩余不足 8 秒时中文化服务一批都不发（`requirement-translate.ts:98-102`），所以预算算出来很小时这次补翻译成 0 条，按「没有进展」记。

被否决：**照旧从翻译开始时算 100 秒**（原稿）：读接口在交出去之前要取全部要求、来源、事实与合规记忆，冷启动时再加几秒；100 秒翻译加写回会顶到 120 秒，被平台停掉时整次写回丢失，还白占一次次数。

### D19 旧页面的写入（部署过渡）

- 矩阵写入接口要求请求体带 `matrixVersion: 2`；缺了就返回 409「页面版本过旧，请刷新页面后再标注」，不写任何东西、不写审计。
- `action: "apply-memory"` 不再接受 `mode: "exact"`（旧卡片打开页面时自动带入用的就是它，`bid-fit-matrix-card.tsx:155-162`）。
- 原因：Next.js 客户端导航不换已加载的脚本，部署后没刷新的页面还跑着旧卡片。旧卡片挂载时自动调 `apply-memory`、批量按钮的确认框写着「已标条目不受影响」，新服务端会把这些写入都算成确认，就成了「没人操作时写标注」。

被否决的备选：

- **只拒绝 `mode: "exact"`**：旧卡片的单条与批量标注仍会被算成确认，而它的确认框没告诉人这一点。
- **不处理**：部署那几天会有无人操作的确认进询价单。

## Risks / Trade-offs

- **[合并后 12-3 这类项目上，原来那份待审分析的 73 条在页面上看不到了]**：最新一条是「AI 分析未完成」时，矩阵显示它的 54 条并只读。这正是 Evan 要的「同一个 run」，代价是要继续或重新分析才能再标。报告里列出附录 E 查到的受影响项目。
- **[任何一次新分析在跑，整张矩阵只读]**：一键分析第 1 步就新建记录，旧管线入队、文件处理完的自动入队也一样（Context 6）。从发起到收尾（FIX-12 之后一次可达十几分钟）矩阵显示新的一条（多半是「这次分析还没有摘出要求」），同事正在标的上一份拿到 409 后自动重新加载，也标不了、批不了。询价、草稿这段时间仍用上一份（G5）。FIX-18 的 G1 按推荐定为 B，开了一键分析的组织上传后不再自动发起；没开一键分析、又开着自动入队的组织，每次上传仍有这样一段。
- **[打开旧项目也会触发补翻]**：上线前就有英文、又是该项目最新一条的旧分析，第一次被打开时会自动补翻，最多 2 次。花费有上限，且只在有人打开时发生。
- **[页面加载变重]**：矩阵读接口返回全部要求的译文全文、原文与来源，再加事实译文用于判定英文；要求多的分析（附录 I）一次返回几百条全文。
- **[停掉合规记忆的自动带入]**：习惯了「打开就填好」的人要多点一下「采纳全部历史建议」，换来的是系统不再替人确认。
- **[No-Go 的行也进询价单]**：按 G10 A，选 No-Go 就是确认，供应商侧的会作为行项发出。
- **[只有编号的要求永远算英文]**：兜底按钮可能一直在（D16）。
- **[摘要 JSON 的其它写入方仍会整块写回]**：`tender-benchmark/route.ts:158-170`、`reply-resolution.ts:206-222` 都是先重读、紧接着写，窗口很短，但没有锁。本次之后被盖掉的代价更大：盖掉 `bidFitMatrix` 会让页面显示「已确认（未标）」，盖掉 `zhBackfill` 会多一次自动补翻。不在本次，登记为后续任务（tasks 7.1）。
- **[询价、自动起草、提交清单、投标草稿的口径]**：最新一条未完成时，它们仍用更早完成的那份（G5）。页面上已不能再改那份，它们说的与页面会不一致，直到继续或重新分析完成。

       count(*) FILTER (WHERE "reviewStatus" = 'AI_EXTRACTED' AND has_fit AND supplier_facing AND NOT coalesce(via_memory, false)) AS human_marked_pending_supplier,
       count(*) FILTER (WHERE "reviewStatus" = 'AI_EXTRACTED' AND has_fit AND supplier_facing AND coalesce(via_memory, false))     AS memory_marked_pending_supplier,
       count(*) FILTER (WHERE "reviewStatus" = 'REJECTED' AND has_fit)                                                  AS rejected_with_fit,
       count(*) FILTER (WHERE "reviewStatus" = 'CONFIRMED' AND NOT has_fit)                                             AS confirmed_without_fit
FROM rows
GROUP BY 1, 2
ORDER BY 3 DESC;

-- G. 全库：页面分析上由合规记忆带入的五态条数（停掉自动带入的影响面）
WITH latest AS (
  SELECT DISTINCT ON ("projectId") "projectId", "id", "summaryJson"
  FROM "TenderAnalysisRun"
  ORDER BY "projectId", "createdAt" DESC
)
SELECT l."projectId",
       count(*) FILTER (WHERE m.value->'provenance'->>'via' = 'memory') AS memory_marks,
       count(*) FILTER (WHERE m.value->'provenance'->>'kind' = 'exact') AS exact_marks,
       count(*)                                                         AS all_marks
FROM latest l,
     jsonb_each(CASE WHEN jsonb_typeof(l."summaryJson"->'bidFitMatrix') = 'object'
                     THEN l."summaryJson"->'bidFitMatrix' ELSE '{}'::jsonb END) m
GROUP BY 1
HAVING count(*) FILTER (WHERE m.value->'provenance'->>'via' = 'memory') > 0
ORDER BY 2 DESC;

-- H. 全库：已批准分析里待确认的行（G12：A 让它们能标五态，B 让它们只读）
SELECT r."projectId", r."id",
       count(*) FILTER (WHERE q."reviewStatus" = 'AI_EXTRACTED')                                                     AS pending,
       count(*) FILTER (WHERE q."reviewStatus" = 'AI_EXTRACTED' AND (r."summaryJson"->'bidFitMatrix'->q."id") IS NULL) AS pending_unmarked
FROM "TenderAnalysisRun" r
JOIN "TenderExtractedRequirement" q ON q."analysisRunId" = r."id"
WHERE r."status" = 'APPROVED'
GROUP BY 1, 2
HAVING count(*) FILTER (WHERE q."reviewStatus" = 'AI_EXTRACTED') > 0
ORDER BY 3 DESC;

-- I. 全库：要求超过 300 条的分析（今天矩阵只列前 300 条）
SELECT q."analysisRunId", r."projectId", r."status", count(*) AS req_total
FROM "TenderExtractedRequirement" q
JOIN "TenderAnalysisRun" r ON r."id" = q."analysisRunId"
GROUP BY 1, 2, 3
HAVING count(*) > 300
ORDER BY 4 DESC;
