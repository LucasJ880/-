## Why

同一页有两处要求列表，读的不是同一次分析：投标合规矩阵只取「等待审核 / 已批准」里最新的一条（`bid-fit/route.ts:23-29`），分析面板取最新的一条、不分状态（`tender-analysis/runs/route.ts:27-31`），于是 12-3 上较新的那份（54 条，按代码推断是「AI 分析未完成」，生产核对见 design 附录 A、B）和较早的待审或已批准那份（73 条）同时出现、各自能确认。中文化在落库前被截止时间跳过时什么也不记（`v2-resumable.ts:356-380`），只能靠人点「翻译成中文」补。

## 需求原文（Evan 2026-11-22）

1. 要求只在投标合规矩阵一处显示。「招标文件自动分析」只留进度（状态、文件纳入情况、失败原因），不再列要求明细。
2. 矩阵承接列表的动作：每行有「来源」；标注任一五态即视为确认该要求；加「这不是要求」承接驳回；「批准分析」移到矩阵顶部。询价单只取已确认要求的口径不变，design 里写清确认状态怎么从五态推出。
3. 两处读同一个 run，口径在 design 里定死；分析未完成时矩阵要写明「本次分析未完成，以下可能不全」。
4. 中文自动出：分析落库前的中文化若被截止时间或错误跳过，之后自动补翻，不需要人点；「翻译成中文」按钮只在自动补翻失败后作为兜底出现。自动补翻是在既有补翻调用上新增一个触发点，Evan 已同意，按硬纪律第 7 条在四件套里登记。
5. 风险、澄清问题、中文分析、来源几个页签保留，折叠放在矩阵下方。

与「分析入口只留一个按钮」（FIX-18）都改这个页面，先后顺序见 design。

## What Changes

**同一次分析（需求 3）**

- 改矩阵取哪次分析：与分析面板同一口径，取该项目最新创建的一条分析记录，不分来源与状态。面板只加载一次，把这一条的 id 与状态交给矩阵；矩阵接口 `GET …/bid-fit` 多收一个 `runId`。
- 定死「已完成」：状态为等待审核或已批准；其余七种状态（等待分析、正在提取、正在分析、AI 数字员工分析中、分析失败、AI 分析未完成、已由新分析替代）为「未完成」。
- 写明未完成：分析未完成时，矩阵顶部写「本次分析未完成，以下可能不全」，再写「分析完成后才能标注」（还在跑的）或「重新分析完成后才能标注」（失败或已被替代的）；这次分析还没有要求时，矩阵照样显示这两句，再加「这次分析还没有摘出要求」。
- 锁住未完成的分析：矩阵上不出现任何写控件；写入接口对「不是最新一条」或「最新一条未完成」的分析返回 409，不改任何东西。

**要求只在矩阵一处（需求 1、5）**

- 去掉分析面板里的要求列表：`Requirement` / 「全部条款」页签、勾选框、逐条确认 / 驳回、批量确认，以及面板上的「批准分析」与它旁边的提示。面板只留进度：一键分析卡片、状态、文件纳入情况（FIX-13 的覆盖清单原样）、增量变更待确认、出错提示。
- 把「风险」「澄清问题」「中文分析」「来源」四个页签收进矩阵下方一块默认收起的分区；分析带「项目解读」时是「项目解读」「风险与缺口」「澄清 / RFI」「来源」。「关键要求」页签也不在这里出现（留给 GATE 第 3 条），「项目解读」里指向关键要求的两个按钮改为滚到矩阵。
- 调整「招标要求」页签的排列：进度条 → 分析面板的进度部分 → 投标合规矩阵 → 收起的四个页签 → 正式澄清（RFI）。

**矩阵承接列表的动作（需求 2）**

- 给每一行加「来源」：点开是文件名、页码或单元标签与原文摘录，与原来列表里的「来源」相同；没有来源记录的行写「来源未记录」。
- 让五态标注即确认：分析等待审核时，选五态任一项，同一次写入里把这条要求的审阅状态改为「已确认」。
- 加「这不是要求」：选它把审阅状态改为「已驳回」，并去掉这一行的五态标注；已驳回的行改选五态，回到「已确认」。
- 冻结批准后的确认状态：分析批准后，已确认的行仍可在五态之间改，不改审阅状态；待确认与已驳回的行只读。
- 对齐上线前的数据：不改库里已有的记录，按显示规则对上。标过五态、仍待确认的行显示该项并加「待确认」；矩阵顶部给「已标的 N 条还没算确认」与「把这 N 条一并确认」。
- 给批量标注加确认框：「未标 N 条全部设为已有」「本组全部已有」「采纳全部历史建议（N）」三个按钮都先弹确认框，写明这些要求会算作已确认。
- 停掉合规记忆的自动带入：逐字一致的历史确认不再在打开页面时自动写进矩阵，改为与相似的候选一起由「采纳全部历史建议（N）」带入（留给 GATE 第 2 条）。
- 把「批准分析」移到矩阵顶部：调用同一个批准接口，权限与可批准的条件不变；只对有项目写权限的人显示。旁边是原来那句「还有 N 条要求没有确认……」，批准后自动起草询价的结果也显示在矩阵顶部。
- 显示审阅计数：矩阵顶部写「已确认 · 待确认 · 已驳回」各几条（原来在列表上方）。
- 给改了审阅状态的矩阵写入加一条审计。
- 给矩阵写入接口 `POST …/bid-fit` 增加取值 `fit: "NOT_A_REQUIREMENT"` 与 `action: "confirm-marked"`。
- 让矩阵列出这次分析的全部要求；超过 300 条时写明只列出前 300 条。

**中文自动补翻（需求 4）**

- 加自动补翻的触发点，挂在矩阵读接口上：这次分析已完成、还有英文、自动补翻还有次数、没有补翻在进行时，读接口先返回，返回之后在同一个请求里补翻一次。
  - 补翻用的就是「翻译成中文」那个调用：同一提示词与版本、同样分批、总预算 100 秒。
  - 不新增调用类型，不新增定时任务、队列或扫描。
- 限次数：每次分析最多自动补翻 2 次，第 2 次只在第 1 次至少译成 1 条时发生；用完不再自动重试。
- 防止同时补翻两份：同一次分析同时只有一个补翻（自动或手动），认领记录写在这次分析既有的摘要 JSON 里。
- 改「翻译成中文」按钮的出现条件：只在自动补翻次数用完、仍有英文、没有补翻在进行时出现，并且只给有写权限的人。
- 显示补翻进度：自动补翻进行中，矩阵写「正在自动翻译成中文…」，每 15 秒重读一次，最多 12 次。
- 修补既有的写回覆盖：手动补翻接口原来读出摘要 JSON、翻译最长 100 秒、再整块写回（`bid-fit/translate/route.ts:38`、`:76-87`），期间别人标的五态会被盖掉。现在补翻写回与矩阵标注都改为「锁这次分析的记录行 → 重读 → 只改自己的键」。
- 让手动补翻接口翻矩阵这时显示的那次分析；它未完成时返回 409，不再改去翻更早的一份。

## 与八条硬纪律的关系（摘要，逐条见 design）

- 第 1 条：零 schema。补翻记录与标注都落在 `TenderAnalysisRun.summaryJson`。这是矩阵标注 `bidFitMatrix` 与补翻频控戳 `bidFitTranslateAt` 已在用的同一处。审计进 AuditLog。
- 第 3 条：自动补翻只挂在矩阵的读接口上，在同一个请求返回之后做完。不建表，不加定时任务、扫描、回收或重试循环；中途断了不会有人接手，下次有人打开页面时再按次数判定。
- 第 7 条（例外，Evan 2026-11-22 同意）：在既有补翻调用上新增一个触发点，不新增调用类型。
  - 用的是同一个中文化服务、同一提示词 `tender-requirement-translate` v1、同样 50 条一批、总预算 100 秒。
  - 每次分析自动补翻最多 2 次，第 2 次只在第 1 次有进展时发生，之后不再自动重试；兜底按钮仍有 60 秒频控。
  - 五态推出确认状态是查表，不调模型。
