# Design：招标分析的降级结果用白话说清楚

## Context

动机见 proposal.md「Why」。来源：FIX-12 报告 §7 第 2 条、#540 合并前第二轮独立审计的「上线安全」维度（2026-11-21）、FIX-13 的走查。下面每一条现状都由本 change 的作者在 main `91d928e4` 上读代码核对过（带 `CALL_DEADLINE_EXCEEDED` 的部分在 #540 的分支上）。

1. 没读完的页面段落只写进局限说明的一句话：`${n}/${m} 个窗口 LLM 抽取失败（〈错误码〉），对应页面内容未纳入结果。`（`src/lib/tender-understanding/analyzer.ts:290–297`）。这句话带英文错误码、说「窗口」，而且不说是哪几页。
2. 局限说明存进分析摘要（`src/lib/tender-auto-analysis/v2-map.ts:322`、`:383`），但 `src/app` 与 `src/components` 里没有任何地方读它（全仓搜索 `limitations` 无结果）；它唯一的去处是综合解读的模型提示——而综合解读没生成时恰好没有。
3. 综合解读两次都没完成时，分析照常进入「等待审核」；通知文案是「可以开始确认招标要求」（`src/lib/tender-auto-analysis/alerts.ts:163–165`），Muse 消息是「〈项目〉分析完成」（`src/lib/muse-bridge/events-pure.ts:62`）。
4. 复核没跑完时写的是 `QA reviewer 调用失败（〈错误码〉），结果未经二次审校`（`src/lib/tender-analyst/synthesize.ts:163`），界面显示的横幅却是「部分结论未通过 AI 质检，需人工重点复核」（`src/components/tender-analysis/analyst-synthesis-view.tsx:573–575`）——与真的没通过分不开。
5. 澄清检查被截止后记为未解决，照样生成澄清问题，没有注明（#540 分支 `v2-resumable.ts:249–258`）。
6. 覆盖清单的说明（`coverage.note`，如「2 个可分析文件尚未纳入本次分析」）情报页显示了（`src/components/bid-workflow/project-intel-sections.tsx:425`），分析面板没有显示；解析失败的说明拼出来是「N 个文件文件解析失败」。

**没有核对到底的**：一键分析的最终结果卡片自己生成的局限说明（第二轮审计提到它在没有内容时写「分析范围以当前已上传的投标文件包为准」）；导出文档是否会间接带出模型对局限说明的转述。前者列为 Out of scope，后者实现时核对并写进报告。

## Goals / Non-Goals

**Goals:**
- 一份有降级的分析，用户在分析面板、通知、Muse 消息三处都能看出来，并知道缺的是什么。
- 全部用固定模板的中文白话，不出现内部用语。

**Non-Goals（不动的模块 / 文件）:**
- `src/lib/tender-auto-analysis/v2-resumable.ts`、`v2-cursor.ts` 的阶段门槛、尝试次数与让出逻辑：不改（时序留给 FIX-16）。
- `src/lib/ai/**`：不改。
- `src/lib/projects/generate/**`（导出文档）：不改。
- 「批准分析」的权限与流程（`requirement-batch-confirm`、审批接口）：不改，不加拦截。
- `prisma/**`：不改；降级记录放在既有的分析摘要 JSON 里。
- 一键分析最终结果卡片的生成（`src/lib/tender-workforce/tools.ts` 收尾步骤）：不改。

## Decisions

### D1 降级记录是结构化数据，句子在显示时生成

分析摘要 JSON 里多一个字段，存结构化的降级记录（段落的文件与页码、综合解读缺失的原因类别、复核是否跑完、未核对的澄清条数）；界面、通知、Muse 各自用同一个纯函数把它变成句子。

- 否决：直接把中文句子存进局限说明。句子改一次措辞，旧数据就不一致；通知与 Muse 需要的是更短的版本。
- 否决：新增一张表或字段。违反硬纪律第 1 条；摘要 JSON 已经是放这类信息的地方。

### D2 局限说明里的那句话改成白话，但仍然保留

局限说明仍会进综合解读的模型提示（让模型知道有内容缺失）。把句子改为「有 N 段页面没有读完（〈文件名〉第 x–y 页…），这些页的内容不在结果里。」，不带错误码。

- 否决：从局限说明里去掉这句。模型就不知道有缺失，综合解读可能把缺页当成「文件没有这项要求」。

### D3 面板只提示，不拦截批准

降级说明放在分析面板顶部（「上传 · 纳入分析 · 排除」那一段的上面），用提醒色；「批准分析」按钮不变。

- 否决：有降级时禁用批准。降级可能只是一段附录没读完，是否影响由人判断；拦截需要另一套「我已知晓」的确认流程，范围等重测后定（proposal「Out of scope」）。

### D4 复核没跑完用新的状态值区分

综合解读里复核的状态已有 `PASS / REVISED / NEEDS_HUMAN_REVIEW / SKIPPED`。复核调用失败时现在记成「需要人工复核」；改为记成「没跑完」（沿用既有的 `SKIPPED` 并带上原因类别），横幅按状态选句子。通知里的「AI 审校标记了需要人工复核的地方」只在复核真的跑完并标出问题时使用。

- 否决：新增一个状态值。会改综合解读的契约版本；`SKIPPED` 的语义正好是「没有做复核」。

### D5 通知与 Muse：有降级就换一句，并提高优先级

站内通知与 Muse 消息在降级记录不为空时用降级的写法，取最重的一种降级写进标题（没读完的段落 > 没有综合解读 > 复核没跑完 > 澄清没核对），其余的让用户到分析页看。Muse 消息只有项目名与降级的种类、数量，不含文件内容（硬纪律第 4 条）。

- 否决：通知里列全部降级。通知是一行字，列不下；分析页有完整说明。
- 否决：降级时不发「完成」通知。分析确实可以开始审核了，只是要先看说明。

### D6 澄清问题只注明，不重查

被截止或调用失败的澄清检查，在问题上注明「没来得及核对文件里是否已有答案」。注明所需的信息（哪几条的检查没有结果）来自检查点里已有的记录。

- 否决：下一切片重查。属于时序与尝试次数的改动，放 FIX-16 与澄清门槛一起定。

## 与八条硬纪律的关系

1. 零 schema：遵守——降级记录放在既有的分析摘要 JSON 里，不加模型 / 字段 / 迁移。
2. 出站先审批：不涉及——站内通知与 Muse 推送是既有的系统消息，只改文案，不新增发送。
3. 禁止第三套队列：不涉及。
4. 脱敏：遵守——新文案只含项目名、文件名、页码与数量；不含毛利率、项目估值、我方最终报价，也不含文件正文。规格里有对应的 SHALL NOT。
5. 不爬登录页：不涉及。
6. 邮箱分离：不涉及。
7. 确定性优先：遵守——句子由固定模板生成，不新增模型调用。
8. 测试注册：新测试同一 task 内注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

- `npx tsx src/lib/tender-auto-analysis/__tests__/degradation-notice.test.ts`：由检查点与结果算降级记录、各种降级的句子、没有内部用语、旧数据为空。
- `npx tsx src/lib/tender-auto-analysis/__tests__/alerts.test.ts` 与 muse-bridge 的事件测试：有降级 / 没有降级两种文案与优先级。
- `npx tsx src/lib/tender-auto-analysis/__tests__/package-coverage.test.ts`：覆盖说明的用字。
- 真实应用截图（隔离库造一份有降级的分析）：分析面板顶部的降级说明、复核没跑完的横幅、带注明的澄清问题，放 `docs/acceptance/fix-17/`。
- `npm run typecheck`、`npm run lint:baseline`、CI 子集、`npm test`、`openspec validate tender-degraded-result-notice --strict`。

## Risks / Trade-offs

- [旧的分析没有降级记录，其中有的其实跳过了段落] → 不回填；局限说明里那句旧文字还在数据里，需要时可以按 `CALL_DEADLINE_EXCEEDED` 查出受影响的分析（报告里给出查询）。
- [页码范围对非 PDF 文件没有意义] → 非 PDF 用单元标签（表名 / 段落号）代替页码，与证据引用的写法一致。
- [范围是按读代码写的，真实的降级样子还没见过] → proposal 头部已注明范围待 Evan 重测后确认；确认前不实现。

## Migration Plan

无数据迁移、无开关。合并部署即生效；回滚 = 回退本 PR（已写入的降级记录旧代码不读，无害）。
