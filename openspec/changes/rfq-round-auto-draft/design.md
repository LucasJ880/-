# Design

## Context

现状（main，`d18e3c80`）：

- 建一轮询价只有两个入口：项目页的「问供应商要价」抽屉（`POST /api/projects/{id}/tender-rfq/rounds`）与 Muse 的 `rfq` 意图。两者都调同一个建轮次函数，产出一张 `tender.send_rfq` 待批卡（一轮一张，72 小时有效，幂等键按轮次）。
- 抽屉打开时已经预选了操作者的常用供应商（个人偏好 `defaultSupplierIds`，最多 5 家，每次选定报价时把那一家挪到最前），贸易条款也取个人偏好。人实际做的是：打开、看一眼、点生成。
- 入口状态由一个纯函数判定（待批锁、近期已发锁、没有已确认要求、含敏感内容、邮箱未连接、缺发信权限、没有就绪供应商），自动起草直接复用它的结论。
- 「要求确认」有明确的人工动作：批准招标分析（`REVIEW_REQUIRED → APPROVED`，CAS，写审计），以及逐条 / 批量确认、驳回要求。询价单只收 `CONFIRMED` 的要求。面板上的「批准分析」不会顺手确认剩下的要求，所以批准之后常常还有未审核的。
- `ProjectInquiry` 有 `(projectId, roundNumber)` 唯一约束。

约束：八条硬纪律；不新增调度；首封询价必须由人批。

## Goals / Non-Goals

**Goals:**

- 要求审核完之后，第 1 轮询价的审批卡自己出现，人只需批准或驳回。
- 系统选的供应商完全可预期：就是操作者自己存的常用供应商，不多不少。
- 不起草时说清楚为什么、去哪里处理。
- 开关关闭时零变化。

**Non-Goals:**

- 不改 `src/lib/tender-rfq/build.ts`（询价单内容）、`execute.ts`（发送）、`round-pure.ts` 的轮次锁与供应商就绪规则。
- 不改 `src/lib/pending-actions/**`、`src/lib/approval/**`。
- 不改 `src/lib/muse-bridge/**`（含个人偏好的读写规则）。
- 不改 `src/lib/tender-auto-analysis/review.ts` 里审核动作本身的行为，只在四个路由里、动作成功之后追加一步。
- 不做供应商推荐、不做第 2 轮、不带跟进授权、不发通知。

## Decisions

### D1 触发点：四个人工审核动作成功之后，同步判定

在批准分析、确认要求、批量确认、驳回要求四个路由里，动作成功后调用一次 `maybeAutoDraftRfq`，结果放进响应。

- 这四个动作都是人点的、都要求项目写权限，操作者身份明确——起草的卡记在他名下，用他的常用供应商。
- 同步执行，不需要任何调度。
- 四个都接，是因为面板上的「批准分析」不确认剩余要求：最常见的顺序是「批准分析 → 再逐条确认 / 驳回」，条件在最后一条审核完时才满足。只接批准这一个触发点，多数项目永远触发不了。

否决的备选：

- **放进既有的 10 分钟定时任务**：没有操作者，不知道用谁的常用供应商；卡会在没人做任何动作时冒出来，难以解释。
- **只在批准分析时触发，并要求先全部确认**：要改人现在的操作顺序。
- **加一个「一键起草」按钮**：那就是今天的抽屉，没有省掉任何一步。

### D2 条件：全部审核完 + 还没有任何轮次 + 入口可发 + 有就绪的常用供应商

判定是一个纯函数 `decideAutoDraft(facts)`，按固定顺序返回第一条不满足的原因：

| 顺序 | 原因码 | 含义 |
|---|---|---|
| 1 | `FLAG_OFF` | 开关关闭（此时响应里根本没有 `rfqAutoDraft`） |
| 2 | `RUN_NOT_APPROVED` | 这份分析还没批准，或已被新的一份取代 |
| 3 | `REQUIREMENTS_PENDING` | 还有 N 条要求没有确认或驳回 |
| 4 | `ROUND_EXISTS` | 项目已有询价轮次 |
| 5 | `NO_CONFIRMED_REQUIREMENTS` | 没有已确认的要求（全部被驳回） |
| 6 | `SENSITIVE_LEAK` | 询价单含不能发给供应商的内容 |
| 7 | `SENDER_NOT_READY` | 授权邮箱未连接或缺发信权限 |
| 8 | `NO_DEFAULT_SUPPLIERS` | 操作者没有就绪的常用供应商 |
| 9 | `DRAFT_FAILED` | 建轮次时出错（含并发时输给另一次） |

第 5–7 条直接取既有入口状态的结论，不重写判断。

「还没有任何轮次（含已取消）」是防止重复起草的唯一依据：人驳回了自动起草的卡，轮次变为已取消，之后不再自动起草——人已经表态，接下来由人在抽屉里自己发。也因此重新分析、再次批准不会冒出第 2 轮。

否决的备选：

- **有未审核的要求也起草（只用已确认的）**：人可能只是还没看完，这时备好的卡内容不全，批了就漏问。
- **用审计记录「已自动起草过」**：轮次本身就是记录，不需要第二份。

### D3 供应商：只用操作者的常用供应商

取操作者 `defaultSupplierIds` 里在用且有邮箱的，保持保存顺序，最多 8 家（抽屉的上限）。被跳过的（停用、没邮箱）计数并写进结果与审计。

- 这正是抽屉今天预选的那几家——自动起草等于替人点了「生成」，不引入任何新的挑选逻辑。
- 常用供应商是人的选择沉淀下来的（每次选定报价挪到最前），不是模型的判断。

否决的备选：

- **按 `Supplier.category` / `tags` / `aiClassification` 匹配要求品类**：这些字段有一部分是模型写的；让它们决定邮件发给谁，等于让模型输出决定对外动作的收件人（违反确定性优先），且选错的代价是把招标要求发给不相干的厂。
- **用项目负责人的常用供应商**：操作者可能不是负责人；卡记在操作者名下却用别人的偏好，不好解释。
- **没有常用供应商时取组织里全部就绪的**：可能是几十家。

### D4 起草：调既有的建轮次函数，来源记为 `auto`

`prepareRfqRound({ source: "auto", supplierIds, incoterm: 偏好, userId: 操作者 })`。`source` 今天只影响审批卡的 `source.toolName`（审计用），加一个取值 `tender_send_rfq_auto`。标题加前缀「自动起草」，摘要加一行「供应商取自 {操作者} 的常用供应商」。轮次列表靠审批卡的 `toolName` 认出自动起草的轮次。

有效期、幂等键、载荷、轮次锁、推送到 Muse 的待批提醒全部沿用。并发：两次触发各自走到建轮次，`(projectId, roundNumber)` 唯一约束让其中一次失败，记为 `DRAFT_FAILED`。

否决的备选：**另写一个起草函数**——会出现两套建轮次逻辑，以后改一处漏一处。

### D5 不带跟进授权

RFQ-AUTO-1 的规格写明授权只在「网页发起且明确勾选」时写入。自动起草没有人勾选，所以不带。`source: "auto"` 不等于 `"web"`，既有判断自然不成立，不需要额外代码。两者怎么接（例如个人偏好里的一个明确开关）等 #422 合并后单独提。

### D6 结果怎么告诉人

- 响应：`rfqAutoDraft: { drafted: true, roundNumber, supplierCount, skippedCount, href } | { drafted: false, reason, messageZh, action: { label, href } | null }`。只有白名单里的这几个字段。
- 面板：审核动作成功后在按钮下方显示一行。`REQUIREMENTS_PENDING` 在逐条确认的过程中每次都会出现，所以这个原因只在「批准分析」时显示，逐条确认时不显示（避免每点一下都提示一次）。
- 不新增通知：既有的建卡流程已经会提醒审批人。

### D7 开关

`TENDER_RFQ_AUTO_DRAFT_ENABLED` + `TENDER_RFQ_AUTO_DRAFT_ORG_ALLOWLIST`，写法与 RFQ-AUTO-1、投标工作区的开关一致。默认关。

## 与八条硬纪律的关系

1. **零 schema**：遵守。不加表、不加字段；自动起草的标记来自审批卡既有的 `source` 元数据，审计写 `AuditLog`。
2. **出站先审批**：遵守，且不放宽。自动起草只产出待批卡；首封由人批准后才发。
3. **禁止第三套队列**：遵守。没有任何后台执行，只在人的请求里同步跑。
4. **脱敏**：遵守。询价单内容与敏感词检查沿用既有；新响应字段只有轮次号、家数、链接与固定文案。不触碰 Muse 通道。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：遵守。发件人与授权邮箱仍只从组织设置读，沿用既有的发件检查。
7. **确定性优先**：遵守。判定是查表；供应商来自人保存的偏好；不新增模型调用；不往偏好里写任何东西。
8. **测试注册**：两个新测试注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## 验证方式

- `npx tsx src/lib/tender-rfq/__tests__/auto-draft-pure.test.ts`：九个原因逐条、检查顺序、供应商选取（顺序、上限、跳过）、结果对象只含白名单字段、开关。
- `npx tsx src/lib/tender-rfq/__tests__/auto-draft-db.isolated.test.ts`（本地隔离库，没有库时自跳过）：开关关闭零变化；批准后起草；最后一条确认后起草；驳回卡后不再起草；并发只起草一轮；别人的常用供应商不被使用；起草失败不影响审核动作；零邮件发出；审计内容。
- 既有测试全量：`npm run test:ci`、`npm run typecheck`、`npm run lint:baseline`、`scripts/check-test-registry.sh`、`scripts/test-runtime-architecture.sh`。
- 真实应用截图（本地库、演示数据）：面板上的结果行、项目页的「自动起草」标记，存 `docs/acceptance/rfq-auto-2/`。
- `openspec validate rfq-round-auto-draft --strict`。

## Risks / Trade-offs

- **卡在人没预期的时候出现**：靠面板上的结果行、标题里的「自动起草」与既有的待批提醒说明；驳回即止，不会再来。
- **常用供应商不适合这个项目**（例如常做窗帘的厂被拿去问清洁用品）：系统不判断适不适合，人在批准时看收件人。批错的代价是多发了一封询价；卡上逐家列出收件人与正文，这一步没有省。这是本方案最主要的取舍，写进报告。
- **操作者没存过常用供应商**：永远不起草，只给出去处。首次使用需要人先走一遍抽屉。
- **四个路由各加一步**：自动起草的任何异常都被接住，不影响审核动作本身；每个路由只多一次调用。

## Migration Plan

无数据迁移。开关默认关；打开后只对之后的审核动作生效。回滚：关开关。已起草未批准的卡就是普通待批卡，批准、驳回、过期都照常。

## Open Questions

无阻塞实施的问题。两处取了推荐做法，Owner 可以改：

- 供应商来源只用操作者本人的常用供应商（D3）。
- 自动起草的轮次不带跟进授权（D5）。
