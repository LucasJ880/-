# Design：招标分析保留数量与单位，价格表从分析带入（FIX-2）

## Context

读代码确认的现状：

- V2 分析的结果里，每条要求有 `quantity`、`unit`（都是模型填的字符串，可空）；提示词还要求把价格表的行、数量上限抽成 `quantity` 类型的事实（`claim` 是那一行的说法，`rawValue` 是原文值）。
- `src/lib/tender-auto-analysis/v2-map.ts` 把结果映射成入库的形状时，要求只留了类别、原文、是否强制、页码；事实只留了说法与原文。**数量与单位在这里被丢掉。**
- `TenderExtractedRequirement` 没有数量或单位的列。同一次分析的各节（`TenderAnalysisSection`）有一个 `structuredJson` 列，已有几节在用（风险、关键事实、提交清单）；「价格与评标」一节现在传的是 `null`。对外的序列化（`serializeSection`）不输出这一列。
- 投标工作区的价格表（TI-4b）只有「粘贴导入」：前端用 `parseSchedulePaste` 解析制表符分隔的文本，人看过解析结果后点保存，经既有接口与结构校验落库。列序固定：行号、说明、数量、单位、包装数、尺寸、最小尺寸、认证要求。数量只接受数字，单位要在封闭的目录里（`Each`、`Pack`、`Box`、`Roll`、`Pair`、`Set`、`Case`、`Bag`、`kg`、`m`、`ft`、`sqft`）。

## Goals / Non-Goals

**Goals**

- 分析已经抽到的数量与单位不再丢。
- 人不用从招标文件里手工转录价格表的行。
- 看不准的不猜；每一行都有人看过才进价格表。

**Non-Goals（具体到文件）**

- 不改 `prisma/schema.prisma`。
- 不改抽取：`src/lib/tender-understanding/**`（提示词、契约、归一、去重）一行不动。
- 不改价格表的规则：`src/lib/tender-price-schedule/**`、`src/lib/tender-bid-workspace/paste-import.ts`、`store.ts`、`contract.ts`、保存接口 `src/app/api/projects/[id]/bid-workspace/route.ts`。
- 不改询价、自动起草、Muse。

## Decisions

### D1 存在「价格与评标」一节的结构化字段里

`structuredJson = { scheduleCandidates: { version: 1, total, items: [...] } }`。每项：`source`（`requirement` / `fact`）、`code`（要求编号，事实为空）、`description`、`quantityText`、`unitText`、`page`、`sourceZh`（文件名 · 位置）、`inConflict`。最多 300 条，`total` 记原本有多少条。

- 否决：给 `TenderExtractedRequirement` 加 `quantity` / `unit` 两列。最直接，但违反零 schema，要生产迁移；而且数量类事实不是要求，放不进去。
- 否决：放进分析的 `summaryJson`。那里已经有摘要、分析师综合等内容，对话上下文会整块读它；数量线索可能有上百条，会把提示词撑大。
- 否决：新增一种节（新的 `sectionKey`）。节的种类对应报告的章节，界面按它渲染；多一种会多出一章空白。
- 带 `version`：以后改形状时读取方能认出旧数据。没有 `scheduleCandidates` 这个键 = 分析是在本功能之前做的，或用的是旧版分析（与「有键但清单为空」区分）。

### D2 入库时原样保存，转换放在读取时

入库只存分析给出的文字（数量文字、单位文字）；「取不取这个数字」「单位怎么规整」在带入时算。

- 否决：入库时就算好数字与单位。规则以后会调（对照表加一项、哪些写法算歧义），算好的结果改不了，原样的文字可以重新算。
- 这些文字叫「分析给出的」，不叫「原文」：要求的数量与单位是模型填的字段，上游没有逐字对过原文片段（只有数量类事实的原文值对过）。界面与规格都按这个叫法。

### D3 数量：整段文字就是一个数字才取（白名单）

形状：`[约 / approx. / about / est. / qty: / total …] 数字 [单位]`。数字是整数（可带千位逗号）加可选的小数。后面跟着的词必须是对照表里的单位、时间单位、连续量单位，或者就是分析给出的那个单位。别的一概不取，并给出原因：没有数字、范围、不止一个数字、金额或百分比、带着别的说明、写法有歧义、单位是时间、数量为 0。

- 否决：「文字里恰好一个数字就取」（本设计的第一版）。独立审查实际跑出来它会悄悄取错：`5k` → 5、`12 dozen` → 12、`Item 3` → 3、`Dec 2026` → 2026、`CAD 5000` → 5000、`50 per month` → 50、`.5 kg` → 5。取错比不取糟得多——行看起来是好的，人未必会去对。
- 否决：取第一个数字 / 范围取上限。这是报价上的判断，不该由系统做。
- 歧义的写法不取：`1.500`（英文是一点五，欧式写法是一千五）、`0,500`、前导零；`2,500 kg`——只有一组千位、单位又是连续量时，逗号可能是法语的小数点。同样的 `2,500` 配件数单位（`Each`）照取：件数不会是小数。
- 代价：`approx. 120 per year`、`minimum 50`、`1,200 ft` 这类带不进来——列在「没带入」里，分析给出的文字与出处就在旁边，人自己填。宁可多让人填几个数，不带进一个错的。
- 已知取不准的一种：没有单位、只有一组千位的 `1,500`，在法语文件里可能是一点五。无法与英文的一千五区分，照英文取；界面列着分析给出的文字供核对。

### D4 单位：固定对照表，认不出的原样保留

`ea / each / pc / pcs / piece(s) / unit(s) → Each`；`pk / pack(s) / pkg → Pack`；`bx / box(es) → Box`；`rl / roll(s) → Roll`；`pr / pair(s) → Pair`；`set(s) → Set`；`cs / case(s) → Case`；`bag(s) → Bag`；`kg(s) / kilogram(s) → kg`；`m / meter(s) / metre(s) → m`；`ft / foot / feet → ft`；`sqft / sq ft / sf / square feet → sqft`；另有几个中文单位（个、件、只、套、卷、双、袋、包、公斤、米）。不分大小写，去掉末尾的句点。

- 否决：模糊匹配或让模型判断。`LF`（延长英尺）与 `ft` 不是一回事，认错了数量就差出去了。认不出的留原样，既有校验会把它标红，人来改。
- 单独一个大写的 `M` 不规整成米：它在北美采购里也表示「每千件」。
- 分析没有单独给单位时用数量文字里跟着的那个（`60 pcs`）；两处都有且不一样（`15 each` 配 `Box`）不带入。
- 比价格表的单位上限（20 个字符）还长的不是一个单位，留空由人填。

### D5 带入只填粘贴框，不保存

按钮把生成的文本放进既有的粘贴框，后面的解析、预览、保存、校验全是既有流程。

- 否决：一键生成价格表并保存。分析会漏行、会把上限当数量；价格表是报价的基础。
- 否决：做一个专门的逐行勾选界面。粘贴框本来就能改、能删行，够用；专门的界面是下一步的事。
- 粘贴框里已经有内容时先确认再替换；取的过程中粘贴框只读；换了项目后还在路上的那次带入作废；粘贴框改过之后，对照清单标明是带入那一刻的。
- 带入的判断（点了之后是问还是取、取回来后粘贴框该是什么）抽成纯函数，带入的那段代码里不出现任何保存的动作——都有测试盯着。

### D6 只读接口单独一条，不并进工作区的主接口

`GET /api/projects/{id}/bid-workspace/schedule-candidates`，点按钮时才请求。

- 否决：并进 `GET …/bid-workspace` 的响应。每次打开项目页都会多读一节的 JSON，而带入是偶尔才点一次的动作。

读取时：取项目最新一份等待审核或已批准的分析（与询价单、投标草稿、报价上下文取分析用的是同一条规则）；来自要求的线索按要求编号对现在的审核状态，已驳回的不返回；来自事实的线索按说法对上事实的审核记录，被驳回的不返回。

### D7 接口与界面的门槛

读权限即可看（它只读招标文件里的数量）；沿用投标工作区的功能开关 `TENDER_BID_WORKSPACE_ENABLED`，关闭时 404。按钮只对能保存价格表的人显示（与「粘贴导入」同一个条件）。

### D8 哪些要求算线索：按类别排除

行政、投标提交、质保、保函、保险、安全、样品、深化图、培训、踏勘、工期、报告这十二类不收；产品、技术、性能、安装、交付、价格、商务、强制、其他照收。

- 否决：不分类别全收。审查跑出来「深化图 3 套」「样品 2 件」会变成看起来像样的价格表行。
- 否决：只收产品与价格两类。类别是模型判的，供货的行常被标成技术、安装或强制；收窄了会漏行，而漏掉的行人看不到。排除的那十二类里即使混进一条真的行，后果是少带一行（界面写明「可能有漏」）。

### D9 说法不一致的：记下、标明、不带入

分析的补遗处理遇到「同一件事两处说法不同、又没有修订的说法」时不替人选，两条要求都标成待复核并记一条未解决的冲突。这里跟着它：两条都记下并标明，带入时都不成为行，列在「没带入」里。

- 否决：两条都带入（第一版的行为）。价格表里会出现 2367 与 2900 两行，没有任何提示。
- 否决：不记。人就不知道分析在这里看到过数量。

### D10 重复的行不合并，只标明

说明、数量、单位都相同的两条线索都带入，后一行标明与哪一行相同。

- 否决：合并成一行（第一版的行为）。上游的去重已经把确实重复的并过了；剩下的可能就是两行（同一种货两个地点）。并掉了人看不到，标出来由人删。

## 与八条硬纪律的关系

1. **零 schema**：遵守。数量线索存在既有的 `TenderAnalysisSection.structuredJson`（同一列已有三节在用），不新增表、列、迁移。
2. **出站先审批**：不涉及。没有任何对外发送；价格表本身也不出站。
3. **禁止第三套队列**：遵守。没有新增后台执行；入库仍在既有的分析流程里。
4. **脱敏**：遵守。数量与单位来自招标文件；接口的响应不含我方的成本、报价、毛利、估值（招标文件里自己写的文字原样显示）；Muse 通道没有新增内容。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。数量的取法是一条固定的形状规则，单位是查表；不新增模型调用，不改提示词。
8. **测试注册**：两个新测试注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## 验证方式

- `npx tsx src/lib/tender-bid-workspace/__tests__/schedule-prefill.test.ts`（新）：收集（类别、被取代的、类型不对的字段、超长与上限）；经真实的去重与补遗处理的两种情形（说法不一致、合并后的出处）；经真实的入库映射；读旧数据；数量的取法（能取的与审查列出的每一种不该取的）；单位对照；生成的文本交给既有的 `parseSchedulePaste` 与价格表行的结构校验；说明里的制表符 / 换行 / 控制字符 / 双引号；面板的判断；接线与「带入的代码里没有保存」的源码断言。
- `npx tsx src/lib/tender-bid-workspace/__tests__/schedule-prefill-db.isolated.test.ts`（新，本地隔离库）：真实的入库映射与入库 → 真实的路由处理函数。带入、没带入的原因、被驳回的要求与事实（用真实的审核函数）、没有分析（七种状态里不可用的五种逐个）、旧分析、取哪一份、不串项目与组织、权限与开关、上限与总数、接口不写库。
- 变异核对：把实现逐处改坏（自动保存、跳过确认、放宽分析状态、不排除冲突、放宽数量规则等 30 处），每一处都要有测试失败。
- `npx tsx src/lib/tender-auto-analysis/__tests__/v2-map.test.ts` 等读到 `v2-map.ts` 的既有测试：不改断言即通过（`grep -rln "v2-map" src --include=*.test.ts` 全部重跑）。
- 全量：`npm run test:ci`、`npm run typecheck`、`npm run lint:baseline`、`bash scripts/check-test-registry.sh`、`bash scripts/test-runtime-architecture.sh`。
- 真实应用截图（本地库、演示数据）三张，存 `docs/acceptance/fix-2/`：带入后的粘贴框与对照、已有内容时的确认、保存后的价格表。
- 开 PR 前请一个不带结论的独立审查（重点：多租户隔离、取数字的规则有没有会悄悄取错的情形、生成的文本会不会被解析成别的行、测试能不能发现问题）。
- `openspec validate analysis-quantity-unit-prefill --strict`。

## Risks / Trade-offs

- **分析抽得不全或不准，带入的行就不全或不准。** 界面写明「需要逐行核对」，每一行旁边有分析给出的文字与出处；不保存。
- **规则偏严，带不进来的比第一版多**（按年计的用量、上限、连续量的千位写法）。它们列在「没带入」里，人自己填。
- **没有单位的行保存时会被既有的解析略过。** 说明文字与解析结果都写明；人补上单位才会保存。
- **要求的数量与单位是模型填的字段**，没有逐字对过原文。界面叫它「分析抽到的数量」，旁边是出处。
- **被驳回的事实按说法对上**（事实没有编号）：两条说法逐字相同的事实，驳回一条会让两条的线索都不带入。
- **用旧版分析（V1）做的项目没有数量线索**，提示写的是「用新版分析重新分析」；本功能之前做的分析同样。
- **一节的 JSON 变大**：300 条、每条说明最长 500 字时约一百多 KB。这一节原来是空的；读分析详情的接口会把它读出来再丢掉（既有的写法，没有改）。
- **隔离库测试在 CI 里跳过**（仓库现状）：本地跑并在报告里写明。

## Migration Plan

无数据迁移。上线后新做的分析才带数量线索；旧分析的行为与现在相同（按钮会提示重新分析）。回滚 = 回滚代码；已经存下的数量线索留在 JSON 里，没有读取方，不影响任何东西。
