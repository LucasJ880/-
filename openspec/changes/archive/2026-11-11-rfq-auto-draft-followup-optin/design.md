# Design

## Context

现状（main，`83dbc898`）：

- RFQ-AUTO-1：发询价的审批卡可以带跟进授权。写入条件在建轮次函数里只有一处：来源是网页、请求里明确带了 `autoFollowUp: true`、功能开关对该组织打开。授权写进卡的载荷，受载荷哈希保护；带授权的卡标题标明、只能在网页批；项目页原地审批处展示范围与三段模板。
- RFQ-AUTO-2：批准招标分析后，系统用操作者的常用供应商自动起草第 1 轮的待批卡。来源记为 `auto`，所以上面那个条件不成立，卡不带授权。自动起草的卡同样只能在网页批，审批处上方有一句说明。
- 两个功能各有一个开关，默认都关。
- 界面上人的实际操作（动手前核对过）：开了自动起草之后，第 1 轮不再经过「问供应商要价」抽屉，而且卡一起草入口就被「有待批的发送卡」锁住——抽屉里那个勾选框在这条路径上根本看不到。所以个人开关不能放在抽屉里。
- 个人偏好今天存在 `Organization.settingsJson.museBridge.userPrefs[userId]`，只认四个字段，Muse 的 `set_preference` 能写它。组织的询价设置存在 `settingsJson.tenderRfq`，更新时保留没传的键。

约束：八条硬纪律；首封询价与授权都必须由人在看得到内容的地方批。

## Goals / Non-Goals

**Goals:**

- 开启之后，一个标从批准分析到供应商回完价，人只点两次。
- 「带不带授权」始终是人的明确选择：事先在看得到范围与模板的地方开启一次，之后每张卡上仍然写明、仍然要人批。
- 关掉任何一个开关都退回上一级行为。

**Non-Goals:**

- 不改 `src/lib/tender-rfq/followup-coverage.ts`（覆盖判定）、`chase-service.ts`、`chase-execute.ts`、`followup-service.ts`（停止）。
- 不改 `src/lib/pending-actions/**`、`src/lib/approval/**`、`src/lib/muse-bridge/**`。
- 不改 `openspec/config.yaml`。
- 不做组织级统一开关、不给已起草的卡补授权、不改授权内容。

## Decisions

### D1 一个按用户、按组织的常设开关

每个用户在每个组织里一个布尔开关，默认关。自动起草时只看触发起草的那个人的开关。

- 自动起草的卡记在操作者名下、用的是他的常用供应商；带不带授权由同一个人决定，责任清楚。
- 最终生效仍取决于批准这张卡的人：卡上写明授权，他批准了才算数；跟进邮件以他的身份执行。这一点与 RFQ-AUTO-1 相同，没有新增信任关系。

否决的备选：

- **组织级开关（管理员替所有人开）**：操作者没有自己选过，卡上却带着授权。
- **两个功能开关都开时默认就带**：等于把「明确选择」换成了「部署配置」，违背 RFQ-AUTO-1 规格里「明确勾选」的要求。
- **不设常设开关，每次在面板的结果行上点「带上授权重新起草」**：每个项目多点一次，还要作废一张卡。

### D2 状态 = 本人最近一条开关记录（只追加），不放进组织设置

**独立审查后改定。** 每次开或关追加一条 `AuditLog` 记录（动作 `tender.rfq_followup.auto_draft_optin`，对象是这个人）；状态 = 这个人在这个组织里最近一条记录。开的那条带当时的模板指纹。读的时候严格解析，形状不对一律当作关。这与 RFQ-AUTO-1「停止自动跟进」是同一做法（记录即状态），`AuditLog` 是零 schema 纪律列出的合规落点。

四件套原稿把它放在 `Organization.settingsJson.tenderRfq` 下。独立审查指出：那一整块 JSON 被好几处「整块读、整块写」且不加锁（收信定时任务的游标、Muse 的偏好与绑定、管理员改设置、日历监听……）。用户刚关掉开关，另一处把先前读到的旧数据写回，开关就悄悄变回开，而接口已经告诉他关了、审计也记的是关——下一次自动起草又带上了授权。给本次的写入加行锁没有用（别的写入方不加锁），反而拉长了窗口。只追加的记录不存在这个问题。

否决的备选：

- **放进 `Organization.settingsJson`**（原稿）：见上。
- **放进 `museBridge.userPrefs`**：那一份只认四个字段，多出来的键会被丢掉；而且那里的键能在 Muse 里改。
- **放浏览器本地存储**：起草发生在服务端，读不到。

### D2a 开启时绑定模板指纹

独立审查指出：开关只存「开 / 关」的话，人开启时看到的是那一版模板，以后模板改了，授权却跟着新模板走。现在开的那条记录带模板指纹；现在的指纹与记录里的不同，开关就是「已失效」：自动起草的卡不带授权，界面提示看过新模板后重新开启。这与 RFQ-AUTO-1 用模板指纹保护已批准的轮次是同一个原则。

间隔天数与回复截止每个项目不同，没法在开启时绑定——它们每一次都写在卡上，由批准人看到并批准。界面在范围说明处注明「以这个项目现在的设置为例」。

### D3 开关放在项目页询价区块的顶部，不放抽屉

两个功能开关都开时，「标书与报价」页签的询价区块顶部出现一行：「自动起草的轮次带跟进授权：未开启 / 已开启」，可展开看范围说明与三段模板（复用 RFQ-AUTO-1 入口已经返回的那份预览），旁边是开启 / 关闭按钮，开启前二次确认。

- 这一行不受入口锁影响，任何投标项目都看得到。
- 范围与模板就在开关旁边：人开启时看得到自己授权的是什么。

否决的备选：

- **放在抽屉的勾选框旁边**：见 Context，自动起草的路径上看不到抽屉。
- **放在个人设置页**：离内容太远，看不到范围与模板。
- **允许在 Muse 里用 `set_preference` 开**：Muse 里看不到范围与模板。

### D4 接线：自动起草的服务读开关，建轮次函数的条件多认一个来源

- 自动起草的服务在起草前读操作者的开关；开着就给建轮次函数传 `autoFollowUp: true`。
- 建轮次函数里写授权的条件从「来源是网页」放宽为「来源是网页或自动起草」，其余不变（明确带了 `autoFollowUp: true`、功能开关打开）。Muse 的调用不传这个参数，条件自然不成立。
- 授权的内容用同一个构造函数，同一套入参（间隔按项目负责人的偏好、回复截止、模板指纹）。

否决的备选：**在自动起草的服务里自己拼授权再塞进载荷**——会出现第二处写授权的地方。

### D5 批准与之后的行为完全沿用

带授权的自动起草卡同时满足「自动起草」与「带授权」两个只能在网页批的条件。项目页原地审批处会同时显示自动起草的说明与授权范围、模板预览——两段都是既有逻辑，按卡的载荷出现，不需要新代码。批准之后的覆盖判定、执行、审计、停止，一行都不改。

面板上的结果行多一句：「这张卡带自动跟进授权：批准它会一并批准后面的催单和追问。」结果对象多一个布尔字段 `withFollowUp`。

### D6 关闭只影响之后的起草

关闭开关不回头改已经起草或已经批准的卡（载荷受哈希保护，也不该改）。已批准的轮次要停用，用 RFQ-AUTO-1 的「停止自动跟进」。

### D7 设置接口

`PUT /api/projects/{id}/tender-rfq/auto-follow-up`，请求体只有 `{ enabled: boolean }`（多一个键都拒绝）。用项目来做权限与组织的判定（要求项目写权限），写的是「登录的这个人在这个组织」的开关。

- 开启：要求两个功能开关都打开，否则 404。
- 关闭：任何时候都可以。**独立审查后改定**——原稿在功能开关关闭时连关闭也返回 404，结果是一个开着的同意在功能关闭期间撤不回，功能一打开又自己生效。
- 状态已经是想要的那样就不写。

否决的备选：**挂在组织设置接口下**——那个接口要求组织管理员，而这是每个人自己的开关。

### D8 带授权的待批卡，不看功能开关都要显示授权

**独立审查后补的。** 入口原来在跟进授权的功能开关关闭时什么都不返回。于是：一张带授权的卡起草之后功能开关被关掉，批准处就看不到授权范围，但授权还在卡的载荷里，功能再打开就恢复生效。这个缺口是 RFQ-AUTO-1 留下的，但那时至少发起人当场勾选过；自动起草的卡没有人在这张卡上看过范围，所以在这里修掉：只要待批卡的载荷里有授权，批准处就显示范围与模板；功能关闭时加一句说明。勾选框与轮次状态在功能关闭时仍然不显示。

## 与八条硬纪律的关系

1. **零 schema**：遵守。开关的状态就是 `AuditLog` 里的记录（合规落点之一），不新增表与字段，也不碰 `Organization.settingsJson`。
2. **出站先审批**：遵守，不需要改纪律文字。现有的补充文字是「一张已批准的审批卡可以一并授权它正文里逐项写明的后续固定模板邮件」——授权仍然写在卡上、仍然由人批准这张卡才生效、每封后续邮件仍逐封建审批记录。本次变的只是「谁让这张卡带上授权」：从起草时当场勾选，多了一条事先开启的途径。
3. **禁止第三套队列**：遵守。没有新增任何后台执行。
4. **脱敏**：遵守。新响应字段只有布尔值与固定文案。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。开关是布尔值，读取是查表；不新增模型调用；不往 Muse 的偏好里写任何东西。
8. **测试注册**：新测试注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

- `npx tsx src/lib/tender-rfq/__tests__/auto-draft-db.isolated.test.ts`（扩）：开启后起草的卡带授权且内容与网页勾选时相同；没开启不带；只用本人的开关；跟进授权的功能开关关闭时不带；设置接口的权限、记录、404；关闭后新起草的不带；批准之前零出站；把卡标为已批准并发出后扫描自动催单（假邮件）；别处回写旧设置不会恢复开关；模板改过后失效与重新开启；功能开关关闭期间关得掉、开不了；带授权的待批卡在功能关闭时仍显示授权。

- 既有测试全量：`npm run test:ci`、`npm run typecheck`、`npm run lint:baseline`、`scripts/check-test-registry.sh`、`scripts/test-runtime-architecture.sh`。

- 开 PR 前请一个不带结论的独立审查（RFQ-AUTO-1 留下的规矩）。
- `openspec validate rfq-auto-draft-followup-optin --strict`。

## Risks / Trade-offs

- **开一次管以后所有项目**：人可能忘了自己开过。每张卡的标题、摘要、原地审批处都写明带授权；询价区块顶部一直显示当前状态；随时能关。
- **操作者与批准人不是同一个人**：操作者的开关让卡带上授权，批准人承担后果。批准人在网页上看得到完整范围与模板才能批（Muse 批不了），可以驳回。
- **状态靠最近一条记录**：同一毫秒内的两条记录按记录号排先后；审计表如果被清理，开关会回到默认的关（偏安全的方向）。
- **三个开关的组合**：自动起草关 → 本功能无从触发；跟进授权关 → 开关不显示、不生效；都开但个人没开 → 与今天相同。测试覆盖这三种。

## Migration Plan

无数据迁移。没有新的功能开关：本功能在 RFQ-AUTO-1 与 RFQ-AUTO-2 两个开关都打开时才可见，个人开关默认关。回滚：关掉任一功能开关，或各人关掉自己的开关。

## Open Questions

无阻塞实施的问题。三处取了推荐做法，Owner 可以改：按用户而不是按组织（D1）；开关放在项目页询价区块顶部（D3）；不给已起草的卡补授权。

## 独立审查后补的（实施完成后、开 PR 之前）

按规矩请了一个不带结论的独立审查。确认并修复：

1. **关闭可能被别处的写入悄悄恢复成开**（存储位置的问题）。见 D2。
2. **功能开关关闭期间关不掉，功能一打开又自己生效**。见 D7。
3. **卡起草后功能开关被关掉，批准处看不到授权范围**。见 D8。
4. **开启时看到的模板与以后实际用的可能不同**。见 D2a。
5. **界面文字**：原来写「仍然要你批准」，实际批准人常常是另一个有审批权的人，催单以他的身份发出，已改；二次确认期间范围说明原来可以收起，现在收不起来。
6. 几处过时的代码注释（仍写着「自动起草不带授权」）已改。

审查确认没有问题的部分：谁能设置（组织设置接口的校验是严格的，注入不了；Muse 的 `set_preference` 只碰自己的四个字段；没有通用的设置接口）；读的是触发动作的登录用户自己的开关；所有批准入口（Muse、微信确认）对这类卡都只能去网页；授权内容与网页勾选时用的是同一个构造函数、同一套入参；`prepareRfqRound` 的三个调用方里 Muse 不传 `autoFollowUp`；设置接口先鉴权再读请求体。

审查提到但没有改的：

- 测试里「人批准并发出」是直接改库模拟的，没有走真实的批准与发送路径（发询价的执行器没有可注入的假发送器）。批准路径本身由 RFQ-AUTO-1 的测试覆盖，但「自动起草 + 带授权」的卡没有单独走过一遍真实批准。
- 一部分接线断言是对源码文本的匹配，不随运行行为变化；它们防的是「有人改掉这一行」，不能代替上面的真库测试。
