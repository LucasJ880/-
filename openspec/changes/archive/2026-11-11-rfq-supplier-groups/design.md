# Design：供应商分组（RFQ-AUTO-5）

## Context

读代码确认的现状（不是假设）：

- 「常用供应商」是每人一份的平铺名单：`Organization.settingsJson.museBridge.userPrefs[userId].defaultSupplierIds`，上限 5 家（`src/lib/muse-bridge/prefs-pure.ts`）。写入只有两条路：Muse 的 `set_preference`，以及在任一项目里选定报价后自动把那家挪到最前（`learnSupplierPreference`）。**网页上没有编辑它的入口。**
- 用它的地方：询价抽屉预先勾选（`rfq-web-entry-drawer.tsx` 的 `defaultSelected`）；RFQ-AUTO-2 自动起草取它作收件人（`auto-draft-service.ts` → `pickAutoDraftSuppliers`，上限 8 家）；Muse 发起询价。
- 没有可用的「品类」：`Project.category` 与 `Supplier.category` 都是自由文本，互相没有词表；投标项目上 `Project.category` 多数为空（对外接口甚至拿 `"tender_opportunity"` 兜底）。供应商另有 `tags` 与模型产出的 `aiClassification`，同样是自由文本。
- RFQ-AUTO-3 的先例：本人的设置存成只追加的审计记录、最近一条即状态，避开了 `Organization.settingsJson` 整块读改写会互相覆盖的问题（那个问题仍在，等 Owner 决定是否另开 change）。

约束：零 schema；确定性优先、不加模型调用；出站先审批（本 change 不新增任何出站路径）；不建第三套队列；测试必须注册。

## Goals / Non-Goals

**Goals**

- 做不同品类标的人，自动起草与抽屉预选能落到对的那几家供应商上。
- 确定不了的时候不猜，把原因和去处告诉人。
- 没建分组的人，一切照旧。
- 人能在网页上管理分组，不必经 Muse。

**Non-Goals**

- 不做组织共用的分组、不做模型归类、不做按供应商字段自动归组。
- 不改那份平铺的常用供应商及其学习逻辑，不改 Muse。
- 不改审批、发送、催单、跟进授权。

## Decisions

### D1 分组按人，不按组织

与 RFQ-AUTO-2「只取操作者自己的常用供应商」、RFQ-AUTO-3「只看他本人的开关」一致：一个人起草给谁，只由他自己保存的东西决定。

- 否决：组织共用。一个成员改了分组，别人批准分析时自动起草的收件人就变了；还要先定谁有权改。小团队里每人各建一遍是有成本的，但这是可以之后再放开的方向，反过来（先共用再收回）不行。

### D2 存储：本人的只追加记录，整份文档，最近一条即状态

`AuditLog` 一条记录 = 一次保存，`afterData` 是整份分组文档（≤10 组 ×（名字、≤8 个供应商 id、≤10 个关键词），几 KB 以内），`beforeData` 是保存前的那份。读 = 取本人在该组织最近一条。记录的 id 就是「这一版的标识」。

- 保存带 `baseVersion`（读到的那条记录的 id，从没保存过为 null）。在一个短事务里：取本人的事务级咨询锁 → 读最近一条 → 与 `baseVersion` 不同则 409 → 否则追加。事务里只有这两条语句，不包任何别的调用（RFQ-AUTO-2 里咨询锁出过连接池问题，是因为锁里包了整个建轮次；这里不会）。
- 否决：放进 `settingsJson.museBridge.userPrefs`。与常用供应商放一起最顺手，但那里是整块读改写，已知会互相覆盖；网页上多一个频繁写入方只会更糟。
- 否决：复用供应商的 `category` / `tags` 字段当分组。那是组织共用的数据，改它等于替所有人归类。
- 代价：`AuditLog` 被当作状态存储用（RFQ-AUTO-3 已有先例）；分组的历史永久保留，这对「当时为什么发给这几家」的追溯是好事。

### D3 项目用哪一组：只拿项目名称比关键词

规整（NFKC、转小写、连续空白并一个、去首尾空白）后做子串包含。恰好一组对上才算；零组或多组都不选。记下第一个对上的关键词（按保存的顺序）作为依据。

- 只比项目名称：投标项目的名称通常就是标的（`Supply and Install Window Coverings – …`），短、稳定、人一眼能核对「为什么对上」。
- 否决：比招标要求正文。长，误中多（窗饰标里会写「保护现有家具」），多组同时对上会变成常态，等于没用。
- 否决：多组对上时取关键词最长的 / 最先保存的。这是猜，而且人很难预料结果。
- 否决：模型归类。硬纪律「确定性优先」；而且起草给谁必须能一句话说清依据。
- 子串而非整词：`blind` 要能对上 `blinds`；中文没有词边界。代价是短关键词会误中，所以纯英文数字的关键词至少 3 个字符，其余至少 2 个字。

### D4 有分组之后，自动起草只认分组，不退回常用供应商

建了分组的人已经表明「我的供应商分品类」。这时项目对不上任何一组，最可能的情况恰恰是「这是另一个品类的标」——把它起草给那份不分品类的常用供应商，正是本 change 要消除的事。所以：

| 操作者的分组 | 比对结果 | 自动起草 |
|---|---|---|
| 没有（或功能关闭） | — | 与现在相同：常用供应商 |
| 有 | 恰好一组，组里有就绪的 | 用这一组 |
| 有 | 恰好一组，组里没有就绪的 | 不起草：`SUPPLIER_GROUP_EMPTY` |
| 有 | 零组 / 多组 | 不起草：`SUPPLIER_GROUP_UNDETERMINED` |

两个新原因都不标 `quiet`（需要人去处理），去处是询价入口。判定顺序放在既有条件之后、「有没有就绪供应商」的位置上，前面的原因（分析没批准、已有轮次等）优先级不变。

- 否决：对不上时退回常用供应商。见上。代价是：只建了一个组的人，其它品类的标不再自动起草——这是有意的。

### D5 抽屉的预选

- 没有分组：不变。
- 有分组、恰好一组对上：预先勾选该组里就绪的供应商（组内顺序），上方一行写依据。
- 有分组、对不上：不预先勾选；一行提示。常用供应商仍排在前面并带「常用」标记，只是不预先勾选（理由同 D4）。
- 分组显示成一排可点的标签；点一个 = 把勾选换成该组里就绪的。之后照常增减。
- 「把分组结果换成勾选」这一步抽成纯函数（输入：分组、比对结果、可选供应商；输出：勾选的 id 与提示文字），抽屉只负责渲染——RFQ-AUTO-4 的教训：组件里的逻辑只靠源码文本断言测不出问题。

入口的供应商列表现在是「active 供应商 ∪ 常用供应商」取最近更新的 100 家；分组里的供应商要并进去，否则组里停用的、或排在 100 家之外的会在抽屉里消失。

### D6 管理分组放在抽屉里

抽屉本来就是勾选供应商的地方，「把当前勾选的存为一组」不需要另造一个供应商选择器。四个动作：存为新分组、用当前勾选覆盖、改名字与关键词、删除（先确认）。每个动作都是「在当前文档上改一处 → 整份 PUT」。

- 接口挂在项目下（`/api/projects/{id}/tender-rfq/supplier-groups`），与 RFQ-AUTO-3 的开关接口同样：借项目写权限做门槛，但写的是本人在该组织的分组，与具体项目无关。
- 否决：单独的设置页。多一处导航，而且要重做供应商选择。
- 否决：细粒度接口（新增一组 / 删一组）。整份替换加版本检查更简单，也只有一种冲突要处理。

### D7 说明文字与审计

- 卡摘要里那一行仍以既有的固定开头起头（轮次列表靠它取这一行），「供应商取自 X 的常用供应商」在用分组时换成「供应商取自 X 的分组『窗饰』（项目名称里有『blind』）」。
- 审计的供应商来源新增一个取值，另记组名、关键词、分组那一版的标识。
- 组名与关键词只进这些内部文字，不进 `buildRfqDocument` 的任何入参——邮件内容与手动选同样几家时逐字相同，测试里直接比对。
- 组名是人填的自由文本，会显示在卡摘要里：按纯文本渲染，长度已限 30 字。

### D8 功能开关

`TENDER_RFQ_SUPPLIER_GROUPS_ENABLED` + `…_ORG_ALLOWLIST`，写法与 RFQ-AUTO-2 的开关相同，默认关。关闭 = 入口不返回分组、保存接口 404、自动起草与抽屉回到常用供应商。已保存的分组留在记录里，重新打开后仍在。

- 说明：没建分组的人本来就不受影响，开关不是必需的；加它是因为这个 change 改的是「起草给谁」，Owner 应当能单独把它关掉而不必关掉整个自动起草。
- 与自动起草的开关互相独立：分组开、自动起草关 → 只有抽屉里的分组可用。

### D9 自动起草时读分组的位置

在 `auto-draft-service.ts` 里，现有「便宜的条件先查」之后、选供应商之前读操作者的分组（一次查询）与项目名称（入口已读）。有分组 → 供应商 id 取自对上的那一组，仍经 `pickAutoDraftSuppliers`（就绪规则、8 家上限、跳过原因都不变）。`prepareRfqRound` 的流程不改，只多一个可选入参把「哪一组、哪个关键词」带到卡摘要的那一句里（实施时发现那一句是在建轮次里拼的）。

### 独立审查后补的

- **保存的先后不能靠应用服务器的时钟。** 审计记录的时间是写入那台机器的时钟给的（不是数据库时间）。两台机器时钟有先后、或时钟被往回拨时，新写的一条会排在旧的后面，「最近一条」仍是旧的——保存显示成功却不生效。改为：持有本人的锁时明确给时间，至少比上一条晚 1 毫秒；保存后直接用新记录的号做版本，不再回读。
- **看不见或无效的字符在入口拒绝。** 名字里的空字符或落单的代理项能通过校验，之后写审批卡时数据库拒收，建好的第 1 轮被标为取消——而取消的轮次也算数，这个项目从此不再自动起草。现在名字与关键词里的控制字符、格式字符、无效编码一律 400；供应商号只认常规 id 字符（带空字符的号原来会让查库抛错变成 500）。
- **读比写宽。** 读库里那份原来复用保存时的严格校验，任何一项不合规就整份当空——哪天把上限收紧，存量的分组会被当成「没有分组」而退回常用供应商，正是 D4 要避免的。现在读只要求结构对；有记录却完全读不出来时标为「读不出来」，自动起草据此不起草。
- **组织里一家能发的供应商都没有时**，有分组的人得到的是分组的原因，而不是「去攒常用供应商」。
- **关键词不能带分隔符**：界面按逗号、顿号、分号拆关键词，带着它存下来，下次编辑就会被拆成两个。
- **比对前去掉软连字符等格式字符**：从 PDF 贴过来的项目名称里常有。
- 没有改的（审查提到、判断为可接受）：大小写按 `toLowerCase` 而不是完整的大小写折叠（`İSTANBUL` 对不上 `istanbul`、`strasse` 对不上 `straße`）；子串误中（`led` 对上 `Scheduled`）是 D3 明说的代价。

## 与八条硬纪律的关系

1. **零 schema**：遵守。分组是 `AuditLog` 里本人的只追加记录（最近一条即状态），不新增表与字段，也不放进 `Organization.settingsJson`。
2. **出站先审批**：遵守，不改纪律文字。本次不新增任何出站路径：分组只决定抽屉里先勾选谁、自动起草的卡起草给谁；卡仍是待批的，仍须人在网页上批准才发。分组的名字与关键词不进询价单与邮件。
3. **禁止第三套队列**：遵守。没有新增任何后台执行；保存时的事务级锁随事务结束释放，不是队列。
4. **脱敏**：遵守。新的响应字段只有分组的名字、关键词、供应商号与家数；不含价格、估值、毛利。Muse 通道没有新增内容。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。项目用哪一组是文字比对，恰好一组对上才用；不新增模型调用；不往 Muse 的偏好里写任何东西。
8. **测试注册**：两个新测试都注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。

## Risks / Trade-offs

- **关键词误中 → 起草给错的一组。** 卡摘要写明组名与关键词，收件人列在卡上；自动起草的卡只能在网页批（Muse 里批不了）。误中的后果是「起草了一张要驳回的卡」，不是「发错了」。
- **只建一组的人，其它品类的标不再自动起草。** 有意为之（D4）；结果行会说明原因。想恢复原样：删掉分组，或关掉开关。
- **建了分组但没填关键词 → 永远对不上，自动起草一直不触发。** 保存没有关键词的组时界面提示「没有关键词的组不会被自动选中」。
- **`AuditLog` 当存储。** 读是一次按（对象类型 + 对象 id = 本人）走既有索引的查询，与 RFQ-AUTO-3 的开关相同；记录量 = 保存次数，很小。
- **分组里的供应商后来被停用 / 删掉邮箱。** 不自动移出（否则人不知道组变了）；抽屉里标不可选，自动起草时跳过并计数，全部不可用时不起草。
- **两套「我的供应商」并存（常用供应商、分组）。** 短期内有重叠感；合并它们要动 Muse 的偏好与学习逻辑，不在本次范围。
- **隔离库测试在 CI 里跳过**（仓库现状）：本地跑并在报告里写明。

## Migration Plan

无数据迁移。上线后开关默认关；打开后没有分组的人行为不变。回滚 = 关开关；代码回滚也不留脏数据（多出来的只是审计记录）。

## Open Questions

需要 Owner 看一眼、不同意就在审核时说的三处（都已按推荐写进四件套）：

1. **分组按人**（D1）。如果你更想要「全组织共用一套分组」，范围和权限都要变，告诉我。
2. **有分组之后对不上就不起草，不退回常用供应商**（D4）。
3. **只比项目名称**（D3）。如果你们的项目名称经常不写标的（比如只写编号），这个办法的命中率会很低，需要换一个依据。
