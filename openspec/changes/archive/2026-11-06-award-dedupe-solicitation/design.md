# Design：不同招标编号不判疑似重复（P2-0c）

## Context

`createOrObserveAwardRecord` 去重三层：①同源幂等（orgId + sourceType + sourceKey）；②强匹配（同编号 + 同中标方，或同中标方 + 同日期 + 同金额）→ 挂源到既有记录；③弱信号（同中标方 + 同买家）→ 新建 NEEDS_REVIEW 并指向疑似原记录。第③层没有看编号。

## Decisions

### D1 只在"两条都有编号且不同"时放行
编号是招标的自然键；两条都有且不同，几乎可以肯定是两次招标。编号缺一方时无法区分，保持人工裁决。
否决：按日期间隔放行（多久算另一次没有确定口径）；按金额不同放行（同一招标的修订额也会不同）。

### D2 编号比较做规范化
大写、去空白与标点后比较。只差写法（`PW-2024-001` / `pw 2024 001`）视为相同编号 → 仍判疑似重复（强匹配用的是原值精确比较，写法不同时落到弱信号，交人工）。规范化只用于判断，不改存储值。

### D3 扫描候选而非取第一条
改为 `findMany`（按创建时间，最多 200 条）后找第一条"不是另一次招标"的记录作为疑似原记录；全是不同编号 → 不标记。上限防止异常数据下全表扫描。

## Risks / Trade-offs

- 同一招标被两个来源用完全不同的编号记录（例如一个用内部编号、一个用公开编号）会变成两条 ACTIVE。概率低；比现状（所有重复中标都被压成线索）代价小。
- 历史 NEEDS_REVIEW 记录不回溯。

## Migration Plan

无 schema / 数据迁移；纯代码，随部署生效；回滚 = 还原文件。已写入的记录不受影响。
