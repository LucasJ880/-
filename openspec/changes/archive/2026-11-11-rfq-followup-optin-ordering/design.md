# Design：个人开关的写入加锁并明确给记录时间（RFQ-AUTO-3a）

## Context

读代码确认的现状：

- `loadAutoDraftFollowUpOptInState`：`auditLog.findFirst`，`orderBy: [{ createdAt: "desc" }, { id: "desc" }]`。
- `setAutoDraftFollowUpOptIn`：读当前状态 → `optInNeedsWrite` → `writeAuditLog(db, …)`。没有事务，没有锁。
- `AuditLog.createdAt` 由应用服务器取当前时间写入。RFQ-AUTO-5 的独立审查记下了实际的写入语句：时间是一个绑定参数，比同一事务里数据库的 `now()` 晚了 700 毫秒——不是数据库时间，也不是事务开始时间。
- `id desc` 作为次序救不了：记录号的计数器是各进程自己的。

RFQ-AUTO-5 的供应商分组有同样的结构，已经用下面的办法修了（#431），并有真库测试：把上一条记录的时间拨后 30 秒，再保存，新保存仍然生效。

## Goals / Non-Goals

**Goals**：最后一次设置一定生效；同时到达的设置不留下不一致的状态；对外行为（接口、界面、记录内容）不变。

**Non-Goals**：不改读取；不改全仓审计的时间来源；不回头修旧记录。

## Decisions

### D1 一个短事务：取本人的锁 → 读最近一条 → 需要才写

`pg_advisory_xact_lock(hashtext('rfq-auto-followup-optin:<组织>:<用户>'))`，事务结束自动释放。事务里只有：取锁、读最近一条、（需要时）写一条。不包任何别的调用——RFQ-AUTO-2 里咨询锁出过连接池问题，是因为锁里包了整个建轮次。

- 否决：只给时间、不加锁。两次同时到达的设置会读到同一个「上一条」，算出相同的时间，先后仍然不定。
- 否决：把读也改成别的排序（比如按记录之间的前后指针）。要改读取方和已有记录的含义，动得更多；有了「时间严格递增」，现有的读法就是对的。

### D2 记录时间 = max(现在, 上一条的时间 + 1 毫秒)

持有锁时上一条不会再变，所以新记录一定排在它后面。数据库里这一列是毫秒精度，1 毫秒足够。

- 代价：上一条的时间如果被拨得很靠后（比如时钟错了一小时），之后的记录时间会跟着靠后，直到真实时间追上。记录的先后是对的，只是时间戳不是真实的操作时间；`beforeData` 里仍有操作前的状态，审计可读。
- 直接用 `tx.auditLog.create`（而不是 `writeAuditLog`），因为要指定时间。写入的字段与 `writeAuditLog` 写的相同（操作者、组织、项目、动作、对象、前后内容）。不改 `src/lib/audit/logger.ts`，免得动到全仓的审计写入。

### D3 返回值不变

仍是 `{ ok, state, changed }` 或 `{ ok: false, errorCode: "DISABLED" }`。「开启要求两个功能开关都打开」的检查留在事务之外（不查库）。模板指纹照旧在写入时记下。

## 与八条硬纪律的关系

1. **零 schema**：遵守。不新增表与字段；仍是 `AuditLog` 里的记录，只是写入时明确给时间。
2. **出站先审批**：不涉及出站路径。本次让「撤回同意」可靠：开关关了，之后自动起草的卡就一定不带跟进授权；带授权的卡仍须人批准才生效。
3. **禁止第三套队列**：遵守。没有新增任何后台执行；事务级的锁随事务结束释放，不是队列。
4. **脱敏**：不涉及。接口的请求与响应不变。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。没有模型调用；状态仍是查最近一条记录。
8. **测试注册**：没有新增测试文件；改动的两个测试文件都已注册。

## 验证方式

- `npx tsx src/lib/tender-rfq/__tests__/auto-draft-db.isolated.test.ts`（本地隔离库，第 17 段）：同时到达两次开启只写一条；已经是开时不写；同时到达四开四关，记录严格开关交替、时间严格递增、最终状态就是最后一条；上一条记录时间比现在晚 30 秒时关闭照样生效，随后自动起草的卡不带授权；再开启后仍交替、递增。
- 同一份测试在 `main` 的旧实现上跑：第 17 段应有失败（时钟那三条必然失败；四开四关那条在没有互斥时写出连续的「关」）。
- `npx tsx src/lib/tender-rfq/__tests__/auto-followup-optin.test.ts`：先取锁、再读、再写的顺序与记录时间的算式（源码断言）；只追加、不读不写组织设置等既有断言。
- `npx tsx src/lib/tender-rfq/__tests__/web-entry-pure.test.ts`：既有的接线断言不改即通过。
- 全量：`npm run test:ci`、`npm run typecheck`、`npm run lint:baseline`、`bash scripts/check-test-registry.sh`、`bash scripts/test-runtime-architecture.sh`。
- 开 PR 前请一个不带结论的独立审查（改的是同意类开关）。
- `openspec validate rfq-followup-optin-ordering --strict`。

## Risks / Trade-offs

- **多一次事务往返**：设置开关是人的低频操作，可以忽略。
- **极端并发下会出现以前没有的失败**：同一个人的设置现在排队执行，独立审查实测同一进程内同时 400 次全部成功、1500 次时约一半因为等不到数据库连接而失败（返回错误、什么都不写，界面提示「没有设置成功，请重试」）。旧实现这时全部「成功」，但写出的记录先后是乱的。一个人不可能同时点几百次，可以接受。
- **读开关与建卡之间仍有一个很短的空档**（既有行为，本次没有动）：自动起草先读开关、稍后才建卡，恰好在这中间关闭的话，这一张卡仍带授权——它仍要人批准才生效。
- **滚动发布期间**：旧版本的实例还在按自己的时钟写、不加锁；如果新版本刚写了一条被顺延到「未来」的记录，旧实例随后写的一条会排在它前面。只在新旧版本并存的几分钟里存在。
- **正确性依赖数据库的默认隔离级别（读已提交）**：取到锁之后的那次读要能看到别人刚提交的记录。审查确认了事务里实际的隔离级别，仓库里也没有别处改它。
- **修复之前已经排错的记录**：如果某人现在的状态因为旧的时钟差而与他的最后一次操作不符，他在界面上看到的就是那个状态，点一次即可纠正——修复之后的写入一定排在最后。
- **隔离库测试在 CI 里跳过**（仓库现状）：本地跑并在报告里写明。

## Migration Plan
