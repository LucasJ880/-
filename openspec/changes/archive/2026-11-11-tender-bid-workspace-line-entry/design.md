# Design

## Context

- TI-4a 的保存接口按块替换：`lineDetails` 给了就整块替换，所以界面保存一行时要带上其它行的已存明细。
- TI-3b 的认证闸有六个条件；`findStaleConclusions` 按「行 + 补遗号」判断结论是否待复核，但 TI-4a 传给它的结论列表一直是空的。
- 存储位置是情报室 JSON 位下的 `bidWorkspace` 键，对所有项目读者可见；证书编号、发证机构、出处不是金额类数据，可以放。

## Goals / Non-Goals

**Goals:**

- 在界面上能把一个真实的标从「不可投标」推进到只剩成本与截标两类阻断项。
- 「已核验」必须带出处，且在写入口强制。
- 补遗真正影响判定。

**Non-Goals:**

- 证书文件上传、真伪核验、角色更细的核验权限。
- 改认证闸或判定规则本身。

## Decisions

### D1 「已核验须有出处」放在保存请求的校验里，不放进认证闸

认证闸是纯函数，已有测试与样例都不带出处；把条件加进去会让既有调用方全部变成不通过。放在保存请求上：从今往后存不进没有出处的「已核验」证书。已存内容的读取校验不加这一条——否则一条旧记录会让整个工作区读不出来。

备选：读取时把没有出处的「已核验」降为「声称」。没选，因为会让存的和显示的不一致；开关默认关，线上没有旧数据。

### D2 `basedOnAddendum` 由客户端带上，服务端只向下限制

界面保存一行时带上当时影响该行的最新补遗号，表示「按这一版核对过」。服务端合并时取 `min(带上的号, 实际最新号)`，不带则记 0。不能虚高，所以不可能靠虚报绕过复核。

备选：服务端比较前后内容，变了才盖章。没选，因为「内容没变但已按新补遗复核」是常见情况，需要一个不改内容也能确认的动作；重新保存就是这个动作。

### D3 待复核结论由行明细现算

有产品尺寸的行生成一条「尺寸对照」结论，有品牌型号或证书且带认证要求的行生成一条「认证判定」结论，都以该行的 `basedOnAddendum` 为基准，交给既有的 `findStaleConclusions`。不新增存储。

### D4 行录入是表格行下方的展开区，不开弹窗

每次只展开一行；保存成功即收起并用接口返回的结果刷新。证书在同一展开区里逐张编辑。

## Risks / Trade-offs

- 有项目写权限的人都能把证书标成「已核验」。缓解：必须填出处；每次保存写审计（谁、何时、改了哪一块）；面板写明是人工确认。是否收窄到特定角色待 Owner 决定。
- 整块替换 `lineDetails` 在两人同时编辑不同行时后写覆盖先写。缓解：服务端加锁读改写保证不坏数据；界面保存前用的是最近一次读取的内容。可接受（同一个标通常一人录入）；真要解决需要按行保存的接口，另起 change。

## Migration Plan

无迁移。新增字段可选；旧内容照常读出，`basedOnAddendum` 缺省按 0。回滚：关开关，或回退本 PR。
