# Design：审批草稿可改（NAV-3）

## Context

动机见 proposal.md。以下是核对到的现状（main `43be745f`）。

**待批草稿里有可直接复用的原文**（任务书前置条件「核对草稿载荷里是否存有可直接复用的原文」）

- 询盘回复草稿是一条审批记录，类型 `sales.send_inquiry_reply`，载荷里有 `to`（客户邮箱）、`subject`、`body`（纯文本原文）、`html`（起草时渲染的整封邮件）、`language`、`opportunityId` 等（`src/lib/revenue-spine/fde/inbound-sales.ts:665-676`）。展后无回复的跟进草稿用的是同一个类型。
- 审批卡上看到的「预览」不是原文：它在原文前面拼了风险提示，后面拼了中文对照，并截到 4000 字（`inbound-sales.ts:143-152`）。所以要预填，只能取载荷里的 `subject` 与 `body`，不能拿预览文字。
- 载荷正文上限 10000 字（审批执行时 `exec-sales-inquiry-reply.ts:98`）；收件箱回复接口的正文上限是 8000 字，超出静默截断（`api/trade/inbox/[prospectId]/reply/route.ts:38`）。

**谁看得到草稿、谁能发**

- 今日询盘与商机详情的接口按外贸读权限放行（`src/lib/revenue-spine/access.ts:23-24`，营收读写键就是外贸读写键），返回每张草稿的预览；商机详情还能看整封邮件效果。也就是说，能打开询盘收件箱的人本来就看得到这些草稿的内容。
- 草稿建立时指定了审批人（`inbound-sales.ts` 里的 `approver`）。批准后由系统执行发送，执行时有几道检查（`exec-sales-inquiry-reply.ts:104-140`）：审批人是本企业在职成员；买家带入驻测试标记的一律不发（「入驻测试询盘不会发送给买家」）；收件人取载荷里的 `to` 且必须与客户档案邮箱一致；买家在起草之后又来了新信就拒绝执行；起草之后已经有过外发也拒绝执行。
- 成员本人在询盘收件箱点「发送邮件」是另一条既有的路（`docs/QINGYAN_MENGXIN_FDE_V1_TRADE_OUTBOUND_SYNC.md`：Trade sends stay human-click actions），要求 `trade.manage`，收件人取线索的邮箱，发的是纯文本。NAV-1c 之后，持 `trade.manage` 的人已经可以从审批卡点进收件箱自己写一封发出去，也可以把审批卡上看到的草稿抄过去。

**发出之后**

- 收件箱的真实外发会把同商机所有待批的询盘回复草稿由系统作废，并为每份被作废的草稿记一条「人工已回复」的改稿反馈，反馈里对比的是草稿与实际发出的文字（`src/lib/trade/outbound-sync.ts:8-15,140-150`，`src/lib/revenue-spine/fde/draft-feedback.ts`）。所以「改一句再发」不需要新写任何反馈逻辑：既有机制会把它记成一次改稿。

**现在的入口**

- 审批卡上的链接 `inboxReplyHref({ opportunityId })` 只带商机 id（`revenue/today/page.tsx`、`revenue/[id]/page.tsx:325`）；今日询盘上它在卡片最下方，不展开草稿也看得到。
- 收件箱的深链分支请求单会话接口后打开空白窗口；不能回复的成员只提示、不开窗口（NAV-6）。

## Goals / Non-Goals

**Goals**

- 从待批草稿卡进收件箱时，窗口里就是这份草稿的原文，改完直接发。
- 发出后的作废与改稿反馈沿用既有规则，不新增发信通路。
- 草稿已经失效时不让人对着一份过期的文字发信。

**Non-Goals（具体到文件）**

- `src/lib/pending-actions/**`（建卡、批准、执行、作废、快照）、`src/lib/revenue-spine/**`（起草、反馈、今日询盘读模型）、`src/lib/trade/outbound-sync.ts`、`src/lib/trade/email-sender.ts`。
- `api/revenue/**` 的任何接口；今日询盘与商机详情的「批准发送」「拒绝」「查看邮件效果」。
- `GET /api/trade/inbox` 列表接口；客户时间线与卡片按钮进入回复窗口的行为。
- `src/lib/navigation/**`（含 `help-tasks.ts` 第 3 行）、路由门映射表、权限键、岗位模板、Prisma schema、`vercel.json`。

## Decisions

### D1 草稿原文由单会话接口带回，凭草稿 id 取

`GET /api/trade/inbox/focus` 加可选参数 `approvalId`。带上时，在解析出这位买家之后再取这条审批记录，七个条件全满足才返回 `approvalDraft: { pendingActionId, subject, body, to }`：属于本企业；类型是询盘回复；状态为待批；未过期；载荷里的商机 id 等于这位买家对应的商机；该商机的买家不带入驻测试标记（与审批执行「入驻测试询盘不会发送给买家」同一口径）；主题与正文都非空。判定写成纯函数放在 `src/lib/trade/reply-target.ts`，接口只负责取数。不满足一律为空，不区分原因。

- 否决新开一个「取待批草稿原文」的接口：页面本来就要请求单会话接口，新接口还要进外贸守卫处理器的盘点。
- 否决不带 id、接口自动返回这个商机最新的一份待批草稿：那样从客户时间线点「回复」也会被预填，超出任务书「从待批草稿卡进入时」；同一商机有多份待批草稿时也说不清带的是哪一份。
- 否决把主题与正文直接放进地址参数：正文可达上万字，且买家信息会进浏览器历史与访问日志。
- 否决返回 `html`：收件箱回复发的是纯文本，用不上；少暴露一个字段。

### D2 深链地址：`/trade/inbox?opportunity=<商机 id>&approval=<草稿 id>`

`inboxReplyHref` 接受可选的草稿 id。页面读到 `approval` 就把它作为 `approvalId` 带给单会话接口。打开后与现在一样把地址参数去掉。

- 否决只带草稿 id、由接口反查商机：现有深链按商机解析买家的逻辑可以原样复用，草稿 id 只多做一次核对。

### D3 回复窗口多一种开法

窗口现在有两种开法（带收件箱分析草稿、空白）。加第三种：带待批草稿。

- 标题「改草稿再发 · 〈公司〉」；副标题「这是等审批的那份 AI 草稿，改好后点「发送邮件」。发出后那份草稿自动作废，不用再去批准；从这里发出的是普通文本邮件。」
- 主题、正文预填草稿原文；提交时声明来自 AI 草稿（沿用 NAV-1c 的口径：改过的草稿仍算来自 AI 草稿）。
- 草稿的 `to` 与线索邮箱不同时（忽略大小写与首尾空格），在窗口里加一行：「这份草稿原本发给 A；从这里发送会发给 B。」线索没有邮箱时，「发送邮件」按现状不可用。
- 没有「看中文对照」：中文对照只存在于审批卡的预览里，没有单独存。

- 否决复用「带收件箱分析草稿」那种开法、只换数据：两种草稿的来源、说明文字与后果不同，混在一起会让标题和副标题说错话。
- 否决在窗口里再显示一遍风险提示：风险提示没有单独存，只能从预览文字里切，切不准；改由 D5 保证进来之前看过。

### D4 草稿不可用时：提示并打开空白窗口

`approvalDraft` 为空（处理过、过期、不属于这位买家）时，提示条写「这份待批草稿已经处理过或已失效，可以直接在下面写回复」，窗口按「写回复」的规则打开（正文空、主题按来信预填、不声明来自 AI 草稿）。

- 否决不开窗口只提示：用户点进来就是想回复，草稿没了也应该能回。
- 否决仍然预填已失效草稿的文字：已作废的草稿多半是因为有人已经回过，或买家又来了新信，照着发会重复或答非所问。

### D5 今日询盘上，链接只在展开草稿之后出现

把这行链接移进「查看草稿」展开的区块里。「批准发送」本来就要求先展开；改稿再发同样应该先看过预览（里面有风险提示）。商机详情的草稿预览一直是展开的，链接位置不变。

- 否决保持在卡片最下方、随时可点：那样可以不看风险提示就把草稿带走发出去，比「批准」的门槛还低。

### D6 回复接口的正文上限提到 10000 字

与待批草稿的正文上限一致。只改这个数字。

- 否决保持 8000、在窗口里提示超长：一份合法的待批草稿被带进来就发不全，问题出在两个上限不一致，不该让用户删字。
- 否决去掉上限：没有理由放开。

### D7 测试放哪

- 新增 `src/lib/trade/__tests__/approval-draft-edit.test.ts`（纯函数 + 源码断言）：判定的七个条件、地址、两个审批面的链接、深链与窗口的三个分支、收件邮箱提示、接口只读与返回字段。注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。
- `reply-entry-db.isolated.test.ts` 加第 5 组：真实的待批草稿 → 接口返回四个字段；四种不可用情况都为空；改后经回复接口提交 → 留底是改后的文字、标记为真、草稿被系统作废且载荷原文未变；9500 字不被截短。
- `reply-entry.test.ts` 里钉着旧链接文字的断言、`reply-clarity.test.ts` 里钉着深链分支形状的两条断言，随实现调整，通过数不降。

## 与八条硬纪律的关系

1. **零 schema**：遵守。只读既有审批记录的载荷，不加字段、不写迁移。
2. **出站先审批**：**不新增出站通路，但请留意这一条。** 改后的邮件走既有的「成员本人在收件箱点发送」，不是系统代发；待批草稿不被批准、不被执行，发出后按既有规则作废。它带来的变化是方便程度：持 `trade.manage` 的成员可以把一份 AI 待批草稿的原文带进编辑框、改完自己发出去，而不经过草稿指定的审批人点「批准」。这件事今天已经做得到（看着审批卡抄过去，或用收件箱自己的 AI 分析草稿），本 change 只是省了抄的那一步；作为补偿，今日询盘上的入口改为先展开草稿才出现（D5）。审批执行的几道检查在这条路上是这样对应的：入驻测试询盘的草稿不提供原文（D1 第六个条件）；收件人取的是线索邮箱而不是草稿的 `to`，不一致时窗口里写明（D3）；「起草之后已经有过外发」的草稿此时已被既有规则作废，取不到原文；「买家在起草之后又来了新信」没有照搬成拒绝——窗口上方显示的是买家最新一封来信，由人判断。
3. **禁止第三套队列**：不涉及。
4. **脱敏**：不涉及 Muse 桥接。`approvalDraft` 只返回主题、正文、收件邮箱与草稿 id，都是该成员在审批卡上本来就看得到的内容；不返回 HTML 与内部元数据；跨企业、跨买家一律为空且不区分原因。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不动发件实现与发件人设置。从收件箱发出用的是外贸发件身份，审批执行用的是组织发件身份（没有配置时才退回审批人邮箱）；本 change 不改任何一边，差异记入报告。
7. **确定性优先**：遵守。零新增模型调用；预填的是已经存在的文字。
8. **测试注册**：遵守。新增一个测试文件，同一个 task 里注册；基线不增。

## Risks / Trade-offs

- [从收件箱发出的是纯文本，没有审批发送用的 HTML 排版；买家收到的样子与「查看邮件效果」里看到的不同] → 窗口副标题写明「从这里发出的是普通文本邮件」；统一两条路的排版不在本次范围。
- [改稿再发绕过了指定审批人] → 见上面第 2 条；既有能力，本次只是更顺手，并加了「先看草稿」的门槛。若要收紧（例如只有审批人本人能带走草稿），需要另立 change 定规则。
- [窗口里看不到风险提示与中文对照] → 进入前已在审批卡上看过（D5）；商机详情上预览始终展开。
- [用户把预填的文字全删掉自己重写，留底仍记成来自 AI 草稿] → 与 NAV-1c 的口径一致（不比对内容）；改稿反馈里的对比结果会如实反映几乎全改。
- [同一商机有多份待批草稿时，发出后全部作废，而窗口里只带了其中一份] → 既有规则就是全部作废；窗口副标题说的是「那份草稿自动作废」，对用户点进来的这一份成立。
