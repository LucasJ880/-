# Design：询盘收件箱里「谁回复了谁」说清楚（NAV-6）

## Context

动机见 proposal.md。以下是核对到的现状（main `59ab1837`）。

**「已回复」在外贸线索上指的是买家来信**

- 线索阶段 `replied` 的显示名在 `src/lib/trade/stage.ts:79` 是「已回复」。
- 这个阶段是买家来信时进的：官网询盘进线先建成 `new`，随即推进到 `replied`（`src/lib/trade/website-inquiry.ts:743,769`）；WhatsApp / 微信 / 邮件渠道来信同样推进到 `replied`，代码注释是「买家主动来信 → 进当日待回复队列」（`src/lib/trade/channel-service.ts:518-523`）。我方在收件箱回复之后阶段不变，仍是 `replied`（`api/trade/inbox/[prospectId]/reply/route.ts:71` 用的是「至少已触达」，只升不降，`stage.ts:190-194`）。
- 所以这个阶段的意思是「买家来过信」：一条刚进线、我们一个字没回的询盘是它，我们回过之后也还是它。它既不表示「我方已回复」，对第一次主动询盘的买家也谈不上「买家回复了我们」。

**这个名字出现在哪**

| 位置 | 来源 |
|---|---|
| 询盘收件箱卡片上买家名字旁的灰色标签（`trade/inbox/page.tsx:429`）、线索详情（`trade/prospects/[id]/page.tsx:804`）、外贸获客首页线索列表（`trade/page.tsx:493`）、活动详情（`trade/campaigns/[id]/page.tsx:433`） | 读阶段表 |
| 驾驶舱漏斗（`src/lib/cockpit/metrics-engine.ts:35-37`） | 读阶段表 |
| 外贸助手的线索列表与详情文字（`chat-assistant.ts:409,436,477`）、数字员工外贸工具的 `stageLabel`（`agent-core/tools/trade.ts:209`）、秘书跟进引擎的「当前阶段」（`secretary/followup-engine.ts:286-291`） | 读阶段表 |
| 外贸获客首页概览卡（`trade/page.tsx:231`） | 写死「已回复」 |
| 外贸看板接口的漏斗（`api/trade/dashboard/route.ts:105-107`） | 写死「已回复」 |
| 活动统计接口的漏斗（`api/trade/campaigns/[id]/stats/route.ts:45-47`） | 写死「已回复」 |
| 外贸助手的阶段分布（`chat-assistant.ts:353`） | 写死「已回复」 |

Muse 桥接不读外贸线索阶段（`grep` 核对），没有受影响的 Muse 意图。

**询盘收件箱自己的「已回复」指的是我方回复**

- 卡片下方绿色文字「已回复」（`trade/inbox/page.tsx:467`）与按钮「已回复，标记」（`:505`）说的是我方。
- 于是一张等我们回复的卡片：名字旁「已回复」（阶段）、右边「写回复」「已回复，标记」（操作）。NAV-1c 的截图 `docs/acceptance/nav-1c/03-cathy-inbox-cards-write-reply.png` 第一张卡片就是这样。

**只能查看的外贸成员：现在没有这样的账号**

- 外贸读接口要 `trade.read` 或 `trade.manage`，写接口要 `trade.manage`（`src/lib/trade/access.ts:156-158`）。收件箱页面不区分两者，所有按钮都画出来；只持 `trade.read` 的人点发送会被回复接口 403。
- 但系统里含 `trade.read` 的岗位模板一共三个（系统模板企业负责人、`trade_rep` 外贸业务员、窗饰老板），每一个都同时含 `trade.manage`（`src/lib/authorization/role-defaults.ts:40-41,133-134,246-247`）；旧模式的兼容回退给的也是 `trade_rep`。岗位的权限键只由种子写入（`src/lib/authorization/seed-org-profiles.ts`），企业不能自建岗位。
- 结论：**今天没有任何账号是「只能看外贸、不能处理」的，这个问题目前不会有人遇到。** 本 change 里与它有关的部分是预防性的——以后一旦加出只读的外贸岗位（例如跟单、助理查看），收件箱不会出现点了没用的按钮。
- 两个收件箱接口已经在响应里带 `capabilities.emailSend`（`api/trade/inbox/route.ts:34-36`、`api/trade/inbox/focus/route.ts:34`）。浏览器端现有的 `useNavigationAccess` 只能回答「某个页面能不能打开」，拿不到权限键。

## Goals / Non-Goals

**Goals**

- 同一张卡片上「买家来信了」与「我方回复了」不再是同一个词。
- 这个阶段的名字只有一个来源，各处不会再各写各的。
- 不能回复的成员在收件箱看不到回复操作，判断只有服务端一个来源。

**Non-Goals（具体到文件）**

- `src/lib/trade/stage.ts` 里阶段取值、先后顺序、别名映射、颜色、漏斗顺序；其他阶段的显示名。
- `api/trade/dashboard/route.ts` 与 `api/trade/campaigns/[id]/stats/route.ts` 里其余各档的 `label`（例如「已联系」与阶段表「已触达」的既有差异）、各档包含的阶段集合与计数。
- `POST /api/trade/inbox/[prospectId]/reply`、`src/lib/trade/outbound-sync.ts`、`src/lib/trade/email-sender.ts`。
- `src/lib/authorization/**`（权限键、岗位模板）、路由门映射表、`src/lib/navigation/**`（含 `help-tasks.ts`）。
- 线索详情、外贸报价、寄样等其他外贸页面的按钮显隐；收件箱卡片上的「打开线索」「新建报价」「开寄样单」。
- `revenue/today/page.tsx`、`revenue/[id]/page.tsx`、客户详情时间线（NAV-1c 的入口条件不动）。
- `src/lib/tender-rfq/**`、`src/lib/inquiry/**`、`src/components/inquiry/**` 里各自的「已回复」。
- Prisma schema、`vercel.json`。

## Decisions

### D1 阶段名定为「买家已来信」

沿用阶段表里「已触达 / 已报价 / 已转化」的「已 + 动作」句式，主语写明是买家；与 NAV-1c 时间线上的「客户来信」是同一件事的两个视角。

- 否决「买家已回复」：这个阶段是买家来信就进，包括第一次主动询盘；对一条我们从没联系过的官网询盘说「买家已回复」，仍然是错的。
- 否决只在询盘收件箱里把这个标签藏掉：线索详情、外贸获客首页、漏斗上同一个词的歧义还在，而且收件箱会少一条有用的信息（阶段）。
- 否决改成「待回复」：我方回复之后线索仍停在这个阶段，那时它并不待回复；等不等我方回复，收件箱已经用「等了 N 分钟」与「我方已回复」表达。

### D2 四处写死的名字改为读阶段表

概览卡、看板漏斗、活动漏斗、助手阶段分布这四处的「已回复」改成取阶段表里 `replied` 的显示名。只换这一个词；这四处其余各档的文字保持原样。

- 否决四处各自改成新词：这次的歧义正是「各写各的」留下的，再写死四次，下次改名还会漏。
- 否决顺手把这四处的全部文字都改成读阶段表：看板漏斗的「已联系」「成交」与阶段表的「已触达」「已转化」是既有差异，统一它们是另一件事，且会改更多对外文字。

### D3 收件箱里我方的状态写「我方已回复」；按钮「已回复，标记」不改

卡片下方的绿色状态文字改成「我方已回复」，与时间线的「我方发出」同一口径。按钮名不动：它是一个由本人点的操作，紧挨着「写回复」，读成「我已经回复了，标记一下」没有歧义；使用说明「我想做什么」第 3 行原样引用了这个按钮名（`src/lib/navigation/help-tasks.ts:29`），`entry-visibility.test.ts` 守着两者一致。

- 否决把按钮也改成「我方已回复，标记」：更长，且要连带改使用说明与守着它的测试；阶段标签与状态文字改完后卡片上已经不存在两个相反的「已回复」。见「审核关注点」Q2。

### D4 能不能回复由服务端在响应里给出

两个收件箱接口的 `capabilities` 加 `reply`：平台 super_admin 为真，否则看当前企业里是否持 `trade.manage`（与回复接口的守卫同一个判定）。页面只读这个布尔值。回复接口的服务端校验不动，标记只管界面。

- 否决在浏览器里按权限键自己判断：浏览器现在拿不到权限键，要么新增一个取权限键的通道，要么复制一份判定，都会出现第二个事实来源。
- 否决新开一个「我能做什么」接口：页面本来就要请求列表接口，多一个字段即可；新接口还要进外贸守卫处理器的盘点。
- 否决用 `useNavigationAccess().canOpen("/trade/inbox")`：它回答的是读权限，只读成员也是真。

### D5 `reply` 为假时页面怎么表现

- 卡片：不渲染「写回复」「再写一封」「已回复，标记」。「打开线索」「新建报价」「开寄样单」是跳去别的页面的链接，不在本次范围。
- 「查看回复草稿」保留：AI 草稿是读得到的内容。窗口里主题与正文只读，不渲染「发送邮件」「已在别处发送，标记」，保留「复制内容」与「看中文对照」，副标题位置写「你的岗位只能查看询盘，不能回复」。
- 深链（`?prospect=` / `?opportunity=`）：不请求单会话接口去开空白窗口，直接在提示条里写同一句话，并照常去掉地址参数。
- 列表首次返回之前 `reply` 未知，按假处理（按钮先不画，返回后再出现），避免先画出来又消失。

- 否决只读成员连「查看回复草稿」也不给：那是把读权限也收窄了，超出「不出现点了没用的操作」。
- 否决按钮照画但置灰并加提示：四个置灰的按钮比没有按钮更吵，而且「为什么灰」还得再解释。
- 否决深链时仍打开只读的空白窗口：一个什么都不能做的空窗口没有用。

### D6 测试放哪

- 新增 `src/lib/trade/__tests__/reply-clarity.test.ts`（纯函数 + 源码断言，无 DB）：阶段显示名与四处同源、阶段取值与漏斗定义不变、卡片两种说法、三个按钮与窗口两个按钮的出现条件、深链分支、两个接口都返回 `reply` 且判定用的是处理外贸的键。注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`。
- `reply-entry-db.isolated.test.ts` 加第 4 组：在隔离库里建一个只含 `trade.read` 的测试岗位并绑定给一个成员（只在测试库里建，不进种子、不进岗位模板），核对两个接口的 `reply` 真假、读到的内容相同、回复接口仍 403。
- `reply-entry.test.ts` 里断言按钮渲染条件的两条随新的出现条件调整，通过数不降。

- 否决为只读成员另开一个隔离库测试文件：前置数据（两家企业、进线、商机）与现有文件完全相同，另开一个要重建一遍。

## 与八条硬纪律的关系

1. **零 schema**：遵守。没有新字段、新表、迁移；只读成员的测试岗位只建在隔离测试库里。
2. **出站先审批**：不涉及。不新增也不改变任何发信路径；回复接口与发信实现不动。
3. **禁止第三套队列**：不涉及。
4. **脱敏**：不涉及。Muse 桥接不读外贸线索阶段；新增的 `reply` 是一个布尔值。
5. **不爬登录页**：不涉及。
6. **邮箱分离**：不涉及。
7. **确定性优先**：遵守。零新增模型调用。外贸助手、数字员工外贸工具、秘书跟进引擎读到的这个阶段名随阶段表变化（「已回复」→「买家已来信」），是既有提示里的一个词，不改调用次数与流程。
8. **测试注册**：遵守。新增一个测试文件，同一个 task 里注册进 `scripts/test-all.sh` 与 `scripts/test-ci-unit.sh`；基线不增。

## Risks / Trade-offs

- [改名对所有开了外贸模块的企业可见，老用户已经习惯「已回复」] → 新名字自带主语，不需要另外解释；随 NAV-1 的通知一并告诉梦馨。
- [助手提示里的阶段名变了，模型对「买家已来信」的理解可能与「已回复」略有不同] → 新名字更贴近阶段的真实含义（买家来过信），不会比「已回复」更容易被读反；不改调用与流程。
- [漏斗里只有这一档改读阶段表，旁边仍是写死的「已联系」「成交」] → 有意只动这一个词（D2）；既有差异记入报告，不在本次处理。
- [只读成员的部分今天没有人用得到，却增加了页面里的条件分支] → 分支只有一个布尔值，且都在收件箱一个文件里；见「审核关注点」Q3，可以整块拿掉。
- [`reply` 未知时先不画回复按钮，能回复的成员首屏会晚一拍看到按钮] → 与卡片本身同一次请求返回，不会出现「卡片在、按钮后到」。
